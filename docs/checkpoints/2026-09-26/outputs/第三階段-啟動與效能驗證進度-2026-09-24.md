## 找到的真正風險

### 正常遊戲與第二階段測試走不同計時器

第二階段成功的是原 AIN 的 CASTimer bytecode，測試中清除了 native 攔截旗標。正常遊戲仍使用舊的 native 替代程式，因此原 AIN 路徑通過不等於這個替代程式也通過。

原 AIN 的 Rate getter／setter 是 FLOAT，native 初始值却是 int 1，getter 以整數位元返回。首次讀取可能變成約 1.4×10^-45，而不是浮點數 1.0。GetScaled 也沒有套用 Rate。ReleaseHandle／CheckHandle／GC 沒有完整實作；建立大量計時器後，2048 格表會出現 handle 碰撞。

另外已完成一個使用真 AIN 簽名、直接連結 production native helper 的無畫面診斷，實際重現以下結果：

| 操作 | 實測結果 |
|---|---|
| 首次 Rate::get | `0x00000001` → `1.40129846e-45`，不是 1.0 |
| FLOAT setter 設為 2.5 後再 get | 正確返回 2.5，表示不是所有 getter 讀取都錯 |
| CreateHandle 得到有效 handle 1 後 CheckHandle | 返回 false |
| ReleaseHandle(1) | native 表中的 active 仍為 true |

診斷 exit 0 代表「診斷完成」，不是這些行為通過驗收。它直接呼叫 native helper，未涵蓋 GUI／bytecode method dispatch 整合，也未以實測驗證 GetScaled 或 2048 次建立。完整程式、signature、hash、輸出及重跑命令在 `work/gui-stage3-20260924/native-audit/README.md`。

這些是既有替代程式的問題；**尚未證明它們就是使用者所見卡頓的根因**。不應僅憑本輪啟動失敗就改掉全部計時器。

### 全域物件有重複初始化路徑

靜態追蹤發現 alloc 先呼叫帶參數的建構子，隨後 global pass 又呼叫預設建構子。例如戰鬥背景尺寸先設定 2560×1024，後續預設建構子會清為 0×0；兩個位置物件也可能被清零。

這是具體的程式路徑，但本輪尚未在 GUI 執行到該場景。下一步應記錄同一 slot／generation 在兩次初始化邊界的值，確認後再修「已建構的實例」判定；不能直接刪除全部全域建構流程。

### FPS 數字需要和畫面進度一起看

9 月 9 日舊預覽紀錄的加權 present 約 153.6 次／秒，仍出現最長約 8.64 秒的間隔，且没有 MSG。這只是歷史例子，不是本輪修正後的成績。高平均值仍可伴隨長停頓或重複畫面。

現有 PERF 只在完成 present 後記錄：若最後一幀之後完全卡住，尾段不會進入報告；無法重建全程 p95 或精確長幀次數。退出 peak RSS 也不等於 live AIN heap，不能用單一數字判斷洩漏。
