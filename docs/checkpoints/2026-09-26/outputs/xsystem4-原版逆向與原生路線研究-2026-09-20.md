# 多娜多娜：原版逆向與 macOS 原生路線研究

研究日期：2026-09-20。目標是回答「是否值得跳出持續修補 xsystem4，研究原版後另寫原生核心」。本輪已做本機材料核對、EXE 機器碼分析、真實 AIN 解碼與既有實作審查。**這份是完成的靜態可行性研究；尚未做出可執行的新引擎，也沒有新一輪遊戲端到端測試。**

## 研究結論

**本機材料足以支持有證據的逆向研究。另寫 macOS 原生相容核心有技術依據，但目前最合理的第一個改造邊界是 HLL 介面與型別／引用契約，還沒有證據要求推倒全部引擎。**

這輪找到可讀的歷史 EXE 傾印檔，從機器碼定位原版 Array 與 PartsEngine 的分派入口，並讀出數個實際行為。同時確認：點擊重複、timer、observer 與 Join 等大量策略已存在遊戲腳本，無須把劇情與所有遊戲邏輯重新編寫。

原生方案仍要正確執行原 AIN、保留 closure／reference 的可觀察行為，並提供圖形、輸入、音訊及保存等服務。現有 xsystem4 已建成 ARM64 原生程式；更換執行核心的價值在於提升相容性和可驗證性，不能僅因「重新寫」就承諾更流暢。xsystem4 本身即是 Unix 類系統的 System 4 引擎實作。[專案說明](https://github.com/nunuhara/xsystem4)

**建議採「原版規則取證 → 宣告驅動的 HLL bridge → 獨立生命週期核心實驗 → 接回既有資源／呈現」的順序。** 總體架構可重新設計；已可用的檔案解析、中文與工具應優先保留。

`final6` 的前七個 packed sections 與現用 EXE 逐位元相同；但所查九個原生核心範圍只有 virtual allocation，沒有 file-backed bytes，無法拿同一偏移比較明文核心。研究明確分開 VA、RVA 與檔案 offset，沒有把「位址存在」誤寫成「資料存在」。相關概念依 [Microsoft PE 格式文件](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)。

以下位址是 SCY dump 的 preferred VA，image base `0x400000`，不是正在執行程序的 ASLR 位址。

|---|---|---|

| PartsEngine 入口 | 名稱字串 `0x7cef20` → 分支 `0x4948f7` → dispatcher `0x57b900` → table `0x589714` | 依索引 0–867 分派；全表定位不代表全表語義已還原 |
| IsExist(value)／IsExist(predicate) | Array #56 → `0x644bd5`；#57 → `0x64473a`，分別進不同比較器路徑 | 值搜尋與 callback 搜尋有區分；搜尋結果非負才回 true |
| Erase(predicate) | Array #16 → first-match helper → CArrayPage RTTI/vtable → `0x67f750` | 刪第一個命中；未命中回 false。成功後儲存長度減一；與 EraseAll 不同 |
| clickable setter／getter | PartsEngine #179／180 讀寫同一物件 byte `+0x1a4` | Getter 查無物件回 false；這仍不足以確定點擊事件的消耗時機 |

這些原版證據讓後續實作可以先定契約再驗證。仍未完整讀出的部分包括元素析構、delegate capture／retain、VM 指令分派、事件排程和存檔復原；不把以上幾項延伸成完整引擎規格。

## 大量遊戲策略已在 AIN，不用重新創作

原 AIN 的精確地址與立即參數保存在 [chain-bytecode.json](原生研究-證據-2026-09-20/ain/chain-bytecode.json)，完整分析見 [AIN 核心契約](原生研究-證據-2026-09-20/ain/ain-findings.md)。

1. **按鍵重複是腳本規則。** `CASClick@IsKeyPress` 先回報首次按下；持續按住後先等 350ms，再每 50ms 重複。`IsClick` 另有按下→放開及命中物件一致的判斷。新 native 輸入層應提供正確狀態／時間，避免再重複實作一套互相干擾的規則。
2. **Observer 傳的是可寫回的引用。** `CObserver@Execute` 建立 local `endObserver=false`，用兩槽 ref-bool 交給 delegate；callback 返回後寫入自身 `IsEnd`。callback 清理時，caller frame 必須仍有效。
3. **Join callback 要改兩個不同位置。** CN f36081 同時透過 `X_GETENV` 寫回捕捉的 Join frame `isFinish`，以及參數 `ref End`。只回傳 true 或強制跳過等待不能等價。
4. **移除策略不同。** Observer manager 使用 Array #16 的 first-match Erase；Motion 的 EraseEndTask 使用 EraseAll。這與本輪 EXE 的分派／搜尋證據互相支持。
5. **沒有自訂 destructor 仍需清理成員。** CASTimer 有 ctor420／dtor422；CASClick、CASJoyClick、CObserver 的自訂 destructor 為 -1，仍包含 timer／delegate 等成員。VM 必須按型別清理，不能等候一個不存在的腳本析構函式替它收尾。

這提供了新核心的具體驗收鏈：建立 timer／observer → 正確輸入與時間 → delegate 雙重寫回 → first-match 移除 → typed cleanup → slot 重用。最難處是閉包、別名和生命週期一致性，不能只靠「99 種指令」估算工作量。

## CN 與 JAST 可以共用什麼

兩份既有 `libraries.txt` 完全相同，SHA-256 為 `95402d7f3969b812927ed9cdeae12915f512724eec2e882e25ff7b2cd32589d3`；五個所選核心函式的 opcode 序列形狀也相同。這支持共用宣告驅動的核心，再搭配不同文字編碼與資源。

但 CN dump 標示 1.01，JAST 為 1.02；函式數分別 37,742／37,737，lambda 編號也不同：Join callback 是 CN36081／JAST36075，另一個 observer predicate 是 CN25697／JAST23866。**不能整表固定加減，也不能把硬編 fno 當通用解法。** JAST README 所列原始目錄目前不存在，本輪未對原始 JAST AIN 或 EXE 重新驗證；兩份 dump 相同的局部內容不證明兩款原引擎完全等價。

## 現有核心的新發現：先把介面契約整理好

本輪進一步核對現有 `ffi.c` 和 `Array.c`，確認三組可直接由來源碼看出的錯配：

| 重載 | 目前實作 | 結果／限制 |
|---|---|---|
| Numof #21 | predicate 版仍選一參數的 `Array_Numof` | callback 未執行，回傳依陣列大小／stride 計算 |
| Count #23 | predicate 版仍選一參數 `Array_Count` | callback 未使用，直接回 `nr_vars` |
| Find #46／#44 | 多個宣告選同一個 `(array,int value)` 實作 | predicate 的函式編號被當值比對；四參數版也有參數意義錯位，真實搜尋值未進入比較邏輯 |

細節、靜態呼叫位置數和行號見 [獨立綁定審查](原生研究-證據-2026-09-20/archive/binding-review.md)。**這是具體缺口，尚未證明是 9 月 9 日最新卡住的原因；本輪也沒有修改它們。**

現有系統其實仍以 libno/fno 保存 runtime table，並依 AIN 宣告建立各自的 libffi CIF；問題在於選 C function pointer 時，多數只按名稱取第一個實作。Erase／IsExist 已有簽名選擇特例，Numof 也已有元素 stride 分流，所以不能描述成整個系統完全不認型別。

下一個架構應由「版本 hash + library/index + normalized signature」選擇處理器，明確驗證參數與回傳形狀，再把 generic `arg3`、closure object 等放進每次呼叫的上下文。未支援的宣告應可辨識地回報，不以固定成功值充數。這可以先在現有引擎旁完成驗證，無須預先承諾重寫全部 VM。

## 路線比較與建議

| 路線 | 可保留的工作 | 新增負擔 | 目前建議 |
|---|---|---|---|
| 持續逐點 patch | 現有全部執行環境與工具 | 每次再發現一個型別／生命週期特例，較難建立完整契約 | 可用於驗證個別假設；不作唯一長期方法 |
| 全新完整引擎 | AIN 與遊戲資源、格式知識 | VM、服務、圖形／文字、音訊、影片、保存、所有流程重新整合 | 有技術可行性；目前沒有證據支持它能更快完成 |
| **保留 parser／服務，先做嚴格的 v14 bridge，再驗證新核心** | 既有 AFA／AIN／pactex、中文、部分繪圖與診斷 | 設計型別、借用／擁有引用、閉包、call frame、服務契約與測試 | **推薦；每一階段都有可比較的成功／停止條件** |
| 維持原 EXE + CrossOver | 已存在的原引擎行為 | 平台相容層與封裝維護 | 適合作為行為基準，也可供日常遊玩；「正常可玩」仍以使用者先前觀察為來源 |

新核心可以採不同內部物件表示與回收設計，不必逐欄複製 xsystem4；但必須維持 AIN 的可觀察結果，包括 reference 別名、析構副作用和保存後恢復。換語言或渲染 API 不會自動解決這些規格問題。

現有工具可讀寫 AIN、資源封包與部分保存格式，是縮小重寫範圍的基礎。[alice-tools 官方說明](https://github.com/nunuhara/alice-tools)

## 下一階段的最小實驗與決策門檻

**先驗證一條真實核心鏈，再決定是否擴大為獨立引擎。** 以下尚未實作，不能與本輪已完成的解碼探針混為一談。

| 驗證 | 成功條件 | 失敗時應做什麼 |
|---|---|---|
| 簽名 bridge | 同名的值版／predicate 版／區間版分開綁定；未知宣告明確報錯；nested callback 後上下文還原 | 回到原 AIN／EXE 比較，不加入按函式 ID 的特殊成功路徑 |
| 真實腳本片段 | 從原 AIN 解碼並執行 observer／Join／timer 鏈，時間與輸入可控；不硬編 End=true | 找出缺失的指令或服務契約，不強行跳過等待 |
| 生命週期 | callback 期間 caller／captured frame 存活；scope 結束 typed cleanup；timer dtor 恰一次；重複循環後活躍物件數回到基準 | 在這個小範圍查 ref／alias，不把永久保留 page 當修復 |
| 連接既有呈現 | 實際可見標題→New Game→首頁停等→單擊第二頁，可重複；原版與新核心同輸入時間軸 | 把繪圖、事件路由與 VM 時序分開追蹤 |
| 保存／復原 | 至少三個點，保存→推進→讀回→重啟載入，對話、等待及必要音訊狀態吻合 | 明確區分新格式與舊檔相容，不能只保存 globals |

第一個有價值的原型可以沒有完整 CG／音訊，但必須執行真實 AIN 指令與型別資料。這與寫一個模仿遊戲外觀的示範不同。通過後再整合成新的 macOS 執行器；若始終需要猜 slot 或硬編函式編號，便沒有證據顯示全新核心更可靠。

## 存檔與效能不能提前承諾

現有 libsys4 `rsave` 格式與 xsystem4 `resume.c` 包含 IP／函式 offset、stack、call frame、heap、序號及函式名稱。既有 xsystem4 dump 也確實有這些結構。這不是本輪讀取原 Windows玩家存檔的結果，但足以指出：替換 VM 後若要保存相容，工作遠超人物變數序列化。Native parts／音訊等狀態還需另驗。

9 月 9 日最新使用者試玩仍有 8.644 秒與 5.351 秒的 present 長間隔、沒有 MSG。當輪沒有停頓中的 CPU sample，本輪也沒有重現，故沒有新根因或 FPS 改善結論。原生效能應在正確行為成立後，以實際輸入延遲、長幀、CPU、RSS 與活躍物件變化衡量；present 次數不等於內容更新率。

## 歷史證據的更正

- Wine 基準共 141 張圖。舊索引把 `wb064–074` 寫成同一句等待 >20 秒，但 064 尚無對白；實看 066／070／074 才同一句，其 mtime 跨度 17.20 秒。只能作歷史視覺證據，不當新一輪精確計時或逐點擊對照。
- 114 張 legacy 截圖的來源有疑慮，不能用它們證明原生 fork 曾可完整遊玩。
- 七月「畫面成功」曾只憑 framebuffer；較晚 handoff 更正真正 SDL 視窗仍灰。以較晚查證為準，避免將歷史成功敘述累加成完成率。
- 舊工程的 fixtures 與視覺 diffs 目錄為空；本次九月工作區另有實際 fixture，兩者不可混稱。單純有資料夾或計畫不代表已有回歸測試。
