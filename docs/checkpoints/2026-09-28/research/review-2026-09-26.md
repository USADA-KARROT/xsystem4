## 2. 本輪發現

### 2.1 新遊戲 blocker 根因（已實證）

CN AIN 的 Array 庫對 `First` 有四個宣告：兩個單參數 `First(ref array self)`、兩個 predicate 版 `First(self, hll_func func)`。fork 的 C 端只有一個 `Array_First(struct page **array, int func)`，`ffi.c` 的 `link_static_library` 對 First 沒有像 Erase/IsExist/Numof/Count/Find 那樣依宣告分流。單參數版的 CIF 只傳一個參數，`func` 讀到 arm64 暫存器殘值；`Array_First` 對 func 越界或 predicate 全 false 時對 string 元素 push -1。

呼叫鏈：`CreatorHelper::Lottery`（f28943）先 `Shuffle(temp, -1)`（把 -1 留在 x1）再 `First#1(temp)` → 取到 -1 → `PushBack(result, -1)` → `InnerCreatePersonalities` 回傳 → `WorkerCreator@Create` 的 `Array.Concat` → `ArrayExtensions::Take<string>` → foreach 第 0 項 `X_REF 2 / X_REF 1 / A_REF` → `NEW Personality(-1)` → assert。

證據層級：

1. Workflow 靜態分析提出 H1（信心 0.85），兩位獨立反駁者（程式碼視角、bytecode 視角）都無法推翻，殘餘信心 0.8 與 0.6。
2. Headless probe（真實 ffi 路徑，非 bytecode）：`fixtures/first-overload-20260926/`。修正前 First#1 二十輪二十次回 -1，對照組 At(0) 每次正確；修正後二十輪全對。

### 2.3 同型系統性缺陷

Array 庫共 15 個名稱同名多 overload、C 端單一實作、無 ffi 分流。AIN 中合計 483 處呼叫：

| 名稱 | 呼叫數 | 走錯實作的形態 |
|---|---:|---|
| First | 153（#1=45、#3=108） | 單參數版讀到垃圾 func（本輪已修） |
| Last | 111（#1=104、#3=7） | predicate 版被綁到單參數 C 函式，predicate 被忽略 |
| Any | 83（#0=37、#1=46） | 同上 |
| LowerBound | 32（#1=30） | predicate 版 → 值比較版 |
| BinarySearch | 30（#1=30） | 同上 |
| Max | 16（#1=2、#3=14） | 單參數版讀到垃圾 func（與 First 同型） |
| Min | 13（#3=12） | predicate 被忽略 |
| Realloc | 13 | 三參數版綁到二參數 C |
| Unique | 12（#1=2） | predicate 被忽略 |
| Fill | 5 | 四參數版參數錯位 |
| Copy / FindLast / Equals / UniqueSorted | 4 / 4 / 3 / 4 | 參數錯位或 predicate 被忽略 |
| UpperBound | 0 | 未用 |

Last#1 有 104 處呼叫、Any predicate 版 46 處，都會在遊戲流程更深處出問題。正確做法是把本輪 `array_select_function` 推廣成通用的宣告驅動分流（依 `nr_arguments` 與是否含 `hll_func`），不是逐個名字加特例。
