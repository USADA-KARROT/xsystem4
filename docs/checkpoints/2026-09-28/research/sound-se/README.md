## 症狀

修前（`cdff563`；`7496f55` 的 `KiwiSoundEngine.c` 和它相同）：

1. **系統音效和腳本的一般通道共用同一個號碼池**。`PlaySe(ID, 名稱)` 直接準備 wav 池裡同號的通道。遊戲的系統音效在 SE 5、6、7（游標、點擊、取消在 5，結算等在 6，語音在 7），腳本的循環音效用一般 ID 3–8，所以 `PlaySe(7)` 會換掉一般 ID 7 正在播的循環，一般 ID 7 的 `Prepare` 也會換掉 SE 7 正在播的語音。實機錄到的是後一個方向（見〈實機錄音〉）。
2. **其他五個是同一個池的讀法或空殼**：`StopSe` 停掉、`IsPlaySe` 與 `IsExistSeID` 讀同號的 wav 通道；`GetFreeSeID` 不看範圍、回池裡最小的空號；`SetSeParam` 什麼都不做，所以遊戲設的 40 ms 同名抑制與「不可同時播」都沒有。
3. **連帶**：修前的 SE 6 佔著一般 ID 6，腳本的 BGM 音量上限管理淡的正是一般 ID 2、4、6、8，所以結算音效跟著 BGM 被壓低、又被腳本對一般 ID 6 的淡出與 `Stop` 切掉（錄音量到）；BGM 上限管理用 `IsPlaySe` 判斷系統音效播完沒，修前問到的是 wav 池的同號通道（見〈推論〉）。

### 腳本與主 EX 的量測【AIN】

- **呼叫點**：KiwiSoundEngine 的 SE 函式在 AIN 裡只有 5 個呼叫點：SetSeParam 2 個（`InitSystemSE`、`Music@InitSystemSound`），PlaySe、StopSe、IsPlaySe 各 1 個（`PlaySystemSE`、`StopSystemSE`、`IsPlaySystemSE`）。**GetFreeSeID 與 IsExistSeID 沒有呼叫者。**
- **參數**：主 EX 的系統音效設定表三列，(0, 40, 可同時播)、(1, 40, 可同時播)、(2, 40, 不可同時播)。`InitSystemSE`（FUNC 19233）逐列 `SetSeParam(5 + ID, …)`：SE 5、6 是 40 ms、可同時播，SE 7 是 40 ms、不可同時播。`Music@InitSystemSound`（FUNC 30232）把 SE 0–4 也設成同一組 40 ms、可同時播。
- **播放**：`PlaySystemSE`（FUNC 19234）先確認檔案存在、群組沒有靜音，再 `PlaySe(5 + type, 名稱, filter)`（回傳值丟掉），之後交給 BGM 音量上限管理。type 0（`SystemSound::Cursor`、`Click`、`Cancel`）→ SE 5，type 1 → SE 6，type 2（`PlayVoice`）→ SE 7；`VoiceRouter` 播下一句前先 `Stop` 同一個 type。`MusicRouter@Join` 用 `IsPlaySe` 的迴圈等 SE 6 播完。
- **一般通道**：腳本的循環音效用一般 ID (3, 4)、(5, 6)、(7, 8) 成對交叉淡入淡出（沿用 UI 盤點的追蹤，沒有重量）；修前和 SE ID 同一個池。
- **BGM 音量上限管理**（FUNC 19166–19168、19162）：`BeginBGMFadeBySystemSE` 把 `5 + seID` 放進清單；`IsPlayList` 拿清單裡的值經 `AFL_SystemSE_IsPlay` → `IsPlaySystemSE(id)` → `IsPlaySe(5 + id)`，所以實際問的是 `IsPlaySe(10 + seID)`：語音是 12（type 2）與 20–23（type 10–13）。
- **檔案**：timemap 裡游標、取消、點擊三個系統音效檔的群組都是 2；戰鬥語音是語音封裝的檔、群組 6–8。音效封存 1036 個名稱、語音封存 22428 個名稱，兩邊沒有同名，也沒有只差大小寫的名稱；腳本與 EX 裡叫得到檔案的字串常數，拼法都和封存相同（只數不印）。

### 推論【推】

- **原版的 40 ms 是播出的時間**：PlaySpan 比的是緩衝區的 GetPos；照 G1b 讀的靜態緩衝區（`0x6fc3f0`），那是「現在時間減本圈開始時間」。這一組沒有重讀。
- **重啟時表會變空**：原版推定在 `system.Reset` 時重建聲音引擎，表變空、聲音停掉；腳本重開後會再跑 `InitSystemSE`。
- **BGM 上限的「雙重 +5」**：這個遊戲沒有人在 SE 11、12、20–23 播東西，原版的表裡沒有這些項目，所以清單下一次更新就清空，BGM 在語音開始約 1 秒後就回升（等 1000 ms、淡 450 ms），不等語音播完。錄音（兩個建置）量到 BGM 在語音開始後約 0.92 秒（錄音時間）開始回升，和這個讀法一致。這是腳本自己的寫法，移植版不該「修」它。修前的移植版問到的是 wav 池 12 號（ADV 的語音通道），ADV 語音在播時 BGM 會一直壓著；G11 之後和原版的表一致。若原版其實有這些項目，原版的 BGM 會壓得比移植版久。
- **修前 `Stop(5)` 晚一步**：修前 SE 6 佔掉一般 ID 6，腳本對 (5, 6) 這一對看到的狀態不同（見〈例行路線〉的聲音呼叫順序）。
- **`MusicRouter@Join`**：修前若一般 ID 6 有循環音效，等 SE 6 的迴圈會等不到；G11 之後不會。沒有實測。

## 做法

- **SE 表**：放在 `src/audio.c`，和 wav、bgm 兩個池並排。項目有 ID、PlaySpan、bMultiPlay，以及「名稱 → 通道」的清單（依加入的順序，同名的第一個就是最早加入的那個，對應原版多重表的等值範圍）。通道是 SE 表自己的通道物件，**不進任何池**，所以一般函式在任何號碼上都碰不到它。資料結構是線性陣列，不是雜湊表（項目很少）【移】。
- **六個函式**照〈反組譯看到的〉：取得或建立項目與預設值、SetSeParam 只寫自己的項目、PlaySe 只走這個名稱的範圍（不在播的跳過，在播而且位置小於 PlaySpan 就整次擋掉），沒有 bMultiPlay 時重用第一個同名的，走訪之後收回這個項目裡不在播的通道（重用的除外）；StopSe 釋放通道、留項目與參數；IsPlaySe 只看自己的項目；兩者對沒有項目的 ID 回假、不建；GetFreeSeID 照 32 位元的算術；IsExistSeID 照原版的算術（除了 0 一律為真；腳本沒有呼叫，照抄不影響遊戲）。
- **綁定與閘門**：KiwiSoundEngine 的六個 SE 函式各有 v14 形狀的版本，只綁到 AIN 的確切宣告形狀；**只在 G1 的群組模式**（v14、GBK 字元規則、主 EX 有辨識得到的群組表）走 SE 表，否則呼叫原本的函式（共用 wav 池，IsExistSeID 也照舊讀 wav 通道）。v14 之前、SJIS、沒有群組表的遊戲不變（探針 SE9 守）。原本的六個函式一字未改，舊遊戲與不認得的形狀照舊用它們。
- **生命週期**：表只在主執行緒動（HLL 函式與 KiwiSoundEngine 的 `_ModuleFini`），音訊回呼不碰表；通道一律經 `channel_close` 釋放（先在裝置鎖內停下，再釋放）。`_ModuleFini`（結束與重啟都跑）在寫 Volume.sav 之後清空表、停掉它的聲音。合併後的 `audio_reset`（G4）只關匿名通道與兩個池，SE 表由 `_ModuleFini` 管。
- **群組與內部音量**：PlaySe 的通道 bStreaming 0、照 timemap 掛群組、沒有列就掛 2、乘所屬群組的鍵，和 G11 之前的 PlaySe 完全相同，所以系統音效的增益不變（探針 SE8 守，修前就通過）；`src/audio_mixer.c` 只把 `channel_gain` 註解裡「沒追」的那一句改成讀到的結果。

### 移植策略（不是原版行為）【移】

- **PlaySpan 用移植版自己的位置量**：位置是 refill 讀到的 frame 換成毫秒；原版讀緩衝區的 GetPos，推定是播出的時間。移植版的位置在清零的第一塊之後才開始、以一塊（1024 frame，約 23 ms）為單位，所以遊戲的 40 ms 要到呼叫後 46–70 ms 才放行。探針只在離界線一塊以上的地方測；用牆鐘量的實作在探針裡會失敗。
- **重用＝關掉再開**：沒有 bMultiPlay 而重用同名通道時，關掉舊的、在同一格開一個新的，所以從頭播之前有一塊清零的緩衝（約 23 ms）。原版 Stop → 重新準備 → Play 之間有沒有可聽的空隙沒追。
- **名稱沒有檔就不留通道**：原版留一個不在播的通道到下一次收回，任何函式都分辨不出；項目照原版建。
- **重啟清空表**：依〈推論〉的兩點。
- **filter 參數不用**；名稱先找音效封存、再找語音封存，和 G11 之前相同（原版 `0x4a4050` 的順序沒追；兩個封存沒有同名）。
- **同時播放的上限**：每個群組混音器最多 32 個聲部；聲部滿時那個通道不在播，PlaySe 仍回真（和一般的 Play 相同）。原版的上限沒追。

## 提交說明的讀法

`4159ce6` 的提交說明（和 `8a8e08e` 相同）在提交前另做了一次逐句查證（41 句，對補查、實作筆記、修正報告、審查結果與證據檔），沒有和量測相反的句子；查證時收窄的 5 處已寫進提交說明（見 [review.md](review.md)）。下面幾句的範圍以這裡為準。程式不 amend：改寫會換掉雜湊與執行檔裡的版本字串，提交後驗收的執行檔就對不上 commit。

- **一般 ID 5–7 的使用**（唯讀，從日誌量）：九條路線（另含 fightr 的 3 趟）一般 ID 5、6 從來沒有 Play；一般 ID 7 只播過數值循環（工作結果那一段約 88、98 秒各一次，haruuri、savedialog 與 fightr 都走到；fightr 戰鬥結束時一次、約 1 秒後下一次點擊就被腳本淡出；片頭路線一次）。路線沒有開函式追蹤，這些時段裡有沒有 `PlaySe(7)` 看不到。

### 實機錄音（提交前的建置）

- **做法**：SDL 的磁碟音訊驅動（float32、44.1 kHz、立體聲），錄的是混音器交給裝置的樣本，不是喇叭。haruuri 的排程，這一組的建置（實作完成時）與修前的建置（G1b 提交後，`src`／`include` 等於 `cdff563`）各錄一趟，兩趟都開函式追蹤；都是 exit 0、時間到、`XSYS4_NO_DESKTOP_WARP=1`、桌面游標不變。磁碟驅動約 0.92 倍速，所以每個聲音的位置都在錄音裡找，不用引擎時間換算。參考從遊戲工作副本的封存唯讀取出、照引擎的方式解碼（只放在私人工作區）。分析：每個聲音定一個起點（正規化互相關），之後每 50 ms 一窗，所有聲音一起做最小平方擬合（每個聲音另有一欄窗內斜坡，淡入淡出與 BGM 壓低變成增益變化，不變成殘差）；被切掉或重頭播的聲音，增益會掉到 0 附近。
- **呼叫序列**：兩趟追蹤到的 56 次呼叫（PlaySystemSE 46 次）的函式、type 與名稱（以雜湊比對）逐列相同。
- **工作結果畫面**：SE 6（結算音效，2.00 秒）與 SE 7（語音，1.75 秒）同時開始；0.95 秒後（錄音時間），腳本才在**一般 ID 7** Prepare 並播數值循環，這時語音還在播。這是**和簡報設想相反的方向**。
  - 這一組的建置：語音整段都在（數值循環開始後的 0.5 秒增益 0.6141–0.6521，之後 0.6400 播到結束）；數值循環從開始到腳本在下一次點擊把它淡出，每窗都是 0.6042；重疊的 0.5 秒裡殘差比電平低 55–79 dB。
  - 修前：數值循環一開始，語音就被切掉（之後增益約 0，少了約 0.8 秒）。
  - 數值循環在兩趟都不中斷，所以「循環不中斷」在這段錄音分不出修前修後；能分辨的是「語音沒被切」。量法分辨得出「被切」（修前語音那一窗）。
- **修前另外兩處錯**：結算音效（SE 6）修前佔一般 ID 6，跟著 BGM 被壓到 0.3625（＝0.6 × 0.6042）、再被腳本對一般 ID 6 的淡出切斷，這一組的建置不被壓、播到結束；金錢音效（SE 6）修前不到 0.25 秒就被腳本的 `Stop(6)` 切掉，這一組的建置在錄音 90.65–92.30 秒都在（前後兩小段擬合解釋不了）。
- **簡報設想的方向**（循環已在一般 ID 5–7 播、這時 PlaySe 同號）：兩趟錄音的 46 次 PlaySystemSE 進入時，一般 ID 3–8 都沒有通道在播；把淡出的尾段也算進去，有 8 次落在一般 ID 4 的淡出尾段，落在自己號碼上的仍是 0 次。所以這個方向**只由探針 SE1、SE6 的合成資料涵蓋**。實機唯一的候選是一般 ID 7 的數值循環（haruuri 的工作結果、fightr 的戰鬥結束，每次約 1 秒），要開函式追蹤並錄音才知道有沒有系統音效落進來；沒有做。
- **BGM**：兩趟都在語音開始後約 0.92 秒（錄音時間）開始回升（見〈推論〉的雙重 +5）。
- **峰值**：這一組的建置整趟最大振幅 0.802，修前 0.763，兩趟都沒有 |x| ≥ 0.999 的樣本；推定是開場連續 9 個 SE 6 的聲音在新的建置可以同時播。
- **錄音沒走到的**：type 0 的游標、點擊與取消（haruuri 的排程沒有）、PlaySpan 擋下第二聲、SE 7 同名重播（每句語音的名稱不同）。

## 沒做與沒驗證

- **引擎自己的聲音不走 SE 表**：原版元件的 CSound 以名稱經 SE 3（遊戲的參數是 40 ms、可同時播）、`0x5feac0` 以 SE 4（200 ms）從記憶體經這張表播；移植版這些聲音走 G4 的匿名通道，不經 SE 表，所以沒有 SE 3 的 40 ms 同名抑制（快速劃過相鄰的同名按鈕時，原版推定只響第一次）與 SE 4 的 200 ms。G11 推送後，可以把元件音效（`audio_play_sound` 這一個呼叫點）改走 SE 3；探針要另想觀察方式（`parts-sound-name` 的合成封存不給資料，看不到抑制）。
- **簡報設想的撞號方向實機沒有錄到**：只有探針 SE1、SE6 的合成資料（見〈實機錄音〉）。fightr 戰鬥結束那約 1 秒的數值循環期間有沒有系統音效，要開函式追蹤錄音才知道。
- **PlaySpan 的時窗**：遊戲的 40 ms 在移植版要 46–70 ms 才放行。快速連按游標時，移植版推定比原版多擋一些（例如間隔 50 ms 的第二下，原版響、移植版可能不響）；沒有實機聽。
- **SE 7 同名重播的空隙**（約 23 ms）沒有錄到。
- **探針不涵蓋**：PlaySpan 的界線附近、負的 PlaySpan、同一個 ID 兩次呼叫之間改 bMultiPlay、ID 在播時 SetSeParam、只差大小寫的名稱（原版是兩個名稱；移植版查封存不分大小寫，遊戲的封存與字串常數沒有兩種拼法）、已播完通道的釋放時機與累積、同時播放的上限（每個群組 32 個聲部）、腳本等 IsPlaySe 的 BGM 上限、filter 參數、負或極大的 SeID、GetFreeSeID 從 0 起。
- **第四次複核另列的五個存活突變**（P5、P10、P16、P15、Q5）：沒有收進突變表，也沒有列進探針檔頭的不涵蓋（見〈突變〉）。
- **fightr 的分群比例**：三趟分辨不出，沒有多跑（要十趟以上才有意義）。
- **推論**：原版的 40 ms 是播出時間、重啟時表變空、原版在 SE 11、12、20–23 沒有項目，都沒有原版實測。
- **原版沒有錄音**：沒有執行原版或 Wine。
- **其他遊戲與平台**：別的 v14 遊戲沒有實測；新行為只在群組模式生效，其他遊戲照舊（SE9 守）。Windows、Linux 沒有建置。
