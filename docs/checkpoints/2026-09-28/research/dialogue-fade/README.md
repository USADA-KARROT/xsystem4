# 對白逐字淡入與全畫面點擊

2026-10-11。程式 `0a4cfdb`（全畫面點擊改在放開時送）、`58eda8d`（逐字淡入），以及 `5cbaafa` 裡屬於這一組的部分（同值再設字型或字距）。基底 `f350109`；一起推送的五個 commit 的第一、二、五個，推送後的 HEAD 是 `5cbaafa`。另外兩個 commit 見[設定畫面](../config-widgets/README.md)。

這一步做了兩件事：訊息視窗的文字照原版逐字淡入；沒有點到可點擊元件的左鍵照原版在**放開**時才送全畫面點擊，引擎不再替腳本結束等待。**可點擊元件自己的點擊沒有改**，仍在按下時送（輸入模型是下一組）。已讀字色、文字裡字型標記的樣式與 ruby 也不在這一步。
> 2026-10-12 更新：可點擊元件自己的點擊已改成放開時才送，每次放開都先送全畫面點擊（`aa541a7`，只有左鍵），見 [input-model](../input-model/README.md)。

## 症狀

- v14 的對白在設定文字的那一幀整句出現；原版每個字依序淡入（先前[與實機的比對](../gui-visual/visual-compare.md)的 D11）。
- `FixMessageWindowText` 是空的、`IsFixedMessageWindowText` 恆為真、字速度的兩個函式是空殼：「按一下先把這一句顯示完」這個操作不存在。
- 做出淡入之後才看得到的：用滑鼠左鍵前進時，下一句清空一幀就整句全亮，沒有淡入。原版用滑鼠前進的下一句照樣淡入。
- 滑鼠是按下就前進；原版放開才前進。

## 根因

1. 訊息視窗沒有每個字的時間，也沒有「還在淡入」的狀態。
2. **輸入模型**：v14 的元件輸入在左鍵按下而沒有可點擊目標時，當下就送全畫面點擊，並由引擎把腳本的全域 `g_EndPartsBusyLoop` 設成 1。任何等待因此在按下的那一幀被引擎結束，腳本自己的放開判斷沒有機會跑；下一句開始時左鍵還按著，腳本的顯示迴圈第一圈看到有鍵按著就把它顯示完（診斷紀錄：按下後 23 ms 設新文字，再 10 ms 就 Fix）。當初這樣寫的理由是「`WaitForClick` 的按鍵檢查在按下時就離開」，與腳本不符：它的按鍵檢查要到放開才成立。

## 做法

- **`0a4cfdb`**（`src/parts/input.c`）：左鍵按下而沒有可點擊的目標（沒有目標、目標只擋游標、目標只有 pactex 的點擊許可而沒有事件）時，按下不送任何東西，只記一個旗標；放開的那一次更新才排入全畫面點擊（訊息 4、元件 0），座標是放開時的游標位置。引擎不再寫 `g_EndPartsBusyLoop`。v13 以前不變。
- **`58eda8d`**：逐字的時間表、腳本倍率、`Fix`／`IsFixed`、有變更的旗標、字速度與它的預設值 23，淡入完成在更新時設定（`src/parts/message_window.c`）；字的 alpha 乘上元件 alpha（`render.c`）；`UpdateComponent` 的第二個時間傳到訊息視窗，`SetEnableSpeedUp`／`IsEnableSpeedUp`（`parts.c`、`src/hll/PartsEngine.c`）；六個函式只在 AIN 的宣告與原版相同時取代空殼，形狀不同或 v13 以前保留原來的綁定（`pe_v14_message.c`）；pactex 的 `字速度`、`スピードアップ有効`（`pe_v14_activity.c`）。NEXT 圖示的動畫用同一個時間。
- **`5cbaafa`**：`SetMessageWindowTextFont`、`SetMessageWindowTextSpace` 在每個值都和現有的相同時直接返回。以前每次都重排；有了逐字淡入之後，重排會把已經 Fix 的文字退回淡入途中。另補一處註解（原版的存檔帶 speed-up 旗標與字速度）。

第一版沒有動輸入的時機，只把「被當成全畫面點擊用掉的那次按下」對腳本讀成放開。審查指出它讓「點一下解除自動模式」失效（實機重現：按下就前進一句、自動模式不解除），所以整個拿掉，改成上面的做法；`src/input.c` 與 `include/input.h` 回到與基底相同。

刻意和原版不同的地方：

1. **可點擊元件自己的點擊仍在按下時送，也不另送全畫面點擊**（原版在放開時送，全畫面點擊每次放開都送而且排在前面）。把它移到放開會動到每個畫面的點擊時機與一批既有探針，留給輸入模型那一組。
   > 2026-10-12 更新：已照原版改（`aa541a7`）：元件自己的點擊在放開時送，全畫面點擊每次放開都送而且排在前面。見 [input-model](../input-model/README.md)。
2. **只有在輸入作用域內看到的按下才算**；原版對進入作用域時已經按著的鍵，放開時也送。因為第 1 點：按鈕開出來的新場景會收到「同一次點擊的放開」，照原版的規則就多一次全畫面點擊（按按鈕進到一個點背景就前進的畫面，一放開就被前進）。
   > 2026-10-12 更新：已照原版改（`aa541a7`）：進入作用域時已經按著的鍵，放開時也送全畫面點擊。按鈕的點擊移到放開之後，它開出來的新場景開始時鍵已經放開，上面擔心的多一次點擊不會發生。見 [input-model](../input-model/README.md)。
3. 小項：對「存在但不是訊息視窗」的元件，原版把內容換成視窗物件，這裡是並存；訊息編號的初值是 0（原版 −1）；原版的 Fix 每次都重建並回呼腳本取倍率，這裡只重建有變的部分；speed-up 旗標只有訊息視窗讀（原版每個元件都依它選時間）。

## `noskip` 路線

這條路線不按住鍵、每 1.2 秒點一下。行數：基底 261；只加輸入的修改 259；`58eda8d` 221（提交前同一份原始碼的另一次是 224）；接上設定畫面之後的一次 226；`5cbaafa` 221。每一次都是基底那 261 行的前段，逐行相同。**比對這條路線只能比前段是否相同，不能比行數與雜湊。**

變少的原因：點擊落在句子顯示完之前時，那一下只把句子顯示完（原版也是），要再一下才前進；前進又改在放開時，離下一次按下只剩約 1.1 秒。實作時的一次紀錄（224 行）裡，夜晚劇情那一段有 20 次這樣的點擊：淡入本身比間隔長的只有 2 次（三行的長句，1350 與 1189 ms）；其餘 18 次是一到兩行的句子，會被打到是因為文字開始之前還有一段前置演出（換頭像、立繪、事件圖），由「間隔 − 淡入長度」推出的前置時間下限是 53–622 ms、中位數 336 ms。**前置演出有沒有比原版長，沒有對照**：原版只量過開場主視窗的三句（260、288、至少 470 ms），而推出的下限裡有 6 次超過 470 ms，不能排除移植版偏長。

固定種子也不保證戰鬥路線每次相同：`fightr` 第一回合誰先行動有兩種結果，修改前後的二進位都出現過，所以它的截圖不能逐張比，比的是對白與有沒有打完。是哪裡依幀數取亂數沒有查。

## 與原版的對照（60 fps 錄影）

兩邊都以 60 fps 無損的螢幕錄影量：以文字清空的那一幀當背景、淡入完成後的一幀當終值，對每個字格算 alpha 隨時間的變化。原版是 Wine 上的專用副本；移植版是審查修正後、提交前的建置（與 `58eda8d` 的原始碼相同），以引擎內的定時左鍵點擊前進，每次按住 100 ms。之後的三個 commit 沒有重量。訊息速度是預設，事件視窗的句子：

| 項目 | 原版 | 移植版 |
| --- | --- | --- |
| 滑鼠左鍵前進後的下一句 | 逐字淡入 | 逐字淡入（只做淡入、不改輸入時：清空 1 幀就全亮） |
| 什麼時候前進 | 放開時 | 放開時；放開到畫面清空在 1 幀內 |
| 清空到首字可見 | 下一幀（+17 ms） | +16、+16、+33 ms（三句） |
| 每字間隔（同一幀相鄰兩字的 alpha 差） | 22.94–23.03 ms | 23.1–23.2 ms |
| 單一字由 0 到全亮 | 197–201 ms | 201–202 ms（第一版量的，之後沒有重量） |
| 整句到全亮（44／34／43 格） | 1200／984／1184 ms | 1250／1000／1217 ms |
| 全亮到 NEXT 出現 | 2 幀（有重複幀時 3） | 1–2 幀 |
| 淡入途中點一下 | 1–2 幀後全亮，下一幀 NEXT，停住；再按一次才前進 | 按下的那一幀全亮、下一幀 NEXT，之後 3.6 秒沒有變化，下一次點擊才前進 |
| 主視窗換說話者，清空到文字開始 | 260 ms | 278 ms（同一句；第一版量的） |
| 按住 Control | 每句直接全亮、沒有 NEXT、每句 1–4 幀，1.5 秒約 14 句 | 約 1 秒走完開場 88 行，中間的畫面幾乎不呈現，沒辦法逐句並排 |

- 每字間隔那一列的差不能當成移植版較慢的證據：兩邊的間隔都是整數 23、斜率都是 0.005／ms，這個量法照理不受時鐘影響卻有同向 0.6–1.0% 的差，是量測法在兩種字型上的偏差。整句的差（+50、+16、+33 ms）在一到三幀的取樣量化之內，沒有再追。
- 「淡入途中點一下」只比定性的結果，不比幀數：兩邊「按下」的時刻定義不同。
- 按住 Control 的差別靜態上與這一組無關（快進時每句第一圈就跳出、不等待），但修改前的速度沒有量過。
- 沒有量的：訊息速度最快與最慢（原版只量了設定頁的樣本文字，兩端在移植版只有探針用真腳本得到的倍率 4 與 0）；用 Enter 前進的移植版；主視窗的句子在審查後的版本。

## 獨立審查

- **第一次**（提交前，三個面向，中等級以上另有對抗驗證）：沒有 High。成立的 Medium 四件，都在提交前處理：補償讓點擊解除自動模式失效（改成上面的做法）；淡入完成在原版是更新時設定，第一版綁在繪製，註解與探針還把相反的行為寫成原版；`SetEnableSpeedUp`／`IsEnableSpeedUp` 對不存在的元件與原版相反；`noskip` 變少的歸因與紀錄不符（更正成上一節的說法，原版對照沒有做）。降為 Low 而一併處理的三件：補償的兩個實作問題（隨補償消失）、四個訊息視窗函式不建立元件。其餘 Low：量測數字與歸因的更正、修前失敗裡取不到函式的案例分開計、探針補 pactex 的鍵與第二個時間。
- **第二次**（提交後、推送前；這一組佔兩個面向）：沒有 High、沒有 Medium，Low 五條。同值再設字型或字距的那一條在 `5cbaafa` 修掉；存檔那一條只補了註解；輸入的三條留著，見下一節。審查全程唯讀，實機追蹤與探針結果只對照了原始碼，沒有重跑。

## 與原版的差異與限制

- **用滑鼠點 AUTO 按鈕進不了自動模式**（鍵盤 A 可以）：按鈕在按下時就收到點擊，自動模式打開並前進一句；下一句的等待開始時左鍵還按著，腳本當成「已經按著的那一次」把自動模式解除（實機：按下後 83 ms）。修改前就有：實機的對照組是第一版，對 `f350109` 是審查從程式靜態確認的。
  > 2026-10-12 更新：已修（`aa541a7`）：按鈕在放開時才收到點擊，用滑鼠點 AUTO 之後自動模式維持，和原版的錄影對過。見 [input-model](../input-model/README.md)。
- **按按鈕之後緊接的第一句不淡入**：同一個原因，左鍵還按著。
  > 2026-10-12 更新：已修（`aa541a7`），同一個原因；按鈕之後的第一句逐字淡入。見 [input-model](../input-model/README.md)。
- **按住背景期間輸入作用域結束或重開，放開時不送全畫面點擊**（例如自動模式或語音剛好讓等待結束）。這是 `0a4cfdb` 新增的缺口：以前按下就送，原版在放開時只要還有作用域啟用就送。後果是那一下對場景無效、要再點一次。靜態推演，沒有實機。
  > 2026-10-12 更新：已補上（`aa541a7`）：開始與回到外層時取樣左鍵，放開時只要還在輸入作用域內就送全畫面點擊，不管按下是在哪個作用域看到的。只有探針，沒有實機專測。見 [input-model](../input-model/README.md)。
- **`system.Peek` 也跑一次輸入更新**，放開幾乎都由它看到，所以全畫面點擊的處理比腳本自己的按鍵判斷早一圈；原版只在元件更新裡跑，順序相反。沒有找到結果會因此不同的畫面。
  > 2026-10-12 更新：已改（`aa541a7`）：v14 的 `system.Peek`／`PeekAll` 不再跑輸入更新。它和元件的點擊移到放開是一起的：放開若由 `system.Peek` 看到，按鈕的點擊會比腳本自己的按鍵判斷早一圈分派（實作前的推演：AUTO 先打開，回呼才看到放開，又把它解除）。見 [input-model](../input-model/README.md)。
- **右鍵與中鍵的全畫面點擊完全不送**（原版送鍵碼 2、4；場景與戰鬥都訂閱右鍵）。既有的缺口。
  > 2026-10-12 更新：仍未做。輸入模型那一組的第一版做過，審查查出兩處與原版不符而整塊拿掉；原版的右鍵與中鍵怎麼運作見 [input-model](../input-model/README.md)。
