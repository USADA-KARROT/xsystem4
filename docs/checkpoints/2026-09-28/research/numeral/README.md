# 數字元件與新物件的 option 成員（戰鬥的傷害數字）

2026-10-09。程式 `9fff3a1`（數字元件）、`4df72e1`（option 成員）、`fe9c40f`（審查後的修正）。

## 症狀（和 Wine 上的原版並排比過）

- 戰鬥中技能命中時，原版在被打的角色旁邊跳出斜 30° 的傷害數字；這裡完全沒有。
- 被攻擊的角色頭頂的量表在每一擊之後變成半透明，原版不透明。

## 根因

1. **數字元件沒有做完**。腳本的 `DamageNumber` 建一個以字型畫數字的 numeral 元件；`PartsEngine.SetNumeralFont` 沒有實作、`SetNumeralShowType` 是空殼，元件沒有貼圖。
2. **新物件的 option 成員不是 none**。`alloc_struct` 把 option 成員留在「有值、值為 -1」，原版寫的是 none。`DamageFrameMotionController.m_deadFrame` 因此讀成有值，每一擊第一次更新就觸發死亡事件，`PlayerViewPartsLayer@HideInterface` 把目標的量表與傷害數字一起淡出。

## 原版依據（靜態反組譯）

| 項目 | 位址 | 內容 |
| --- | --- | --- |
| 數字元件 | 物件 `0x5b3e80`、重建 `0x5b4df0`、字元 `0x5b5230`、排版 `0x5b4380` | CG 數字與字型數字兩種型態；位數、補零、逗號、全形、字距、顏色 |
| 函式庫 | `0x599270`–`0x5999a0`（22 個）；找不到元件就返回（`0x599540`） | Numeral 的 setter 與 getter |
| pactex | `0x5b66f0` | 載入器讀數字元件的屬性 |
| 新物件的成員 | `0x679db0` → `0x656b10` → `0x656970` → `0x656a44` | option 成員：值的槽寫 -1，最後一槽寫判別值 1（none）；建構子不寫就保持 none |

## 修正

- `9fff3a1`：照原版把數字元件整組做完（新檔 `src/hll/pe_v14_numeral.h`，`parts.c`、`PartsEngine.c`、`pe_v14_activity.c`）。
- `4df72e1`：v14 的 `alloc_struct` 把 option 成員初始化成 none（兩槽是 (-1, 1)，三槽是 (-1, -1, 1)）。
- `fe9c40f`（審查後）：讀檔之後，沒有 CG 字型的數字保留存檔裡的尺寸，不再被重建成 0；連結 CG 載入失敗時不再解參考空指標，字型編號有上界；setter 對不存在的元件不再建立元件；字型警告每種只印一次。

## option 成員的影響面

本 AIN 有 208 個 option 成員（171 個兩槽、37 個三槽），其中 189 個靠配置時的預設值。參照型的 option 在腳本的讀法裡另有「值不是 -1」的檢查，修改前後相同；改變的是**值型的 option 與只看判別的讀法**，都是變成原版的行為：

- `DamageFrameMotionController.m_deadFrame`（這一組的症狀）。
- `ShopDisplayUnit@PriceRatio::get`：沒有設折扣時原本算成 1.01 倍，現在是 1.0。
- `FeelEventResult@Apply`：沒有設的欄位原本各加 -1，現在不動。
- `WorkerCollection@Limit::get`：原本是 -1（所以 `Full::get` 恆真），現在是沒有上限。
- `WorkerCreator@GetRarity`：`Rarity` 沒設時原本回 -1，現在走預設的稀有度計算。
- 其餘見 [harness 說明](../../harness/README.md) 的 `option-member` 條目。

修改前的建置寫出的存檔裡，這些成員仍是「有值 -1」，讀回後不會被修正。

## 驗證

- 新模式 `numeral`（10 案）與 `option-member`（5 案；掃全部 208 個 option 成員，並以真位元組碼的 `Limit::get`、`PriceRatio::get`、`FeelEventResult@Apply` 釘住數值）。
- 正式 before-check（[before／after](before-after.txt)）：`95e2da0` 上 `numeral` 9 案中 8 案失敗；`9fff3a1` 上 `option-member` 4 案全失敗；`4df72e1` 上 `numeral` 新增的讀檔案例與一項 setter 檢查失敗（其中空指標與越界由 sanitizer 報出；`option-member` 新增的案例釘的是 `4df72e1` 已有的行為，在那裡就通過）；修正後全過；兩種字元規則結果相同，還原後乾淨。
- 反向檢查：數字元件 39 處裡 38 處有案例失敗（另 1 處是等價寫法）；審查後的修正每一處還原都有案例失敗（其中兩處由 sanitizer 報出）。
- 預設與 GBK 各 84 模式 VERDICT PASS、sanitizer 0（[預設](verify-default.txt)、[GBK](verify-gbk.txt)）；既有斷言只有 `text-size` 的一個數字元件補了字色的鍵（載入器把缺的鍵當 0）。
- GUI（[摘要](gui-summary.json)，`RUN_RANDOM_SEED=20261008`）：十條路線沒有斷言、下溢或 VM 錯誤；對白的行數與雜湊和前一組相同。

## 實機上的改變（與原版並排）

- **每一擊都有傷害數字**：位置、斜 30°、大小、白字黑邊、彈出後上移淡出與原版相符（數值不同是亂數）。
- 被打者的量表不透明；量表上的狀態圖示出現。
- 據點的金額、春銷的計數與結算、地城狀態卡的數字與修改前相同。

## 獨立審查

一輪兩個面向，中等級的發現另有對抗驗證。

- 沒有 High。原版的預設值、none 的形狀、參照計數、數字元件的語義核對無誤。
- 成立的 Medium 兩件：讀檔後字型數字的尺寸被重建成 0（已在 `fe9c40f` 修掉）；筆記把「春銷結算換了一張 CG」歸因於這一組，沒有根據（已更正，見下）。
- 「實機佐證不是在最終的建置上取得」這一條被對抗驗證推翻（二進位雜湊不同只是重編）。

## 與原版的差異與限制

- **傷害數字的字形不同**：字型類型 257 在原版是外部字型，被系統換成粗的無襯線體；這裡落到預設的哥德體。
- **存檔沒有存數字的型態、字型、CG 名、補零、全形**：讀檔後字型數字不會重畫（這次只保住尺寸與排版），腳本重設字型後才會出現。要補得升存檔版本。讀檔沒有實機驗證。
- **固定種子不保證亂數的順序**：腳本有靠實際時間觸發的亂數消耗，同一個種子的兩次執行，春銷結算的 CG、戰鬥開場的行動角色可能不同。對白的行數與雜湊是穩定的比對基準。
- 戰鬥結果畫面的感情值是 600、800、400、0，原版是加完之後的 640、840、440、0；地城的狀態卡在原版是斜的平行四邊形，這裡是直的。都是既有的差異，沒有查。
- 商店、感情事件結果、隨機人材的稀有度這些因 option 成員而改變的路徑，自動路線走不到，沒有實機驗證。
- 區域變數的 option 初值與 `alloc_struct` 仍不一致（這次沒有動，原版也沒有查）；巢狀的 option 在本 AIN 沒有實例。
- 真的 CG 數字（型態 0、1）在路線上沒有出現，只測了探針自建的 CG 字型。
