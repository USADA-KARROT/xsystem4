# 全域 struct 的啟動順序（戰鬥場景位置、顏色常數）

2026-10-08。程式 `5846210`。

## 症狀

第一場戰鬥裡，我方四人擠在畫面上緣之外，敵人被切在畫面最底，戰鬥中還留著地城的標題列；角色頭頂的量表是黑的。

## 根因

v14 的啟動流程讓啟動函式 `"0"` 裡的 `NEW x, -1` 只配置、不建構，等 `"0"` 跑完再對每個 struct 型的全域呼叫一次無參建構子。這第二趟同時重設了 `"0"` 已經以帶引數的建構子建好的 30 個全域，以及 3 個由函式回傳值填入的全域：

- `BattleBackground::Size`、`CameraCenter`、`ScreenCenter` 變成 (0, 0)，戰鬥場景的平移少了常數項。
- 18 個 `CASColor` 常數全部變成 (0, 0, 0, 255)，連 `WHITE` 也是黑的。
- `DamageNumber` 的字型與兩個 `MotionSet`（由 `CreateFont`、`GetCompiled` 回傳）被重設。

## 原版依據（靜態反組譯）

| 項目 | 位址 | 內容 |
| --- | --- | --- |
| `NEW`，運算元為負 | `0x66bb90` → `0x679b30(type, 1)` → `0x669cb0` | 配置後當場跑 struct 的建構子；沒有建構子才逐成員給預設值 |
| `NEW`，運算元非負 | `0x679db0`、`0x66a0e0` | 配置後只跑運算元指定的那個建構子 |
| 啟動 | `0x666e00` | `0x667820` 建全域頁並給預設值（struct 全域是 -1，不配置）→ `0x667af0` 以名稱 `"0()"` 找到啟動函式並同步執行 → `0x6678d0` 只設 main 的指令指標 |

`"0"` 返回之後，原版沒有任何走訪全域或呼叫建構子的程式。C++ 端呼叫腳本建構子的入口以呼叫掃描窮舉過（`NEW`、解構 `0x6813c0`、delegate 呼叫 `0x65aca0`、`CALLMETHOD` `0x66d36c`、`DG_CALL` `0x66e1ea`），審查者獨立重做的結果相同。

## 修正

- `src/vm.c`：`NEW x, -1` 在啟動期間也當場建構；啟動函式之後的兩趟建構子拿掉；全域初始化抽成 `vm_init_globals()`。
- `src/page.c`、`include/vm/page.h`：刪掉 `init_global_struct_v14`。
- v13 以前不變。

啟動函式初始化 181 個全域：46 個 `NEW x, -1`、30 個帶建構子的 `NEW`、3 個函式回傳、其餘是 delegate、陣列與數值。逐一檢查過建構子之間的依賴：沒有任何建構子讀到排在它後面的 struct 全域。

## 驗證

- 新模式 `global-init` 9 案（[harness 說明](../../harness/README.md)）：真的啟動流程之後，帶建構子的全域保有腳本給的值；每個建構子只進入一次而且在 `"0"` 之內；巢狀成員都建好；函式回傳填入的字型與動作表沒有被重設；v13 與沒有建構子的 struct 兩個守衛。
- 正式 before-check：修前 `634e6d7` 9 案中 7 案失敗（GI1–GI6 與 G3），修後 `5846210` 全過；兩種字元規則結果相同，還原後 src／include 乾淨（[before／after](before-after.txt)）。
- 反向檢查三處（啟動期間只配置、加回第二趟、帶建構子的 `NEW` 之後多跑一次無參建構子），每一處都有案例失敗。
- 預設與 GBK 各 74 模式 VERDICT PASS、sanitizer 0（[預設](verify-default.txt)、[GBK](verify-gbk.txt)）；既有模式的輸出相同，沒有動既有斷言。
- GUI（[摘要](gui-summary.json)）：八條路線沒有斷言、下溢或 VM 錯誤；七條既有路線的對白與點擊目標和前一組相同。

## 與原版仍不同的地方（戰鬥）

- **頭頂的量表**：灰色斜框的位置對，但粉紅與綠的填色條沒有跟著斜，水平擠在畫面最上緣；敵人量表旁的斜名稱沒有。
- 行動中角色的高亮偏橘，原版是黃色。
- 技能演出時，原版其餘角色變成粉紅剪影，這裡是半透明的原色。
- 行動順序不同（原版 第 2 位 → 第 4 位 → 第 1 位，這裡第二個是第 1 位）。
- 18 個顏色常數修好之後，在這八條路線上看不出顏色的變化；它們的讀取者在傷害數字、地城地圖、商店按鈕與轉場。

## 獨立審查

一輪兩個面向（原版語義與建構順序、程式與探針），中等級的發現另有對抗驗證。

- 沒有 High。原版 `NEW` 與啟動順序複核一致；沒有 struct 全域漏建；v13、重新啟動與映像恢復的路徑不變。
- 成立的 Medium 一件：探針說明裡「修正前哪幾案失敗」的句子沒有對應的實測（真正的舊樹沒有跑過）。已改成指向本頁的 before／after，實際結果是上面的 7 案。
- Low 已處理：兩處程式註解；探針檔頭的說明；GI5 加上「沒有巢狀成員留在 -1」的斷言；`verify-step.sh` 的 `diff_sha` 改成對 HEAD 比較，暫存的修改才會顯示在摘要裡。

## 限制

- 帶建構子的 struct 成員的護欄、沒有建構子的 struct 的預設初始化，與原版仍有差異（既有，這次沒有動）。
- 戰鬥路線的峰值記憶體是 1351MB（前一組較短的路線 968MB）；路線變長而且第一次打完戰鬥，沒有分辨是正常載入還是累積。
- 探針在舊樹上以該版自己的函式重現舊流程，不含舊樹的兩道修補步驟。
