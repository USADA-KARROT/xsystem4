## 問題與量測（修前）

【量測】快照樣本裡，一格、值 -1、參照數 1 的 wrap 頁（以下稱盒子）99.96% 以上沒有任何持有者。從全域頁、呼叫框與 VM 堆疊出發做保守的可達性分析（任何值等於活槽號都算一條邊）仍到不了的：第 15 天的讀存檔路線進戰鬥時 75,398 個（活槽共 85,032），新開局第二場進場時 1,051,599 個（共 1,060,750）。同一趟裡較早快照的這種盒子，在較晚的快照裡全部還在，被釋放的是 0 個。研究者與查核者各自寫解析器，數字逐位相同。

【量測】累積照遊玩時間，不只照場次：地城地圖上完全沒有輸入時每秒約 1,090 個；第 15 天的讀存檔路線約每秒 1,190 個；戰鬥中更快（四場的數據像「每場固定約 9 萬、另加每秒約 3,400」，只有四個點）。讀玩家存檔或回標題會讓 VM 重啟，活槽清回起點；但堆積陣列不縮，同一種畫面下記憶體仍多約 150 MB。

【量測】變慢的是寫引擎快照的那一下停頓。腳本在地圖每走一格、進戰鬥與戰鬥結束時把整個堆積寫成快照；含快照的 5 秒窗裡最長的一幀，每多 10 萬個活槽約多 18 ms（21 個點，殘差 2–3 ms；拿掉最大點或只看 100 萬以下，結果相同），8.6 萬活槽時約 0.05 秒、137.5 萬時約 0.38 秒。同樣很重但不寫快照的切換（戰鬥結束到結算畫面）在 36 萬到 105 萬活槽之間持平在 152–183 ms。查核者從原始紀錄獨立重算，結果相同。

【量測】戰鬥中的幀率沒有趨勢：9 場（含一場 13 分鐘）平均 58.6–58.9 fps。限制：引擎有約 17 ms 的限速，每幀實際的工作量看不到；高活槽數的戰鬥只有兩場。使用者回報的「越打越多場、越來越慢」，目前量到的就是切換時的停頓；戰鬥中每一格畫面有沒有變慢，量到的範圍內沒有。

【推論】外推（超出量到範圍 8–12 倍；數量級可信、秒數不準）：不讀檔連玩一小時，每次切換約卡 2 秒。據點、城市地圖與劇情畫面的漏速沒有量；量測各趟都在螢幕鎖定下跑。

## 機制【讀程式】【讀位元組碼】

移植版建區域頁時（`_function_call`、`alloc_scenario_page`）對每個區域變數呼叫 `variable_initval`；wrap 型得到一個新配的、一格、index −1、內容 −1 的 struct 頁，就是上面說的盒子。v14 的位元組碼對宣告時就給值的 wrap 變數與 foreach 的元素變數，第一次寫入是前面沒有 `DELETE` 的 `X_ASSIGN`；v14 的 `X_ASSIGN` 不加減參照、不釋放被蓋掉的值，盒子就留著一個參照、沒有東西指向它。每呼叫一次，每個這種變數留下一個。同一種機制先前只對值型 option 修過（`ff77c18`：函式進入時給 -1）。

## 原版依據【反組譯】

| 位置 | 讀到的語義 |
|---|---|
| `0x679970` | 建區域頁（呼叫點 6 個，原版所有區域頁都經同一個初值函式）：把函式描述存進頁，以函式的變數表呼叫 `0x656b10`；引數之後才複製進前面幾格。 |
| `0x656b10` | 逐變數寫初值：字串、struct、delegate、陣列（型別碼 12、13、63、79）直接寫 -1；其他型別交給 `0x656970`。 |
| `0x656970` 的 `0x6569b8` 分支 | wrap（型別碼 82）與各種 ref、iface：第一格寫 -1，其餘格（槽數由 `0x653420` 算）寫 0；這個分支沒有任何配置呼叫。 |
| `0x656a44` | option：除最後一格外寫 -1，最後一格（旗標）寫 `0x653610()` + 1，表示沒有值。 |
| `0x66f080`（`X_ASSIGN`） | 把值原樣寫進格子，不看型別、不加減參照。 |
| `DELETE` 與返回 | `DELETE` 遇到 -1 什麼都不做；函式返回時區域頁的清除（`0x6570f0` → `0x656cf0` → `0x656c10`）依宣告型別放掉格子裡當時的值。 |

所以沒賦值的 wrap 型區域變數在原版就是 -1，沒有物件；「宣告時給值、前面沒有 `DELETE`」的第一次寫入，在原版沒有舊值要放。這是直接讀到的，不是類推；查核者與實作後的語義審查各自把關鍵位址重新反組譯、跳表重新解碼。struct 成員裡的 wrap 在原版也是 -1（陣列元素只看了呼叫者清單，把握中等）；本組不改這兩處。

## 位元組碼的分類【讀位元組碼】

| 類 | 個數 | 第一次碰到 | 會不會漏 |
|---|---|---|---|
| 回傳值暫存（沒有名字） | 12,158 | 12,154 個先 `DELETE`；1 個先 `X_REF` 取值再 `DELETE`；3 個從沒用到 | 不漏；修後少一次配置與一次釋放 |
| 有名字、宣告時給值 | 1,880 | 前面沒有 `DELETE` 的 `X_ASSIGN` | 漏 |
| foreach 的元素變數 | 1,248 | 同上 | 漏 |
| 合計（不是引數的 wrap 型區域變數） | 15,286（分布在 6,631 個函式） | | |

- 迴圈的每條回頭路徑都先刪除並設成 -1，所以第二圈之後蓋掉的是 -1；只有函式進入時的初值會漏。
- 沒有 wrap 型區域變數在第一次寫入之前被讀：三種靜態查法都是 0，含 137 個 lambda 讀父框 wrap 變數的 142 處（兩位各自查過，父框都在 lambda 建立前寫入）。不是完整的資料流分析。
- 建區域頁的地方只有兩處（一般函式呼叫、劇本頁：`CALLONJUMP` 依名字預先建的劇本函式區域頁）；快照讀回照檔案還原、不經初值。本作位元組碼沒有 `CALLONJUMP`，劇本頁那一處本作走不到。

## 修改【策略】

- `src/vm.c` 新增 `local_initval()`（+25／−8，只動這一個程式檔）：值型 option → -1（`ff77c18` 原有的條件，搬進來、不變）；v14 且型別是 wrap → -1；其他照舊 `variable_initval`。`_function_call`（引數之後的區域變數）與 `alloc_scenario_page` 的初值迴圈改用它。註解寫了原版依據。
- 兩格的 wrap（例如對 ref 的 wrap 佔頁與索引兩格）：第二格在 AIN 裡是它自己的 void 變數，照舊得 0，結果是 [-1, 0]，和原版相同。
- 不變：v14 之前；全域（只初始化一次，不是洩漏來源）、struct 成員與陣列元素的初值；`variable_initval` 本身；`X_ASSIGN`、`DELETE`；HLL 包裝對盒子的處理；部件引擎與快照讀回。複製 wrap 值與讀入映像也會做出同形狀的盒子，那兩條路不變。
- 不採「寫入時認出沒用過的初值盒子就放掉」：`DELETE` 不清格子、槽號會被重用，有誤放別人物件的風險，而且離原版遠。
- 只做 wrap：字串、陣列、非值型 option 的同型漏法另開第二階段（見〈仍有差異與未涵蓋項目〉）。

## 連帶的行為改變【讀程式】

1. 之後所有配置的堆積槽號與配置序號改變（有大有小，不是一律變小）；堆積成長與回收的時機、VM 映像的大小跟著變。
2. 回傳值暫存每次呼叫少一次配置與一次釋放。
3. 第一次寫入前就讀 wrap 型區域變數的話，會讀到 -1 而不是盒子（給 `X_REF`、方法呼叫的自動配置、把它當引數的 HLL 呼叫）；靜態沒有找到這種讀取。
4. 開了除錯器的建置裡，沒賦值的 wrap 型區域變數顯示 -1。
5. 舊版本寫的 VM 映像裡已經存著的盒子照原樣讀回，那個框的第一次寫入會把它再漏一次（每個框最多一次）；映像裡本來就沒有持有者的盒子，也連同參照數照原樣讀回、仍然沒有持有者（兩者都是讀程式，沒有跑）。

## 既有探針的預期值為什麼改、依據的先後

- **四條把這些盒子寫進預期值**：`array-literal` 的一案（11 個）、`arg-ownership` 第二次呼叫那一案（25 個）與兩百輪那一案（398 個）、`working-cards` 的一案（1 個；舊註解說它是匿名暫存，其實是有名字的 foreach 元素變數）。新預期是 0（或回到基準）；`array-literal` 那一案的其他 3 個 slot 不是盒子、不變。
- **第五條** `delegate-args` 的一案檢查回傳值暫存進入時的值。原本預期是一個新盒子（那個盒子不是洩漏的頁：暫存寫入前會被 `DELETE`），改成 -1、它後面的伴隨格 0；它原本要防的「引數複製蓋到這一格」仍守得住，-1 不是 delegate 頁的槽號。
- **依據**：只放在匯出副本的來源追蹤（不在工作樹、不提交）在沒改的程式上記下每個 wrap 型區域變數拿到的盒子，再把四條數到的盒子逐一歸到來源：100% 來自新區域頁替 wrap 型區域變數配的盒子，所以新值＝舊值減去這些盒子。被點名的 23 個（函式, 變數）逐一用位元組碼核對，都是宣告時給值或 foreach 元素、寫入前沒有它自己的 `DELETE`。
- **先後（照實寫）**：來源追蹤是在改預期值之前、在沒改的程式上量的；但修後的實測也在改預期值之前已經跑完；位元組碼的逐一核對，以及下面三個只印不判的計數的來源追蹤，是之後補的。數字經證據審查從原始輸出獨立重算，都對；說法依審查意見改成現在這樣。
- **不用改的兩個 fixture**：手做框的那一個，函式的四個變數沒有 wrap 也沒有值型 option，`local_initval` 與 `variable_initval` 結果相同；手做全域的那一個用 `variable_initval`，全域初始化沒改。
- **只印不判、跟著下降的三個計數**：第一次呼叫的活槽 +33 → +8、一次不寫入的呼叫留下的槽數 1 → 0（兩個計數）、一次拆除留下的活槽數 7 → 4。最後一個只在拆除那一刻追了來源，「每輪一個」沒有逐輪量；那個模式要求的是既有的退出碼 87，不變。
- **其他有變的輸出**逐條歸類：槽號與配置序號重新編號（有大有小）、亂數、計時、暫存目錄名、警告訊息裡的行號；沒有解釋不了的。

## 仍有差異與未涵蓋項目

- 期望值都來自原版的靜態反組譯，沒有一案在原版上跑過；本組沒有做原版實跑（洩漏是移植版自己的配置，原版不配這個物件）。
- 所有實機趟都在螢幕鎖定下跑；修後沒有量超過連續三場（12 分鐘）；寫快照本身的淨耗時分不出來（量到的是含快照的窗裡最長的一幀）。
- 字串、陣列、delegate、非值型 option 的區域變數在原版也是 -1，這裡仍配一格。其中第一次寫入前沒有 `DELETE` 的（字串、陣列、option）是同一種漏法，量小一到兩個數量級，讀取端另要查（第二階段）。修後戰鬥結束時仍沒有持有者的東西，大多是這一類加上戰鬥物件。
- 值型 option 的旗標格仍和原版不同：原版寫「沒有值」，這裡第一格之後是 0。既有差異，不改。
- 全域與陣列元素的 wrap 仍是盒子（全域只初始化一次，不是洩漏來源）；元素是 wrap 的陣列在本作有沒有、會不會漏，沒有找。
- 每寫一次快照仍留下一頁部件序列化的資料（部件引擎的存出把陣列槽當成盒子用；屬引擎快照讀回那一組）。
- 讀程式得到、沒有實跑的：舊版本寫的映像裡的盒子讀回後每個框最多再漏一次，映像裡本來就沒有持有者的盒子照原樣讀回；開了除錯器的建置顯示 -1。
