# 片頭影片：APEG 影像解碼

2026-10-18。程式 `4f2c7cd`，基準 `0e2e750`（前一組程式 `b31bc51`），libsys4 固定 `247f544`。提交前、後的預設與 GBK 各 103 個模式 PASS。

這一步讓片頭有畫面。前一步（[純音訊預載止崩](../movie-audio-only/README.md)）之後，走到片頭不再當機，但畫面一直是黑的。

## 格式

遊戲唯一的影片是 `Movie/Op.apeg`，格式是 AliceSoft 自訂的 APEG。

**容器**：
- 檔頭：版本、寬高、量化矩陣、總長、I 影格索引。
- 之後是一串區塊：縮圖、音訊（直接是一段 Ogg Vorbis），以及 I／P／B 影格。
- 每個影格區塊帶自己的時間戳，檔內是解碼順序。

**影像**：骨架是 MPEG-1，但不是任何標準的位元流：
- 和 MPEG-1 相同的部分：16×16 巨集區塊、4:2:0、8×8 DCT、I／P／B、半像素向量。
- 和 MPEG-1 不同的部分：沒有起始碼、沒有 slice 層、欄位順序不同、碼表重新分配；反量化的奇數化方向和 MPEG-1 相反（往遠離零的方向）。
- 所以現成的解碼器（FFmpeg、pl_mpeg）都解不了。

## 原版依據

只做靜態分析：讀已解殼的執行檔與它的 AIN，沒有執行；位址都在多娜多娜這一支執行檔裡。

| 項目 | 位址 | 內容 |
|---|---|---|
| 開檔、檔頭、影格區塊 | `0x4484f0`、`0x4492b0`、`0x448820` | 版本只收 3 與 5；區塊走訪 |
| I／P／B 解碼 | `0x45cd70`、`0x45ce10`、`0x45cf90` | 巨集區塊語法、八張碼表、向量（`0x45e170`） |
| 補償 | `0x44bbe0`、`0x44c6e0` 起 | 半像素的兩點、四點平均都往零截斷；色度向量是亮度向量 ÷2 往零截斷；雙向是兩邊各自取整後再平均 |
| P／B 的跳過 | `0x44bb10`、`0x45d0f0` | P 從前向參考原位複製；B 沿用上一個巨集區塊的方向與向量，跳到影格尾時向量歸零 |
| 反量化與 IDCT | `0x44b590`、`0x44b330`、`0x44afd0` | 奇數化往遠離零；定點 IDCT（縮放表 `0x80d408`，結構同 AAN），每一步的取整方式照抄；只有 DC 時捷徑 `trunc(c0/256)` |
| 參考影格 | — | 兩張 int16 平面、不夾值；P 開頭輪替、I 解完輪替 |
| 輸出 | `0x44c2c0` | Y 夾 16–235、Cb／Cr 夾 16–240，打包進一張紋理，色度不在 CPU 上取樣 |
| 轉色 | 內嵌的著色器包，影片用的鍵值由 `0x6f43a0` 決定 | 限幅 BT.601 的精確反矩陣；色度由 GPU 雙線性上取樣 |
| 挑格 | `0x44a1b0`、`0x44a5d0` | 每次繪製顯示「時間戳 ≤ 現在」的最新一格，不退格；時鐘是音訊的播放位置 |

## 做法

- **新檔 `src/apeg.c`**（加 `include/apeg.h`）：
  - 容器、位元讀取、八張碼表（以碼字對數值的表格寫在檔內）。
  - 反量化、IDCT、I／P／B 重建、參考影格管理、依時間挑格。
  - 轉 RGBA：CPU 上照著色器的矩陣，色度做雙線性（取樣位置 x/2−0.25、夾邊）。
  - 原版不檢查的地方（向量指到畫面外、資料截斷）這裡安全失敗。
- **`src/movie_ffmpeg.c`**：
  - 音訊照舊由 FFmpeg 播 Vorbis。
  - 影像依音訊時鐘挑格；挑格用的時鐘不退。
- **PartsEngine**：
  - `CreatePartsMovie` 建一個由 parts 擁有的影片：表面等於影片大小，先用給的 Y／Cb／Cr 底色填滿。
  - `UpdateComponent` 時上傳目前的影格。
  - `IsEndPartsMovie` 跟著音訊；`GetPartsMovieEndTime` 回檔頭總長；`PlayPartsMovie` 的起始位置有效。
  - `PartsEngine.Release` 會停掉影片：遊戲的 `CDrawMovie` 就是這樣釋放影片的 parts。修改前影片在 Release 之後還在，跳過片頭後聲音會繼續播（推論）。
- **`movie_plmpeg.c`**：補上缺的 `movie_get_video_size`，非 FFmpeg 後端又能連結。

## 驗證

- **全片逐位元**（私人工具，遊戲資料不進 repo）：
  - 另寫一份獨立的參考解碼器（Python），全片 3078 格的 int16 平面與 RGB 和這裡的 C 實作完全相同。
  - 參考解碼器和原版遊戲在 Wine 上的片頭截圖比了 44 張：4054 萬個像素只有 681 個差 1，全部落在 GPU 浮點取整的 .5 平手點。
  - 把關鍵規格一條條換成別的寫法（取整方向、捷徑、色度向量、雙向平均、跳過的規則等），差異都會大量增加。
- **探針 `apeg-video`**（15 案，說明見 [harness](../../harness/README.md#apeg-影像探針)）：
  - 素材在建置時合成，期望值由探針裡另寫的模型算出。
  - 修改前 15/15 失敗，見 [before.tsv](before.tsv)。
  - 這個探針證明的是「合成影片的產生器與解碼器一致」；和原版一致靠上面的私人比對。
- **兩組 verify**：提交前、後的預設與 GBK 各 103 模式 PASS，見 [verify.tsv](verify.tsv)。
- **實機片頭**：
  - 從第 2 天的自動存檔，用自動點擊重播一條手動玩過的路線：兩場戰鬥、撤退、片頭，之後接到第 3 天。不需要人操作，結果可以重現。
  - 提交後的執行檔：760 秒，exit 0，錯誤 0；對白 451 句，和前一組（只有聲音的片頭）逐字相同。
  - 片頭期間每 2 秒取一張引擎畫面，共 50 張，每張都和參考解碼器的某一格**逐像素完全相同**。對到的影片時間從 1933 到 99900 毫秒，每秒前進約 1000 毫秒（擬合殘差最大 0.096 秒）：畫面確實跟著音訊時鐘走。見 [movie-frames.tsv](movie-frames.tsv)。
  - 既然參考解碼器和原版截圖只差 .5 平手點，移植版的片頭畫面在這些時點和原版一致。實作版（審查修正前）也跑過一次，結果相同；那次使用者在電腦前，看到片頭動畫並接到第 3 天。
- **例行路線**：
  - normal150、haruuri、fightr 都跑完：時限結束、exit 0、錯誤 0，沒有載入影片。對白和前一組逐字相同（88／629／681 句），haruuri 的 15 個點擊目標相同。
  - fightr 的點擊目標和前一組提交後那次差 63 處、和提交前那次差 3 處，是已知的兩群現象，根因仍未確認。
  - 見 [routes.tsv](routes.tsv)。
- **另外的審查**：程式、接線、探針與公開 repo 衛生各有獨立審查與修正後的複審，摘要見 [review.md](review.md)。

## 與原版還不同、沒做與沒驗證

- **聲音**：
  - 沒有錄音或聽測。
  - `SoundID`／`SoundGroup` 沒接，片頭聲音是自己一條音訊流、音量固定，不跟遊戲的音量群組。
  - 挑格的時鐘是「已交給混音器的音訊量＋牆鐘」，比聽到的聲音超前約 23–46 ms，再加上輸出裝置的延遲（沒量）；原版用聲音的播放位置。
- **效能**：解碼與轉色在主執行緒同步做；最佳化建置每次換格約 4–5 ms，隨機往回跳最壞約 23–35 ms。原版在背景執行緒預先解 30 格。
- **轉色**：在 CPU 上做，所以和 GPU 在 .5 平手點的取整可能差 1；顯示用的取樣器是不是 CLAMP 只能由畫面推定。
- **沒有音軌的 APEG** 打不開（原版改用計時器播放）。多娜多娜只有這一個影片，它有音軌。
- **別的遊戲、版本 3**：沒有檔可以驗；版本 3 用同樣的解析。
- **探針用的移植版選擇與推論**：不是原版行為的期望值都在 harness README 標出來了（例如找不到的 parts 的 `IsEndPartsMovie` 回真）。
- **其他平台**：Windows、Linux 沒有建置。
