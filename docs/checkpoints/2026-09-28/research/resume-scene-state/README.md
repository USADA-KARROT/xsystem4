# R1b：v14 引擎快照讀回後的場景狀態

2026-11-22。程式提交 `7444591`（2026-11-22）、父提交 `8afc86b`（R1a 的文件提交；R1a 程式 `372c83e`）；libsys4 固定 `247f544`。審查經過見 [review.md](review.md)；新模式的修前修後見 [before-after.tsv](before-after.tsv)，提交說明的逐句查證摘要見 [verify.tsv](verify.tsv)。程式推送的三方核對記在 [HANDOFF](../../HANDOFF.md)。

這一組是引擎快照讀回的第二段（讀回後的場景狀態）。第一段（[R1a](../resume-image/README.md)）讓移植版自己寫的快照讀得回來；這一段讓讀回之後畫面與腳本跟快照裡存的一致，兩個重試鈕與回想的重播讀回之後能接著玩下去。讀不回時的處理是第三段，還沒做。

用語沿用 R1a：**引擎快照**是腳本以 `system.ResumeSave` 寫、`system.ResumeLoad` 讀回的整個 VM；預設格式 rsm（移植版寫 libsys4 的第 9 版），另一種 json。**部件影像**是腳本在寫快照之前，以 `PartsEngine.Save` 把部件引擎存進自己的一個 `array<int>` 的資料（移植版的 XPE 格式，v14 是第 14 版）；讀回之後以 `PartsEngine.Load` 還原。**盒子**是移植版給 v14 的 wrap 值所用的一格 struct 頁。**上一個候選建置**是這一組補上快進停用段之前的那一支執行檔（`c904e6a5`）。

## 問題【量測】

R1a 之後（已推送的版本），從標題讀舊的手動存檔複本、在敵方數值調過的遊戲資料複本上全滅：

- 回到戰鬥之前：回到同一場戰鬥的第一回合、可以打贏，結算正常，但回到地圖後畫面全黑（音樂、輸入、腳本都在走）。
- 回到一格之前：讀回後畫面全黑，點地圖沒有反應。
- 回想的重播：讀回後回到回想頁，但要按兩次返回才回到標題。
- 每次讀回都印部件資料是空的；回到地圖或回想頁之後印一行堆疊下溢。

R1a 提交後的前期研究（讀程式並對上實機紀錄，經獨立查核）找到兩個獨立的成因，查核另指出只修第一個操作不會恢復：

1. **部件影像是空的（全黑的原因）**。`PartsEngine.Save` 與 `Load` 在 AIN 裡宣告成 `wrap<array<int>>`，FFI 傳的是呼叫者那個陣列的堆積槽號。移植版把那個槽當成 wrap 的盒子：沒有元素的陣列寫不進東西，呼叫者的陣列一直是空的，另外配的頁沒有人持有（每存一次留下一頁）。讀回時 `Load` 拿到空陣列就放棄，遊戲結束畫面那一層與合上的遮板留在原地、蓋住地圖；重試回到戰鬥時戰鬥畫面疊在上面所以看得到，戰鬥結束回到地圖就被蓋住。
2. **呼叫框的內部欄位沒有還原**。快照每個框只存四個欄位（函式、返回位址、區域頁、struct 頁）。移植版自己加的欄位——返回時校正堆疊用的基準、是不是方法或委派呼叫、委派要回傳的格數、閉包的環境頁、委派呼叫持有的兩個參照——與正在呼叫的委派的游標與上限，讀回後都是 0。第一次從讀回的框返回就把運算堆疊截掉（堆疊下溢的警告由此而來），委派迴圈剩下的處理函式也被跳過。三種快照都是在部件的更新事件委派迴圈裡寫的，所以只修第 1 項，操作不會恢復；兩項同一組、一次提交。

修好第 1 項之後已知還會壞的（同一份研究）：部件的唯一編號沒有存（腳本的訊息管理以它比對訊息）、部件的訊息佇列讀入時不清、活動登錄表、使用者元件資料、v14 數字部件的欄位沒有存；查核之後又找到部件的快進旗標沒有存（見〈快進停用旗標〉）。

## 原版怎麼做【靜態反組譯】

原版只用靜態工具讀，沒有執行原版或脫殼版。證據等級照實分：

- **部件存讀的入口**【兩位以上各自核對】：`Save` 經 `0x589535` → `0x59b580` → `0x5405a0`，`Load` 經 `0x58959d` → `0x59b5a0` → `0x540830`。引數直接解成陣列物件，寫入的對象就是呼叫者的那個陣列，原版沒有盒子。`Load` 先清空（放掉全部部件、刪掉每個控制器）再從資料重建，不是合併。
- **活動登錄表**【三位查證者各自用靜態工具核對】：存出函式裡 `0x540665` 呼叫 `0x563b10`（對象是部件引擎 `+0x128`，`IsExistActivity` 也用這個位置）；讀入在 `0x56d870` 裡呼叫 `0x563c20`，一開頭先清空。表裡每個活動有部件名對編號表、關閉的部件名、結束鍵；原版每筆活動另有第二個字串，移植版的活動沒有這個欄位。
- **快進停用旗標**【實作者與兩位審查者各自核對】：設值 `SetEnableSpeedUp`（`0x5909f0`，寫入 `0x590a36`）與取值 `IsEnableSpeedUp`（`0x590a80`，讀取 `0x590ac8`）都用部件 `+0x22d`，也就是參數區（在 `+0x84`）的 `+0x1a9`；新部件預設啟用（`0x550a9c`）。參數區的存出 `0x551771` 讀這個位元組、`0x55179a` 寫成 0 或 1；讀入在原版自己的資料版本 36 起（`0x551ee4`，版本來自函式的第一個參數）由 `0x551ee9` → `0x72c6b0` 讀回（剩餘長度不足就不寫；否則寫「位元組等於 1」）。設值與取值都先經 `0x540250`，那是「取得或建立」：號碼大於 0 時會建立部件，0 以下才沒有物件；移植版在這一點和原版一致。原版的資料版本 36 是原版自己的格式版本，和移植版 XPE 的版本分開。
- **使用者元件資料、唯一編號、v14 數字欄位**：**沒有找到原版存檔的位址證據**，是依腳本怎麼用這些東西決定要存的（例如腳本的訊息管理以唯一編號比對每則訊息）。
- **呼叫框**：原版自己的快照是 rsm 第 14 版的另一套配置（R1a 已對照），格式本身帶了移植版沒有的 VM 狀態（區域頁的外層頁、委派頁的兩個計數），和移植版遺失的環境頁、委派游標是同一類東西【推論】。原版讀回時除了 VM 之外有沒有動 C 端（訊息佇列、聲音、輸入），沒有讀到。
- 原版的部件存出沒有先跑一次部件更新；移植版的存出先跑（既有行為，這一組沒有改）。

## 移植版的做法【讀程式】

### 部件影像

- `PartsEngine.Save` 與 `SaveWithoutHideParts` 在 v14 寫進呼叫者的陣列（換掉那個槽的頁），`Load` 讀那個陣列；陣列沒有資料（沒有元素的陣列、沒有頁的槽，也就是前一版寫的東西與從沒存過的腳本）時，讀入在放掉現有部件之前就失敗、什麼都不改。一格的 wrap 盒（轉接也接受的形狀）照樣能存讀。
- 讀入 v14 部件影像時清空部件的訊息佇列（訊息指名的部件與唯一編號屬於被換掉的狀態）。
- 這款遊戲的 AIN 只宣告了 `Save` 與 `Load`，`SaveWithoutHideParts` 是探針用一個引數的 `Save` 合成的。

### 影像格式的可選段

XPE 第 14 版原本就有幾個可選段（每段以四個字元的標記開頭；既有的是 CG 變形、滾輪、音效名，最後是控制器編號段）。這一組在音效名段之後、控制器編號段之前，依序加上五段：

| 內容 | 缺段時 | 壞段時 |
|---|---|---|
| 唯一編號（部件號碼與唯一編號成對；只列有主記錄的部件） | 照以前讀（沒有唯一編號） | 印警告；筆數不合理時略過（讀入不失敗），讀到一半出錯時讀入失敗 |
| v14 數字部件的欄位（表示類型、字型、ＣＧ名與寬度、全角、補零） | 照以前讀（數字部件是未定型） | 印警告；筆數不合理時略過（讀入不失敗），讀到一半出錯時讀入失敗 |
| 使用者元件資料（元件名、鍵與值） | 照以前讀 | 讀入失敗 |
| 活動登錄表（部件名對編號、關閉名、結束鍵、下一個號碼、控制器已釋放的標記） | 保留現有的活動表 | 讀入失敗；先在暫存表驗證再換入，活動表不會只換一半 |
| 快進停用的部件號碼 | 讀取位置不動，全部是預設（啟用） | 讀入失敗 |

唯一編號與數字兩段壞掉時【讀程式，沒有探針案】，這兩段自己只印警告，結果分三種：(1) 筆數不合理（負數或超過剩下的字數）：讀了標記與筆數就停，讀取器沒有出錯；下一個字通常不是任何段的標記，所以之後的使用者元件、活動、快進三段被當成缺段，讀入回報成功，但那三段沒有讀進來（活動表保留讀入前的）。(2) 讀到一半超出範圍（數字段的筆數合理、但每筆實際比剩下的字長，或唯一編號段的標記剛好是最後一個字）：讀取器出錯，數字段在這之前已經套進的幾筆保留，接著使用者元件段與活動段一開頭看到讀取器出錯就回報失敗，讀入失敗——這時現有的部件已經放掉。(3) 內容錯位但沒有越界：之後的段可能被當成缺段，也可能被誤讀，結果不確定。讀取都有界限檢查、失敗路徑都會放掉暫存，沒有看到記憶體安全的問題。只有損毀或被改過的資料會走到；移植版自己寫的資料，寫出與讀取兩端逐欄對稱，不會走到。這兩條路併入下一組（讀入失敗時的處理）。

- 段的內容都是移植版自己的記法。**部件影像和原版引擎寫的部件資料不相容**（原版是位元組流加壓縮、另一套欄位），這一組不追求相容。缺段的資料（前一版寫的）照以前讀，所以舊資料的行為不變；不認識新段的讀取端讀完它認識的段就停，控制器編號段本來就從尾端讀。
- 活動表超過段的上限（下一個號碼超出範圍、某個部件號碼等於上限、控制器已釋放的標記超出範圍）時存檔失敗。
- `PE_Load` 不是原子操作：上表標「讀入失敗」的，失敗時前面已經換掉的部件不會還原，和既有各段相同。
- **快進停用段**的寫出篩選和主記錄相同：`SaveWithoutHideParts` 不列隱藏的部件、標成不保存的不列、控制器根不列；只列停用的號碼，沒有停用的部件就不寫段（這種存檔逐字不變）。讀入時只對已經存在、不是控制器根的部件設停用，不憑號碼建立部件；筆數為負或超過剩餘字數時失敗。移植版只存停用的號碼、其餘用預設，對有主記錄的部件和原版逐部件存一個位元組等價（讀入都是從空的部件表開始）。控制器根：移植版不列、讀回後是啟用；原版的根有沒有自己的參數區、會不會被保存，沒有追——移植版只有訊息視窗讀這個旗標，根不會是訊息視窗，所以移植版內沒有可觀察的差別。
- AIN 14 之前，部件影像照舊寫讀（v13 寫出的位元組不變、沒有新段標記，探針驗過）。

### 呼叫框的還原

- 從 v14 快照讀回的框，方法與委派旗標（含委派要回傳的格數）由「結束在返回位址的那一條呼叫指令」取得（方法呼叫、委派呼叫）；返回時從堆疊頂取結果。
- 每個框的閉包環境頁、委派呼叫持有的兩個參照、正在呼叫的委派與它的游標與上限、從 C 進入的框是不是方法，v14 時寫進快照：rsm 寫成最後一則保留的 comment，json 寫成呼叫堆疊項目的欄位。這也是移植版自己的記法，**和原版引擎寫的快照不相容**。
- 沒有這些資料的快照（前一版寫的）：委派呼叫的物件參照用框的物件，環境頁在委派項目只指一個時從那裡取，游標與上限在框返回時設定；不是委派的框沒有退路。
- rsm 的腳本 comment 不含保留的紀錄，腳本改寫 comment 時保留它。**舊程式讀新寫的 rsm 時，會把保留的紀錄當成最後一則 comment 交給腳本**。反過來，舊版寫的完整 rsm 若最後一則一般 comment 剛好符合保留紀錄的標記、可解析的欄位與框數，新版會把它當成紀錄、不交給腳本（以欄位格式與框數判定，沒有逐框確認數字的來源）；單純以相同文字開頭的一般 comment，兩種字元規則都確認照常交給腳本。
- v14 的 json 讀入端現在保留最底框與從 C 進入的框的返回位址 0xFFFFFFFF（以前經 cJSON 的整數值飽和成 0x7FFFFFFF）；v13 照舊。
- AIN 14 之前，引擎快照照舊寫讀（框的重建在 14 之前直接返回）。

### 兩個不分版本的小修正

- 讀 rsm 的腳本 comment 不再每則留下一個字串槽（配陣列時已經配好字串槽，舊程式又另配一個蓋掉）。
- 經 wrap 盒存部件時，不再先放掉盒子還持有的舊頁（那時槽還指著它），也不再多持有一次新頁。AIN 14 之前、`Save` 宣告成 wrap 的遊戲會走到這一條；只改記憶體與槽號，影像內容不變。

### 診斷用環境變數

`XSYS4_RESUME_TRACE` 與 `XSYS4_PARTS_CTRL_TRACE`，空值或 0 以外都算開，只在 AIN 14 起有作用，預設關。前者印每份寫出或讀回的快照的呼叫框、堆疊下溢與不平衡的返回；後者印控制器、部件樹與每次部件存讀的摘要與活動表。只作觀察，不改行為。

- **格式**：快照與部件影像都是移植版自己的格式（rsm 第 9 版加一則保留的 comment、json 的附加欄位、XPE 的可選段），和原版引擎寫的檔不相容，這一組不追求相容。

- **重試後地圖上的四張隊員卡**：隊伍五人、卡片只顯示四張；讀回當下的四張和之後打贏時的四張不是同四個人——全滅那一場最後上場的是第五位，重試後那一場上場的人和讀回當下的卡片一致，數值和上一個候選建置相同。判斷是隊列在戰鬥中輪替、不是讀回造成的不一致，**沒有原版對照**，列為沒有驗證的事。
- **存檔的天數**：前幾組公開文件寫的「第 15 天的存檔複本」，讀檔清單上實際顯示第 16 天（同一份種子，名稱沿用了舊交接）；重試後回據點存的是第 17 天。
- **沒有涵蓋**：
  - 讀不回時的處理（下一組）。
  - 唯一編號段與數字段壞掉時：筆數不合理時只印警告，之後三段被當成缺段、讀入回報成功；讀到一半超出範圍時，已經套進的數字保留，接著讀入失敗（部件已經放掉）；內容錯位時結果不確定（見〈影像格式的可選段〉；讀程式，沒有探針案）。
  - 可選段對畸形資料的上界檢查不完整：快進停用段與既有各段一樣，把尾端的控制器編號段也算進剩餘長度，手改或壞掉的資料可能把控制器段的字當成部件號碼（只影響畸形資料，不是這一組的退步）。
  - json 格式沒有實機趟。
  - v14 之前的遊戲沒有實跑（只有合成探針）。
  - 讀回後的從 C 呼叫：只驗了探針裡的形狀，不主張任意 C 呼叫者能接續，也沒有驗全部的方法呼叫形狀。
  - 委派不回傳值、處理函式卻回傳值的讀回（探針那兩案一律跳過）；回傳 wrap 的讀回方法框（格數是估計值，沒有樣本）；前一版寫的快照在讀回到返回之間有委派項目被刪的情形（退路的游標可能差一）；同一個委派跨讀回的巢狀呼叫、找不到呼叫指令的框（都沒有探針案）。這幾項是第一、二回合語義審查的意見，見[審查](review.md)。
  - 部件存出前先跑一次更新（原版沒有，既有行為）；原版每筆活動的第二個字串（移植版沒有這個欄位）。
  - 每次讀回仍印附加檔找不到，腳本仍以 `system.Error` 報告劇情回顧的附帶資料讀不回；重試或回想之後劇情回顧對玩家的影響沒有量。
  - 長時間連續遊玩、反覆重試或反覆進出回想。
  - 跨字元規則的資料互換（活動名與元件資料只驗了相同規則下的原樣往返）。

## 給玩家

戰鬥全滅後，遊戲結束畫面上方的兩個重試鈕現在都能用。選「回到戰鬥之前」：回到同一場戰鬥的第一回合重打；打贏之後結算照常，回到地圖時地圖完整（隊員卡和可以點的格子都在），可以接著走、打下一場，下一場打完地圖上隊員卡的數字會更新。選「回到一格之前」：先回到進這場戰鬥之前的地圖，地圖完整，再點同一格就重新進這場戰鬥、從第一回合開始；打贏之後回到地圖，隊員卡的數字會更新，系統選單也開得出來、關得掉。連續兩次全滅時，第二次也能重試（第一次全滅時持有 2 個重試道具，第二次剩 1 個）；道具用完之後的情形沒有測。重試之後撤退，結算畫面是乾淨的。重試、撤退回到據點之後存檔，不關遊戲直接讀回，回到同一天、同樣金額的據點；關掉遊戲再開、再讀這份新存檔還沒有驗過，重要的進度請另外多存一格。之前的版本存的一般存檔照常讀得進來（試了兩份存檔的複本，都能進據點、地城、開戰）。鑑賞模式的回想：看完一段會回到回想頁，按一次返回就回到標題（是按住快轉看完的，沒有測不快轉、自然播完）；再進回想頁，縮圖還在，可以再看。已知的事：打贏之後地圖上的四張隊員卡，顯示的四位可能和重試當下不同（隊伍有五人、卡片只有四張；判斷是戰鬥中換人上場，沒有和原版對照）；重試或回想之後，劇情回顧（看過的對白紀錄）可能不完整，這一點沒有量；快照讀不回時程式仍會直接結束（下一組處理），所以進地城前先存檔仍然是好習慣。這些是在人工條件下量到的（重試的情況用敵方數值調過的遊戲資料複本），全部在螢幕鎖定下跑，每種情況只跑了一兩趟；上一個候選建置曾和英文原版在不同進度上走過相同的步驟，沒有和原版同情境的畫面對照。
