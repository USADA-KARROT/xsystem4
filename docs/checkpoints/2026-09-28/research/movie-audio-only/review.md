# 獨立審查摘要

2026-10-18。在提交之前，由四個獨立的唯讀審查分頭進行：

- 正式程式
- 新探針與 harness
- 證據數字逐項重算
- 移植版與原版的同狀態並排

沒有 High，也沒有這次修改引入的 Medium。完整審查與並排圖留在私人工作區，這裡不收錄遊戲畫面、遊戲輸出與個人路徑。

## 程式

- 修改只動 `preload_packets()`。兩個佇列都存在時，算式與原本相同。反組譯正式目標檔的結果：多了一個「佇列是否為 NULL」的判斷，門檻比較不變。
- 純音訊時會走到的函式逐一讀過：載入、讀封包（含結尾）、解碼、音訊 callback、播放、繪製、結束判斷、位置、音量、尺寸、釋放。除了這一處，沒有其他 NULL 解參考。
- 讀到結尾之後不會無窮迴圈。
- 鎖的順序沒有死結。
- 沒有改到任何 AIN 版本或文字編碼的分支。
- 既有的兩個 Medium 不是這次引入的，止崩之後純音訊影片才真的走得到；已寫進研究的限制，之後另開一組：
  - 解碼錯誤或播放失敗時永遠不結束。
  - `movie_play()` 呼叫兩次時，前一個混音聲道會讀到已釋放的記憶體。

## 探針

- 修正前，MA1–MA5 都是 `av_fifo_can_read+0x4` 的 NULL 解參考，行號對得上基底的原始碼。MA6、MA7 原本就通過，理由合理。
- 新探針只用基底已有的 API，可以在舊程式上建置。
- 新增的每一行都掃過：沒有遊戲素材、遊戲字串或個人路徑。
- 採用的建議：在 harness README 寫明修正前的結果、各案的界限（MA4 的 30 ms、position、預讀封包數、MA6 只是對照），以及素材的相依與影響範圍。
- 沒採用的建議：探針程式本身的小改動，以維持修前失敗證據所用的同一份探針。

## 證據

可量的說法逐一重算，沒有不符：

- verify 的模式數與結果。
- 四條實機的秒數、exit 與執行檔 hash。
- MSG 與 PNG 的數量。
- 黑畫面的範圍。
- 錯誤關鍵字為 0。
- 點擊的差異。

另外指出：

- **執行檔內嵌 `git describe`，提交後的 hash 必然不同。** 處理方式是提交前先保存所有建置產物的 hash，提交後逐位元組比對，結果見研究 README。
- **片頭期間沒有輸入**，log 只能證明滑鼠那一半。

## 並排

同步紀錄的說法與畫面一致：

- 第二戰技能欄的位置。
- 片頭期間全黑，原版有影像。
