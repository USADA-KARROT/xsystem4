# `X_ICAST` 的結果槽、亂數與 `Array.Shuffle`（顧客同一張臉、劇情回顧沒有字）

2026-10-09。程式 `6ee5521`（`X_ICAST`）與 `f2ad370`（亂數）。兩者都來自照原版逐一核對 VM 指令與函式庫的盤點，而不是從單一畫面的症狀追出來的。

## 一、`X_ICAST`（`6ee5521`）

### 根因

`X_ICAST` 在堆疊上留下 [物件, 物件, vtable 偏移]。原版留下的是 [物件, vtable 偏移, 0]（成功）或 [-1, 0, 1]（失敗）。腳本測第三槽的地方有 157 處，於是把 vtable 偏移 1 以上的介面轉型一律當成失敗。

遊戲本體受影響的轉型有 15 處：`CSpriteParts@Get#1` 取 `ISprite`（10 處；對 `CCGParts`、`CTextParts` 一律回 null）、`CBackLogView@GetFont`（劇情回顧拿不到字型）、商店的三種按鈕（`IShopButton`）、`SceneYakataMenu@CreateButtons`。另外，回傳或存入 option 的形狀在失敗時由「有值但為 -1」變成「無值」。其餘使用點在活動編輯器裡，遊戲不會走到。

### 原版依據（靜態反組譯）

| 項目 | 位址 | 內容 |
| --- | --- | --- |
| `X_ICAST` | `0x66c540` | 同型在 `0x66c727` 推 0、0；介面配對命中在 `0x66c752` 推偏移、0；失敗在 `0x66c6bc` 把物件改成 -1 後推 0、1；整個函式不動參照計數 |
| 取 struct 頁 | `0x67ac30`（`0x67ac8e`） | 頁的型別不是 struct（4）就失敗 |
| `X_TO_STR`，bool | `0x66c1a6` | `"true"`／`"false"` |
| `X_OP_SET` | `0x66fcf7` | 運算元 0x10001 與 0x10003 是三槽，其餘兩槽 |

### 修正

`src/vm.c`：`X_ICAST` 照原版的三槽與失敗值，並檢查頁型別；`X_TO_STR` 對 bool 產生 `"true"`／`"false"`；`X_OP_SET` 0x10001 寫三槽。

`X_TO_STR` 對 bool 的 14 個使用點裡有一處寫進存檔的註解欄（`SaveObjectParam@Encode`）。讀回時以整數解析那一欄，隨後又被建構參數覆寫，所以修正前寫出的存檔照樣讀得進來。

## 二、亂數與 `Array.Shuffle`（`f2ad370`）

### 根因

`Array.Shuffle` 呼叫 `srand(種子)` 再用 C 函式庫的 `rand`。腳本 37 個呼叫點傳的種子全是 -1，所以每次洗出同一個順序，還順帶把全域的亂數序列重設。春銷的顧客立繪是「依標籤算分、取最高分那一批、洗牌後取第一個」選出來的，四位顧客因此是同一張臉、同一份簡介。

### 原版依據（靜態反組譯）

| 項目 | 位址 | 內容 |
| --- | --- | --- |
| `Array.Shuffle` | `0x6493f0`（函式庫表 `0x644f18` 第 60 項） | 每次呼叫在堆疊上建一個自己的產生器；種子小於 0 時取時間（`0x41b3c0`）；正向 Fisher–Yates；以陣列的虛方法交換整個元素；不動 Math 的全域序列 |
| 產生器 | `0x4c6e40`、`0x4c6d40` | R521 |
| `Math.SetSeed`／`Rand`／`RandF` | `0x4c673c`、`0x4c676a`、`0x4c70c0` | 同一種產生器的全域實例；`RandF` 的範圍是 [0, 1] |

### 修正

- `src/hll/Math.c`：v14 的 `SetSeed`、`SetSeedByCurrentTime`、`Rand`、`RandF` 改用 R521；更早的版本維持 C 函式庫的序列。`SetSeedByCurrentTime` 仍然對 C 函式庫播種（引擎裡別處的視覺效果直接用它）。
- `src/hll/Array.c`：`Shuffle` 照原版——自己的產生器、種子小於 0 取時間、正向洗牌、多槽元素整個交換。
- 測試用的開關（預設都不啟用）：`XSYS4_RANDOM_SEED=<n>` 讓取時間的種子可重現（第 k 次用 n + k）；`XSYS4_TRACE_OUTPUTLINE=1` 印出 `system.OutputLine`。`run-gui-bounded.py` 把 `RUN_RANDOM_SEED`、`RUN_TRACE_OUTPUTLINE` 轉成這兩個環境變數。

### 戰鬥的行動順序

第一場戰鬥第二個行動的角色與原版的截圖不同。排序的比較函式是速度降序、陣營、Id，與資料一致；每個角色的速度每回合加上一個亂數（`RAND(4401) − 2201`），而第 1 位與第 4 位的基礎速度只差約 7%。同一場的第 2 回合，這裡排出來的順序就是原版第 1 回合的順序。所以判定是亂數的結果不同，不是規則不同（沒有原版的數值可以直接對照，這是推論）。

## 驗證

- 新模式 `icast` 與 `shuffle`（[harness 說明](../../harness/README.md)）。
- 正式 before-check：`89b3d10` 上 `icast` 三組案例全部失敗；`6ee5521` 上 `shuffle` 五組案例全部失敗；修正後都通過；兩種字元規則結果相同，還原後 src／include 乾淨（[before／after](before-after.txt)）。
- 反向檢查：`X_ICAST` 的成功分支與失敗分支各自改回舊值、`X_TO_STR`、洗牌的步幅、固定的種子、種子小於 0 不取時間、`Rand` 改回 C 函式庫，每一處都有案例失敗。
- 預設與 GBK 各 76 模式 VERDICT PASS、sanitizer 0（[預設](verify-default.txt)、[GBK](verify-gbk.txt)）；既有 74 個模式的輸出相同，沒有動既有斷言。
- GUI（[摘要](gui-summary.json)，以 `RUN_RANDOM_SEED=20261008` 執行）：八條路線沒有斷言、下溢或 VM 錯誤；對白的行數與雜湊和前一組相同。同一個種子跑兩次，春銷準備畫面的四位顧客逐像素相同。

## 實機上的改變（與 Wine 上的原版並排比過；原版截圖只存本機）

- **春銷準備畫面的四位顧客是四個不同的人**（原版也是四位各不相同）。對手展示的人材、成交的金額也跟著每次不同。
- 戰鬥路線打到結果畫面並回到地城地圖。
- 劇情回顧的字型路徑由探針證實修好；畫面要等 controller 的修正併入後才開得起來，還沒有實機看過。

## 獨立審查

一輪兩個面向（VM 指令、亂數），中等級的發現另有對抗驗證。

- 沒有 High。三處指令修正與產生器、洗牌都和原版的反組譯逐項相符。
- 成立的 Medium 一件：筆記把「修正後會改變的畫面」寫錯了（把活動編輯器的類別當成遊戲路徑，漏了商店與 `SceneYakataMenu`）。已依審查者的掃描改成上面的 15 處。
- 已處理的 Low：`X_ICAST` 補上頁型別的檢查；亂數的新實作限定在 v14；`SetSeedByCurrentTime` 仍對 C 函式庫播種；`RandF` 的範圍；時間種子的整數運算；探針補失敗分支的突變、非 struct 的輸入、種子 0、空陣列與單元素、v13 的守衛。

## 與原版的差異與限制

- 商店按鈕與 `SceneYakataMenu` 的轉型現在會成功，下游呼叫到的按鈕函式多半還是空殼；自動路線到不了這兩個畫面，**沒有實機驗證**。
- 亂數序列沒有原版的實測值可以對照；參考值來自照同一份反組譯另寫的 python 版。Mersenne Twister 那一組函式沒有逐一核對。
- 固定種子只讓「取時間的種子」可重現。較長的路線裡呼叫順序受畫面時序影響，同一個種子跑兩次戰鬥路線，後段的點擊目標仍然不同。
- 亂數改成真的隨機之後，春銷與戰鬥的自動路線每次遇到的顧客、金額、行動順序都不同；仍然穩定的是對白的行數與雜湊。
- `A_REF`、`X_SET`、`X_OP_SET` 運算元 2 在原版是複製內容，這裡是共享參照；這一組沒有改（腳本裡 `X_SET` 222 處、`X_OP_SET` 2 共 274 處，要連同參照計數一起設計）。
- 戰鬥路線的峰值記憶體在 1.0 到 1.5GB 之間波動，沒有分辨是正常載入還是累積。
