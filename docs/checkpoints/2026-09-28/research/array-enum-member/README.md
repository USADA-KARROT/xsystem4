## 問題與修正範圍

【量測】讀存檔之後進到下一場戰鬥，擊倒結算畫面點不掉：結算畫面只接整畫面的左鍵放開，而整畫面的點擊沒有人處理。同一條路線在父提交上，結算約 149 秒出現，第一下點擊（約 149 秒）之後約 147 秒、到趟結束都還是同一張結算畫面（點了五下，另按了兩個鍵）；新開局路線沒有這個問題。程式提交說明寫的「144 s」是用不屬於那一趟的點擊時刻算的近似值，以這裡為準。

【量測】加了計數的診斷版（不提交）量到的經過：讀存檔時 `system.DeserializeStruct` 還原戰鬥資料，為它逐層建出的成員物件不跑建構子，戰鬥獎勵的那個列舉陣列成員因此由 `init_struct_slot` 建成泛型陣列頁（`AIN_ARRAY`）。進下一場戰鬥時拆掉這份戰鬥資料，泛型頁的拆除把元素當成堆積槽號；陣列裡的兩個列舉值剛好是兩個全域物件的槽號，兩個物件的參照數都被扣到 0 而釋放，其中一個是把整畫面輸入交給腳本的管理物件。之後 method call 的自動配置在原處放了一個沒有建構的物件（父提交讀存檔路線：值被當成槽號 2 次、自動配置 1 次）。新開局路線上，這個成員由建構子裡的 `X_A_INIT` 建成 int 頁，所以沒事。

【量測】這個缺陷不是近期改動的退步：11/07、11/10、11/12 三個舊版的最佳化執行檔用同一份存檔各跑一趟，擊倒結算畫面都關不掉，加上 11/13 的版本，共四個版本重現；根因那一段程式是 7/06 移植 v14 核心時就有的，比 11/07 更早的版本沒有量。會不會發作取決於存檔內容：讀檔還原的那個陣列裡的列舉值剛好等於某個全域物件的槽號時，才會誤刪那個物件；量到的那份存檔是兩個值、對到兩個全域物件，其中一個負責把整畫面的輸入交給腳本。其他存檔可能誤刪別的物件或沒有可見症狀，沒有查。

【讀程式】`init_struct_slot`、`X_A_INIT`、`system.DeserializeStruct` 這三條建陣列頁的路徑裡，只有 `init_struct_slot` 把列舉元素留在泛型；`X_A_INIT` 與 `system.DeserializeStruct` 為沒有頁的目的新建陣列時都對成 int 頁。其他建頁的地方見〈仍有差異與未涵蓋項目〉。本作陣列的值型別元素只有 int、float、bool、列舉四種；struct 成員宣告為列舉陣列的有 5 個，實際量到出錯的只有戰鬥獎勵那一個（只有它有一條不跑建構子的建立鏈）。

【策略】本組只做三項：

1. **建立點一致**：新增 `array_value_page_type()`（int、bool、列舉元素 → int 頁，float 元素 → float 頁，其他 → void），`init_struct_slot`、`X_A_INIT`、`system.DeserializeStruct` 的載入與下面的映像修補都用它判定值型別。行為上唯一的改變：`init_struct_slot` 對列舉陣列成員建出的頁，和 `X_A_INIT` 對同一宣告建出的頁型別相同（int 頁；struct_type 仍是成員宣告的型別編號）。`X_A_INIT` 與載入時目的沒有頁的情形照舊。
2. **還原時有舊頁**：`system.DeserializeStruct` 的目的頁是泛型、宣告的元素是值時，新頁照宣告的頁型別建（struct_type −1），不再照抄舊頁的型別；目的頁是其他型別時照舊。移植版的舊頁可能是舊版引擎留下的。
3. **VM 映像的修補**：讀入 v14 VM 映像（rsm、json）之後走一次堆積：存活的 struct 頁的成員宣告為值陣列、指到存活的陣列頁、而那一頁是一維、每元素至多一槽的泛型頁時，把頁型別改成宣告的頁型別；struct_type、版面與值不動，其他頁都不改。舊版引擎寫的映像可能存著這種頁。

另外改寫兩段註解：原版陣列的元素型別描述在物件 +0x2c，+0x48 是由它算出的每元素槽數（舊註解把 +0x48 寫成元素型別）；載入時新頁的函式說明補上新用途。

不做的（留給之後或列為限制）：method call 的兩段自動配置（原版在這裡是報 VM 錯誤）；`heap_unref` 對參照數已歸零的槽靜默返回；泛型頁的 struct_type 與每元素槽數（會動到兩百多個參照型成員的未建構頁）；`array_type()` 對泛型頁回傳參照的預設與各使用端；元素是 long int、第二種列舉代碼與函式型的陣列（本作沒有）；還原時 struct 成員只建物件、不跑成員的建構子是否符合原版（另案）。

## 移植策略與界線【策略】

- **共用函式只收四種值型別**：int、bool、列舉 → int 頁，float → float 頁，和 `X_A_INIT`、載入時新建陣列原本的集合完全相同。long int、第二種列舉代碼、函式型元素原版也不碰堆積，但三條路徑原本就一致地建成泛型頁、本作沒有這種宣告，不加。
- **struct_type 不統一**：`init_struct_slot` 與 `X_A_INIT` 給的 int 頁 struct_type 是列舉的型別編號，第 2 項建的新頁是 −1。【讀程式】目前找到的使用端在 int 頁與 float 頁上都不依它改變行為（沒有窮盡查過）。
- **第 2 項的條件**只看舊頁是不是泛型頁（`AIN_ARRAY`），不含參照陣列頁；舊頁是別的具體型別時照抄。【讀程式】v14 建不出宣告為值、頁卻是參照陣列或別種具體型別的頁。
- **第 3 項的條件**：v14、存活的 struct 頁、成員宣告為值陣列、成員指到存活的陣列頁、頁是泛型、一維、每元素至多一槽。struct 頁的槽號就是成員號（option 與介面的後續槽是 void 成員，不會錯位）【讀程式】。只修 struct 成員持有的頁；區域、全域、陣列元素持有的同類頁不修。一頁被多個持有者共用時型別一起改，和原版「頁帶宣告型別」一致。修補在堆積讀完、呼叫堆疊還原之後做，之後沒有別的步驟再改頁型別。
- **v14 之前不變**【讀程式】：`init_struct_slot` 的陣列成員分支與映像修補都只在 v14 執行（修補遇到 v14 之前的 AIN 一開頭就返回），`X_A_INIT` 的改寫逐分支和原本等價、v14 之前行為相同；`system.DeserializeStruct` 載入時的新條件沒有明寫版本，只對泛型頁（`AIN_ARRAY`）成立，v14 之前建不出這種頁【推論】。
- **修補救不回已經發生的事**：舊版在泛型語義下可能已經把值當成槽號扣過參照（物件已被刪）、struct 複製時把值換成新槽號、副本多加了參照。修補只改頁型別；最壞是留下多出的參照（洩漏），不會造成新的提早釋放【推論】。

## 連帶的行為改變【讀程式】

這五個成員有了 int 頁之後，凡是由頁型別決定的地方都改成值陣列。逐項（提交說明列的八項）：

1. 拆除（含 Array.Free、Clear、Duplicate 的拆除）不放掉任何東西。這是根因的修正。
2. `X_SET`、`X_OP_SET`、`ASSIGN` 寫入元素時，不再替新值加參照、替舊值扣參照。
3. `X_A_SIZE` 不再以列舉的型別編號除元素數（泛型頁會把 struct_type 當成每元素槽數）。
4. struct 複製保留值，不再把值當成槽號、複製那個槽上的物件；`A_REF` 做的副本不加參照。
5. 把含這種成員的 struct 存進 struct 值陣列時，陣列成員走正規的複製，不再共用並各加一份參照。
6. Array 函式庫的值搜尋接受它們，不再報「不支援的元素型別」錯誤。
7. 不帶比較函式的 Max、Min 照 int 排序，不再警告並回傳最後或第一個元素。
8. 帶值運算元的 Alloc 把每個元素設成 0（原版也是），不再保留舊元素並放掉砍掉的。

這些都是往原版的值語義靠攏。腳本有沒有對這五個成員的元素用 `ASSIGN`、`X_SET`、`X_OP_SET` 寫入，或呼叫不帶比較函式的 Max、Min 與帶值的 Alloc，沒有逐一查；本作對戰鬥獎勵那個成員的寫入是 PushBack（值運算元），讀取有 Unique 等【讀程式（AIN 反組譯）】。

## 讀檔方式的驗證範圍

- **已實機驗證**：從讀取畫面讀玩家存檔（第 15 天的存檔複本，兩場）與新開局（兩場）。玩家平常從讀取畫面讀存檔，走的是重啟之後由 `system.DeserializeStruct` 逐物件還原，不讀引擎快照。
- **舊版本寫的引擎快照由新版本讀回：正常遊玩沒有入口，尚未實機驗證。**【讀程式（AIN 反組譯與移植版）】腳本只有一處寫引擎快照（`system.ResumeSave`）、一處讀回（`system.ResumeLoad`）。讀回的時機：開機自動續玩、偵錯重載、遊戲結束畫面的兩種重試、重播，另外幾個本作沒有呼叫者。跨行程讀的只有開機續玩與偵錯重載；開機續玩的檔只在主機送系統訊息時才寫，移植版不送系統訊息，所以這個檔永遠不會寫出來；同一行程內的重試與重播讀的是同一支執行檔剛寫的快照。
- **人工情境下量到的**：修前版本在讀存檔後進第一場戰鬥時寫的快照（兩種格式各一份）。離線讀樣本檔（不經修補程式）確認：戰鬥獎勵那個成員是泛型頁，兩個值就是那兩個全域物件的槽號，兩個物件當時都還在；另有一個空的泛型頁屬於另一個列舉陣列成員。把它改用 json 格式、放成開機續玩的檔讀回：修補改了 2 頁（就是這兩頁），值保留；列舉值被當成槽號 0 次、自動配置 0 次、兩個全域物件到結束都在；最佳化版與診斷版續玩的那一場結算都能關。這只說明修補在那份樣本上做了這幾件事，不寫成「舊版快照的續玩已經可用」。
- **不當成證明的部分**：修前版本在同一份樣本上的對照只跑了一趟、續玩後的戰鬥時序每趟不同、沒有診斷碼，所以不當成「樣本能踩到問題」的證明；樣本含要修的陣列，依據是離線讀樣本檔。
- **快照讀回本身目前就不能用**（既有缺陷，見下一節）：預設格式（rsm）的快照在本輪實測都讀不回（修前、本組最佳化、本組診斷三支，都在修補執行之前失敗；其中一趟的原因查到是讀回時用了越界的 struct 編號，另兩趟被另一個檢查擋下，原因沒查）；json 讀回後戰鬥能接續，但回不了地圖（畫面全黑），修前與本組相同，在不需要修補的對照樣本上也相同。

## 既有缺陷（不是本組造成，本組不改）

1. **遊戲結束畫面的重試**：戰鬥全滅後，在遊戲結束畫面選兩種重試之一並確認，程式會直接結束、沒有提示。本輪預設格式的實測：回到戰鬥之前的重試印出讀檔錯誤後結束（exit 1）、回到一格之前的重試中止（exit 134）；新開局路線的教學戰選回到戰鬥之前的重試，父提交與本組都是 exit 139、停在同一行。json 格式下，回到戰鬥之前的重試能回到那場戰鬥（之後能不能打完、回地圖沒有走），回到一格之前的重試畫面全黑。同一畫面的讀取與回標題正常。實測是人工條件：正常玩法很難輸，所以用遊戲資料夾的複本、只把複本裡敵方的數值調高；戰鬥、遊戲結束、重試與讀快照走的都是原本的腳本與移植版程式，但沒有用原版數值輸過。重試道具在讀回成功之後才扣，讀回失敗時還沒扣【讀程式（AIN 反組譯）；沒有實跑】。
   - **給玩家的注意事項**：戰鬥全滅後，遊戲結束畫面上方的兩個重試鈕（回到一格之前、回到戰鬥之前）不要選；選了並確認，程式會直接結束、沒有提示，上次存檔之後的進度會不見。下方的讀取與回標題正常，請改用讀取。
2. 快照沒有帶畫面需要的幾份資料（腳本另外存在區域陣列裡、讀回時要還原的幾份），json 讀回後地圖畫面出不來，載入後印出還原失敗的錯誤。
3. 系統訊息沒有實作，所以沒有開機續玩。
4. 命令列說明寫的預設快照格式是 json，實際是 rsm。
5. 一種附加檔寫到遊戲資料夾而不是存檔資料夾，各次執行共用。

引擎快照讀回的前期研究（唯讀、經獨立查核），還沒有實作：預設格式讀不回有三個互相獨立的原因——寫出端把結構編號無效的頁寫成空名，而讀入端沒有處理；同名的多載函式只寫名字，讀回時取到第一個；讀入後沒有重建空閒清單，清空堆積時留下已釋放的指標——另有兩個修好這三個之後才會遇到的缺口。讀回之後地圖出不來是另一個原因：快照旁邊要一起存的幾份資料沒有存。快照裡有大量一格的頁：是不是洩漏、和多場戰鬥後變慢有沒有關係，研究中。

## 驗收方式與結果

照既有判準：修前對照、預設與 GBK 兩組完整套件（143 模式）、九條路線（對 B1 提交後的趟，程式和父提交相同）、片頭三趟（相位判準與組層級），加上本組的結算實機、診斷版計數與舊版快照補查。判準與門檻都不改；片頭判準要對上的元件編號改成參數，見下。用語：片頭的**正式判準**指片頭相位判準（判定依據；組層級另看同組三趟的平均與標準差），**舊式判準**指固定影格比對（只作記錄）；**包裝腳本**是依序跑提交後各關卡的腳本；**帶編號行比對**見下面第一點。

**片頭判準的元件編號**：既有片頭相位判準寫死的片頭元件編號是 B1 之前的值；B1 之後片頭元件的編號變了，B1 提交後的基準趟用舊編號判也是無法判定，當時是靠追蹤趟的編號對映轉換後才判定通過。本組把這個編號做成判準工具（私人，沒有公開）的參數：預設值不變，時間窗、門檻、擬合、辨識與錨點行的選法都不動，另加「同一組各趟用的編號必須相同」；三趟明確傳入 B1 之後的值。依據是 B1 提交後正式判定的編號對映：這個編號的建立者就是片頭元件。**本組沒有追蹤趟，沿用是間接證據**：

- 本組三趟和 B1 提交後三趟，帶動態編號的行對齊比較（下稱帶編號行比對：把兩趟紀錄裡帶執行時配發的元件編號的行逐行對齊，看同一行的編號有沒有換）：只有游標取樣行不同、沒有同一行換編號，型態和同一支執行檔兩趟之間的自然差異相同；另一種比法（各編號第一次出現的順序、非取樣的帶編號行）結論一致：非取樣的帶編號行六趟兩兩相同，第一次出現的順序只有一趟少一個只出現在游標掃過時的取樣行的編號。
- 六趟錨點行的位置、種類與編號相同；那個編號在六趟都是第一次出現就在錨點那一行，片頭音訊開啟之前沒有出現過。
- 交叉驗證：B1 提交後三趟用參數直接判，和當時轉換後的結果逐值相同（狀態、擬合參數、錨點偏移、每張截圖的辨識）。負例（不帶參數、帶錯的編號、轉換後的副本帶新編號、組內混用編號）都是無法判定。
- 工具原有的自我測試所用的歷史基準趟原圖已不在，沒有跑；改用同樣定義的 28 個注入案，修改前後逐案一致。
- 提交後關卡再加一項收緊：傳非預設編號時，該編號在片頭音訊開啟那一行之前不得出現在紀錄裡，否則無法判定。收緊版已經獨立複審（PASS-WITH-NOTES，High 0、Medium 0、Low 1：命中這項檢查時，原本會判不通過的趟也變成無法判定，是設計上的取捨）。提交後的三趟以收緊版判定；收緊前的版本另外重判同三趟，狀態、擬合參數、錨點偏移與每張截圖的辨識逐值相同（只差版本字串與新增的檢查欄位）。
- 提交後的片頭判定：包裝腳本在只作記錄的舊式判準中斷（它的參考檔被誤刪，已重新產生並核對），正式判準直接執行。正式判準與組層級工具以相同的參數，對包裝內跑出的同三趟執行；編號的前置檢查三趟都做了、沒有命中。不帶編號時兩個版本都是無法判定（抽第一趟試）。對新趟重做的帶編號行比對（對 B1 提交後三趟與本組提交前三趟，共六組）同一行換編號 0、非取樣行的差異 0；錨點行九趟（B1 提交後、本組提交前、提交後各三趟）的位置關係、種類與編號相同。舊式判準的記錄在參考檔放回後補跑，只作記錄。

## 仍有差異與未涵蓋項目

- **原版實跑**：期望值都來自靜態反組譯，沒有一案在原版上跑過；本組沒有做原版實跑（理由見〈遊戲實機〉）。
- **舊版快照的續玩**：正常遊玩沒有入口，尚未實機驗證；快照讀回本身目前就不能用（既有缺陷）。
- **修補的範圍**：只修 struct 成員持有的一維、每元素至多一槽的泛型值頁；映像裡由區域、全域或陣列元素持有的同類頁不修。修補救不回舊版已經做過的事（被釋放的物件、被 struct 複製換掉的值、多出的參照）。
- **struct_type**：第 2 項建的新頁是 −1，新建的成員頁是列舉的型別編號；目前找到的使用端在 int 頁上都不讀它（沒有窮盡查過），日後若有人讀要注意。
- **沒有涵蓋的元素型別**：long int、第二種列舉代碼、函式型（本作沒有）。
- **沒有為列舉元素檢查過**：其他從宣告建陣列頁而沒用共用函式的地方（`A_ALLOC`、`A_REALLOC` 在內）。【讀程式】這兩個指令以 struct 成員的宣告型別建頁、不經共用函式，宣告為泛型的列舉陣列成員會得到泛型頁；本作腳本對這五個成員用不用到它們，沒有查。
- **泛型頁其他既有的問題照舊**：`X_A_SIZE` 以 struct 編號除元素數、介面成員頁沒有每元素槽數、Array 函式從空頁建頁時不管元素都給 int 頁。
- **method call 的自動配置**不變（原版在物件 −1 上是報 VM 錯誤）；這次它是把誤刪放大成畫面卡住的那一步，根因修好之後要不要拿掉，另案研究。
- **`heap_unref` 對參照數已歸零的槽靜默返回**不變。
- **還原時 struct 成員只建物件、不跑成員的建構子**是否符合原版，另案處理；本組的修正不依賴它。
- **連帶的行為改變**在本作走不走得到（上面八項裡除拆除之外的各項），沒有逐一查。
- **探針的界線**：表驅動的「非值型別成員逐欄位不變」只是一次性的跨建置比較；AE10 的「沒有成員指到的泛型頁」兩案沒有突變能讓它們失敗；參照型對照組只挑一個成員；新探針的檔頭沒有列沒涵蓋的範圍（最近兩組的探針有），以本頁與提交說明為準，之後改這個探針時補上。
