# 引擎快照讀不回時：告訴玩家並結束（R1c 提交一）

2026-11-22。程式提交 `3d31ef1`（2026-11-22）、父提交 `61985f2`（聲音停止型淡出那一組的文件提交；那一組程式 `6b42512`）；libsys4 固定 `247f544`（沒有動）。審查經過見 [review.md](review.md)；新模式的修前修後見 [before-after.tsv](before-after.tsv)，提交說明的逐句查證摘要見 [verify.tsv](verify.tsv)。程式推送的三方核對記在 [HANDOFF](../../HANDOFF.md)。

腳本以 `system.ResumeSave` 把整個 VM 寫成引擎快照，遊戲結束畫面的兩個重試鈕與回想的重播再以 `system.ResumeLoad` 讀回。R1a 讓 AIN v14 的快照讀得回來，R1b 讓讀回之後能接著玩；這一組處理**讀不回來的時候**：照原版告訴玩家哪個檔讀不到、然後結束，不再無聲結束、黑畫面卡住或當掉；寫快照失敗時照實回報、保住上一份完整的快照；壞掉的檔不讓程式卡住或越界讀。**讀不回時仍然不能接著玩**（原版大多數情形也是停止遊戲），這一組是安全網，不是讓讀不回的快照變得能用。

這是 R1c 的第一個提交，只改快照（VM 影像）的寫出與讀回；**部件影像那一側（讀入失敗時的防護）是下一個提交**，這一個沒有做。

用語：**快照**指 `system.ResumeSave`／`ResumeLoad` 寫讀的 VM 影像，預設格式是 rsm，另一種是 json。**讀回了**＝VM 換成快照裡的狀態、從存的地方接著跑；**不讀**＝VM 維持原狀、腳本在 `ResumeLoad` 之後接著跑；**讀不回**＝走失敗出口（訊息框、結束程式）。

## 問題與玩家看得到的差別

修前是上一個提交的引擎；「修後」的實機欄在提交前（`1db0a805`，見〈提交前實機〉）與提交後（程式提交上重建的 `d164cb79`，見〈提交後驗收〉）各跑過一次自動回答模式，兩次的結束碼與關鍵紀錄行相同；真的訊息框只在提交後量到。

## 原版怎麼做【靜態反組譯】

只讀這個移植跑的那一版（多娜多娜繁中版）的執行檔，用靜態工具讀位元組，**沒有執行原版**；其他版本沒有比。各條由前期研究與一位獨立查核者各自讀過，提交說明的兩位查證者又抽查了位址；和前期研究不一致的地方以查核者的更正為準。

- **`ResumeSave`**（`0x6727e0`）：把「影像有沒有寫成」寫進第三個引數（`0x6728d4`–`0x6728db`），不論成敗都推 1（`0x6728f0`）；這裡不開框。
- **`ResumeLoad`**（`0x672960`）：**不先查檔案在不在**，`0x67b990` 一開頭就是讀檔（`0x67cdf0`）。讀入失敗、而且錯誤不是「函式的檢查碼不符」那一種時，呼叫 `0x668d30`、不推回傳值（`0x672a4c` → `0x672a95`）。`0x668d30` 開一個寫出檔名的訊息框、清掉 VM 的執行旗標，所以腳本不會接著跑；VM 的某個欄位是 2 時（`0x668d5c`；那是什麼狀態沒有再往下讀）兩件事都不做。
- **函式的檢查碼不符**（`0x67c057` 設的錯誤碼）：改走 `system.Error` 用的那個框（`0x668e90`），之後原版可能回到腳本，或在玩家選擇結束時停止。
- **讀入順序**（把握中，細節沒有逐一確認）：檔頭、版本（必須是 14）、指令位址與返回紀錄都先讀進本地的緩衝，函式的檢查碼在這時比對（`0x67c03c`），所以檢查碼不符時 VM 還沒有被動；之後才寫指令位址、把運算堆疊複製進 VM，返回紀錄與另外三個本地表由 `0x6614c0` 套用（套用到哪裡沒有逐一確認）；最後才讀堆積（`0x678e80`，推論是堆積讀入）。讀回成功時重建空閒清單（`0x67a180`）再推 0。
- 原版自己寫的快照是第 14 版；移植版寫的是另一個版本（移植版自己的格式），兩邊互不相容。

## 移植版的做法【讀程式】

改的是 `src/resume.c`，配合 `src/vm.c`、`src/hll/system.c`、`include/vm.h`；引擎 4 個檔 +482／−50。libsys4 沒有改。

### 照原版的部分

- 讀不回——**包括檔案不存在**——就告訴玩家哪個檔讀不到、結束程式；不推回傳值，腳本不會接著跑。`system.ResumeLoad` 不再先查檔案。
- `system.ResumeSave` 一律回傳真，第三個引數寫 1 或 0。

### 三種結果與兩個入口

`vm_load_image` 的結果改成三種：**讀回了**（回傳真）、**不讀**（回傳假，VM 維持原狀）、**讀不回**（走失敗出口，不返回）。兩個入口都**只在讀回了才推回傳值**：

- `system.ResumeLoad`（CALLHLL；實際的讀入延到 CALLHLL 的處理器做）：讀回了推假；不讀時什麼都不推，腳本在 `ResumeLoad` 之後接著跑。
- v14 之前的程式用的系統呼叫入口（libsys4 的系統呼叫表上不回傳值）：讀回了推假（兩個字串引數跟著舊堆積一起消失）；不讀時照同檔其他系統呼叫的做法放掉兩個字串引數。
- 讀入改用 key 與檔名的副本：系統呼叫傳進來的是堆積字串的文字，讀入換掉堆積時會把它釋放。
- 讀寫快照註解的兩個函式遇到壞資料時，維持原本的 VM 錯誤（這款遊戲的腳本不呼叫它們）。

### 訊息框與結束（移植版自己的做法）

- 框只有一個按鈕，文字是移植版自己寫的（說續玩資料讀不到、遊戲即將關閉，寫出檔名），不抄原版的字串；語言跟關閉前的確認框相同（日文、繁體中文、簡體中文，其餘英文），標題是遊戲名稱。按下之後經 `vm_exit` 以結束碼 1 結束，和 `system.Exit` 走同一條結束路徑。
- 框**不像原版那樣看 VM 的狀態**：只要會問玩家就開框。自動回答模式（`XSYS4_AUTO_MSGBOX`）或沒有視窗時，文字只寫進紀錄；框開不出來時記一行警告；不論哪一種都會結束。
- 讀到一半、已經開始換掉堆積之後才失敗時，開框之前先丟掉讀到一半的堆積、呼叫框與運算堆疊（探針的替身在開框當下量到框、堆疊與存活的格數都是 0）。
- 函式的檢查碼不符也結束（原版走可以選擇繼續的那個框；移植版一律結束）。

### 外來格式的快照：不讀、接著跑（移植版自己的做法）

libsys4 讀不了的 rsm 版本——原版寫的第 14 版就是，例如從原版複製過來的存檔資料夾——**不讀**：印一行警告、VM 維持原狀、不推值，腳本在 `ResumeLoad` 之後接著跑。只有 libsys4 回報「格式不支援」時走這一條；其他失敗一律讀不回。

為什麼「檔案不存在」照原版結束、外來格式反而接著跑：外來格式只可能是另一次執行留下的檔。照這款遊戲腳本的讀法，從上次離開的地方續玩與快速讀取在沒有讀回時都會往下走（快速讀取會先查檔案在不在）；重試與回想讀的是同一次執行裡自己剛寫的檔，不會是外來格式。原版寫的兩份真檔（複本）離線讀過、其中一份另在實機開機試過，回報的確是「格式不支援」、走不讀那一支；「VM 維持原狀」在合成的檔上直接量到，原版真檔量的是程式庫的回報與讀入後的狀態。外來格式的檔**不會被刪**，每次開機與讀檔都會再碰到一次、各印一則警告。

### 寫入（移植版自己的做法）

- 先寫到 `<檔名>.xs4tmp`，寫完整才改名蓋過原檔，這時才算存好。失敗時留下的是**較舊但完整的同名快照**，之後的讀回會讀到那一份較舊的。改名前沒有呼叫 fsync：程式寫到一半當掉時可能留下暫存檔（下次寫入時蓋掉）；寫完改名後不久就斷電，同名檔可能是空的（讀程式，沒有量）。暫存檔的權限照 umask；原檔是符號連結時，換掉的是連結本身。Windows 照舊就地覆寫：失敗會算成失敗，但可能留下截斷的檔。存檔資料夾唯讀、但裡面的檔可寫時，修前就地覆寫會成功，修後建不了暫存檔、寫入失敗（同一個資料夾裡的其他幾種存檔本來就是先寫暫存檔再改名，修前在這種情形下也會失敗；實機修前修後各一趟量到）。
- rsm 的寫出端拒絕沒有呼叫框的影像（以前會對空的函式取值）與有一框沒有函式的影像（以前會跳過那一框），這時存檔失敗。
- 從 C 進入、不在最底下的框，rsm 寫成返回紀錄 −2、位移 −1，保留呼叫者的名字與檢查碼，讀回成「返回 C」。
- json：沒有字串的字串格寫成空字串（rsm 本來就這樣寫）。

### 讀入時的檢查與上限（移植版自己的做法）

目的只是不讓壞掉的檔當掉、卡住或越界讀，不是完整檢查內容。擋到的都走訊息框並結束。

- **呼叫框**：至少一框可以接著跑；返回紀錄的筆數和框數對得上；每一框都有函式（rsm 照名字找、檢查碼要相同；json 照編號、要在範圍內）；返回位址落在所屬函式起點之後的程式碼裡（終點不查）；指令位址落在指令上（json 只在 v14 查）。
- **框的頁**：每框的區域頁是活的頁，格數不少於該函式的變數數；**頁型別不查**，所以較早建置在那裡放了別種頁的快照照舊讀得回來。框的結構頁、區域頁裡記的結構指標只查是負數或小於堆積大小，不查是不是活的。
- **rsm 的頁與字串**：沒有負的格數；沒有長度 0 或以下的字串；全域頁、區域頁、結構頁的格數不少於變數或成員數（沒有格的結構頁照舊讀得回）；陣列的結構名不在 AIN 裡就拒絕；只有註解的檔拒絕。
- **堆積格數上限 1 << 24**：移植版自己設的，遠小於 VM 自己的保留範圍換算出的上限（只有一種配置模式下才有、約 2^31 格，照它等於沒有上限，一個壞掉的數字就能把記憶體吃光）。依據：這款遊戲用移植版近期各建置寫的快照最多 512K 格（近期一個實驗用的建置寫的），有洩漏的較早建置寫的最多 8M 格；VM 理論上寫得出比上限大的快照，但到那個量遊戲早就玩不下去。
- **json**：不認識的頁型別、負的堆積格號（以前讓讀入端無窮迴圈）、超出上限或重複的格號、少於兩個的運算堆疊值。
- 除了 json 的指令位址檢查，讀入時的檢查都不分 AIN 版本；**v14 之前的遊戲沒有實跑**。

### 程式庫（libsys4）不改

- rsm 的讀入改成自己分兩步呼叫程式庫的讀檔與解析（好資料上結果相同）。這兩步執行期間，把程式庫的錯誤處理掛鉤（**整個程式共用的那一個**）導向失敗出口；解析器放棄的影像，只釋放到它第一筆沒讀的堆積項目為止；讀回路徑因此避開了程式庫自己的釋放函式對空指標取值。
- 讀入端的錯誤訊息不再把共用的緩衝區交給錯誤常式。
- **擋不到的**：程式庫的解析器在呼叫錯誤處理之前就自己出事的壞資料（例如負的格數、負的字串長度，解析器會先寫出界），仍可能讓程式結束或當掉；要完全擋住得改子模組，這一組不改。讀寫快照註解的兩個函式沒有改成兩步呼叫，解析失敗時程式庫的釋放函式仍可能對空指標取值（這款遊戲的腳本不呼叫這兩個函式）。

## 驗證

### 探針【量測】

新模式 `resume-unreadable`（`probe/resume_unreadable_fixture.inc`，71 案），全套 158 → 159 模式。內容：從 C 進入的框在呼叫堆疊中間與最上面；經 CALLHLL 與系統呼叫存與讀回；寫不了的存檔（資料夾不可寫、寫到一半失敗、同名的是資料夾、寫出端拒絕的兩種形狀）；第 14 版的 rsm 經三種入口；上面每一項檢查各一個讀不回的檔（格式有差別的 rsm 與 json 各一）；兩個限制案（程式庫解析器自己先出界的資料）。訊息框經 `vm.c` 的測試替身，開框當下記下框的文字、呼叫框數、運算堆疊深度與存活的格數；每次讀入在另一個子行程裡跑、限時 20 秒，讀不回的案要求結束碼 1、有框而且框裡有檔名、紀錄有失敗原因、沒有重複釋放的警告、沒有 sanitizer 報告、讀入沒有返回。

## 已知的限制與沒涵蓋的

- **真的訊息框沒有人在現場操作過**：框、框裡的檔名與按下確定之後的結束，是提交後三趟的自動截圖、程式透過無障礙介面按下確定、結束碼與紀錄確認的；沒有人用眼睛看或用滑鼠點過。提交前不設自動回答的四趟（三種情形，螢幕鎖定）只量到框的視窗有出現。
- **程式庫內部擋不到的壞資料**：子模組的解析器在呼叫錯誤處理之前就自己出事的資料（例如負的格數、負的字串長度），移植版這一端擋不到；壞到那種程度的檔仍可能讓程式結束或當掉。讀寫快照註解的兩個函式沒有改成兩步呼叫，解析失敗時程式庫的釋放函式仍可能對空指標取值（這款遊戲的腳本不呼叫這兩個函式）。
- **框頁檢查擋不住的形狀**：區域頁是格數夠多的別種頁、或別的函式的區域頁（返回時照頁型別與索引釋放，可能洩漏或放錯別的格）；全域頁那一格放了別種頁，完全沒有檢查。
- **不支援往回相容**：這個提交之前的建置讀到含新的「從 C 進入」返回紀錄的快照，會算錯返回位址（既有實機紀錄的 110 份快照裡沒有這種框）。
- **寫入**：改名前沒有呼叫 fsync（當掉可能留下暫存檔，改名後不久斷電時同名檔可能是空的）；寫入失敗時之後的讀回會讀到較舊的同名快照，一份都沒有時走訊息框結束（讀程式）；**存檔資料夾唯讀、但裡面的檔可寫時，修前就地覆寫會成功，修後寫入失敗**（同一個資料夾裡的其他幾種存檔修前就已經如此）——這是這個提交造成的已知差異，修正（暫存檔建不起來時退回就地覆寫、在紀錄註明、補探針案）排在下一個提交；只有資料夾唯讀、資料夾裡又留著原版寫的同名快照時，寫入失敗之後讀回的是那一份，照上面的規則不讀、腳本接著跑、不跳框（讀程式，沒有驗；條件罕見）；Windows 是就地覆寫、可能留下截斷的檔。
- **玩家看不到的提示**：腳本的「存檔失敗」提示與錯誤回報在移植版目前只寫進紀錄（之後把腳本的錯誤回報做成對話框的那一組處理）；外來格式的續玩檔不會被刪，每次開機與讀檔各一則警告。
- **測試的限制**：系統呼叫入口「讀回了」那一支如果之後被改成也放掉兩個字串，沒有案能抓到（這款遊戲走不到這一支；留給之後處理 v14 之前遊戲相容性的工作）；突變有一列的後半預測沒有直接觀察到；子行程的 sanitizer 報告只計前 40 行；探針沒有初始化各模組，**失敗收尾時各模組的收尾函式做了什麼只有讀程式的結論**（實機的強迫失敗趟走過這條收尾、沒有當機，但沒有逐一檢查）；格數上限的依據是近期一個實驗用的建置與較早有洩漏的建置寫的樣本；6 份較早樣本的寫出建置已重新認定（見上）；提交前的視窗驗收與實機趟用的是另一支執行檔，和提交的程式碼等價、只差版本字串與路徑字串，不是用提交後的執行檔跑的；提交後各趟的顯示狀態不一致（大多在螢幕沒鎖時跑，基準都在鎖定時跑）；重試與回想的九個專項是提交之後才跑的；升級情境那一趟沒有讀到任何引擎快照，新版讀舊建置寫的快照只有離線讀回的證據。

重試或回想用的資料（引擎快照）讀不回來時（檔案不見了、被截斷或內容壞了），遊戲現在會跳出訊息框，寫出是哪一個檔讀不到、說明遊戲要關閉，按確定後遊戲就關閉，不再黑畫面卡住或沒說一聲就關掉；壞到某些程度的檔仍可能讓遊戲直接關掉或當掉。那一次不能接著玩（照對原版程式的靜態讀法，原版大多數情形也是停止遊戲），重要的進度請另外存檔。存檔資料夾裡有原版留下的續玩檔時，現在可以正常開機到標題（那個檔不會被讀，也不會被刪）。這個訊息框由自動測試的截圖確認過（框與框裡的檔名都看得到），也由測試程式按下確定、確認遊戲接著關閉；沒有人在現場用眼睛看過或用滑鼠點過。已知差異：只有存檔資料夾本身設成唯讀、裡面的檔可以寫時，以前快照照樣寫得進去，現在寫不進去（照程式的設計，之後按重試會回到更早存好的那一份，一份都沒有時跳出這個框並關閉，這兩件沒有實機試過；遊戲目前不會為存檔失敗跳提示；修正排在下一個提交）。看到這個框，請回報框裡的檔名與當時在做什麼。
