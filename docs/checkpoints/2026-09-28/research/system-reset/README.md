# `system.Reset`：重啟 VM（讀檔、返回標題、Game Over）

2026-10-12。程式 `6267ed3`（基底 `cd46ec3`）。

這一步讓 `system.Reset` 真的把 VM 重新啟動：存檔讀得回來，設定頁的「返回標題畫面」回得到標題，重啟後的標題可以再開新遊戲或讀檔。同時把重啟會留下的東西清掉（VM 的計數、v14 的舊堆、PartsEngine、HashMap、劇情回顧），並修掉這條路上暴露出來的兩個既有問題（主 EX 檔每重啟一次就重讀、丟一份；讀取畫面上 `parts_cg_set` 的越界讀）。存檔的格式是先前的 [save-persistence](../save-persistence/README.md)，已讀表在重啟時寫檔是 [msgskip-msk](../msgskip-msk/README.md)。**沒有做**：返回標題的確認框（`system.MsgBoxOkCancel` 仍固定回「確定」）、存檔縮圖、原版重啟時另外寫的設定檔、`ResumeLoad` 那條路（回想、Reload、中斷恢復）與它用的元件存檔、`system.Exit`、SealEngine 的狀態。**Game Over 沒有實機。** 重啟點和 v13 以前程式的 `SYS_RESET` 共用，那些程式一款都沒有實跑。

## 症狀

修改前：

- 存檔寫得出來，但從來讀不回來；設定頁的「返回標題畫面」按下去就卡住。每次都得從新遊戲開始。
- 腳本在讀檔、返回標題、Game Over 三個地方呼叫 `system.Reset`，之後的事全交給重啟。返回標題那一處，呼叫後面就是一個只呼叫 `system.Peek` 的迴圈，沒有離開條件；另外兩處後面是 `RETURN`。
- 修改前的實機紀錄只有返回標題（[msgskip-msk](../msgskip-msk/README.md) 那一步：點擊命中、已讀表寫出、空殼的警告，之後不動）。讀檔在 GUI 上沒有走過，Game Over 沒有走到；這兩處的依據是探針的修前失敗（重啟沒有發生，後面的指令被執行）。

## 根因

`system_Reset` 是空殼：只做了原版重啟的第一步（寫已讀表）並印一行警告，沒有接到既有的 `vm_reset()`。接上之後還有四件事讓重啟走不遠；`vm_reset()` 以 `longjmp` 離開，而這條路在這棵樹上沒有被走過：

- **執行深度不歸零。** `vm_execute_depth` 在最外層永遠不返回，每重啟一次至少多 1，超過 10 之後 `vm_execute` 直接返回。實機把歸零拿掉，第 3 次重啟之後 VM 就不再執行（重啟當下 C 堆疊上不只一層）。舊程式的 `SYS_RESET` 也經過這裡。
- **舊堆整個漏掉。** 全域頁所在的格子收尾時不釋放，重入的 `heap_init` 直接把整張表清 0，還活著的頁與字串沒有人釋放。
- **函式庫的殘留。** PartsEngine 在 v14 的訊息佇列、activity 表與元件號碼的起點、motion；HashMap 的 64 個 handle；劇情回顧的緩衝。重啟不跑腳本的解構子，沒有人歸還。
- **主 EX 檔每次重讀。** 它的收尾刻意不釋放（釋放會當），只把指標清掉；重啟時再讀一次，舊的那一份就丟了。

腳本（兩邊跑同一份）：

- **一般的讀檔不用 `ResumeLoad`。** `ResetLoadManager::Run` 把目標的編號與種類用 `SystemService.GameVariable_Set` 寫下，呼叫 `system.Reset`。重啟後主流程一開始呼叫 `ResetLoadManager::LoadObject`：鍵不存在就開標題；存在就讀出、清掉兩個鍵、載入那個存檔（`system.DeserializeStruct`），再依存檔裡的階段重開場景。讀檔後的畫面全部由腳本重建，不經過元件存檔。
- `system.Reset` 的呼叫只有三處：設定頁「返回標題畫面」的處理（設定要求確認時先 `system.MsgBoxOkCancel`，回 0 就不重啟；之後存設定與備份，再 Reset）、`ResetLoadManager::Run`、Game Over 場景（確認框、音樂淡出之後）。返回標題與 Game Over 重啟之後鍵不存在，所以開標題；`IsResetOnce` 為真時跳過商標。
- 返回標題的那個函式另有兩個呼叫者（審查查到的）：`gamesave::detail::PrepareReload`（先存一個檔，成功才呼叫；它的呼叫者是 `AFL_Debug_Reload` 與 `_system::detail::ProcessSystemMessage` 的一個分支）與一個劇情控制函式。
- `ResumeSave`／`ResumeLoad` 是另一條路（地圖與戰鬥的快照、回想、Reload），元件存檔用在那裡。這一步沒有動。

## 做法

`src/hll/system.c`、`src/vm.c`、`src/heap.c`、`src/page.c`、`src/hll/PartsEngine.c`、`src/parts/parts.c`、`src/parts/motion.c`、`src/hll/pe_v14_message.c`、`src/hll/pe_v14_activity.c`、`src/hll/HashMap.c`、`src/hll/AnteaterADVEngine.c`、`src/hll/MainEXFile.c` 與幾個標頭；`src/audio.c`、`src/hll/KiwiSoundEngine.c` 只加追蹤（`XSYS4_STAGE2_TRACE` 開啟時才記）。

- **`system.Reset` 只設旗標**（先照舊寫已讀表）；`CALLHLL` 的處理在那一次呼叫返回之後看到旗標，才經既有的 `vm_reset()`（`vm_free()` 加 `longjmp`）重啟。不在函式庫呼叫裡 `longjmp`：VM 會在呼叫者腳下被拆掉（反向檢查這樣改，sanitizer 有報告）。只經 ffi 呼叫、不是 `CALLHLL` 指令時只設旗標。
- **重啟點把 `longjmp` 留下的東西歸零**（新的 `vm_reset_runtime_state()`，`vm_execute_ain` 在 `setjmp` 之後呼叫）：堆疊與呼叫深度、執行深度、指令上限、配置階段的旗標、CASTimer 的表與 handle、訊息行；堆這一邊是延後釋放的佇列、擋住回收的計數、掃描上限與 `page.c` 的四個深度。第一次啟動時它們本來就是這些值。函式旗標表只跟程式有關，已經配置就不重配。
- **v14 把舊堆上還活著的頁與字串直接釋放，不跑解構子**；v13 以前照舊只清表，舊的不釋放。
- **PartsEngine 的收尾**（v14）在 `PE_Reset()` 之後再清：根位置、訊息視窗的顯示旗標、空號碼的起點、上次更新的時刻、motion、v14 的訊息佇列、activity 表與它的元件號碼起點、更新中的旗標。
- **HashMap 多一個收尾函式**，歸還全部 handle。**劇情回顧**（`AnteaterADVLogList`）的緩衝在 v14 隨重啟清掉，記錄開關設回開啟；v13 以前照舊保留。
- **`MainEXFile` 跨重啟保留已經載入的檔**：收尾不再清指標，啟動時已經有就不重讀。`AddEX` 或 `AddEXReader` 追加過的話照舊放掉、連同查找的快取，下一次啟動重讀，追加的內容不會每重啟一次多一份。所有用這個函式庫的程式都生效。
- **`parts_cg_set`** 比對 `<save>` 前綴用的是 `memcmp`，名稱比前綴短時讀過頭；改成 `strncmp`，結果相同。讀取畫面會設這種名稱。這是上游既有的一行，所有程式都生效。
- **音訊沒有補程式**：重啟時 `audio_reset()` 本來就會被呼叫（ChipmunkSpriteEngine 與 PartsEngine 的收尾都走到 `sact_ModuleFini()`，所以是兩次），兩個頻道池裡的頻道全部關掉，空的 ID 回到剛啟動的值。`KiwiSoundEngine` 自己沒有收尾函式；一個只宣告它的 v14 程式不會重置音訊，這種程式存不存在沒有查。
- GameVariable 不用動：它本來就是 C 的靜態陣列，`vm_reset()` 不碰；`IsResetOnce` 回的旗標由 `vm_free()` 設。

刻意和原版不同的地方：

1. **離開的方式**：原版清掉旗標後就地等宿主收走 VM；這裡在同一條指令裡、呼叫返回之後 `longjmp` 出去。兩邊都不再執行腳本的下一條指令（函式庫呼叫在 VM 裡只有一個進入點）。巢狀的腳本呼叫裡重啟，這裡不論多深都直接離開。
2. **重建的範圍**：原版釋放 VM 與所有引擎再重建；這裡只做 `vm_free()` 與各函式庫的收尾，視窗、封存檔、字型、音訊裝置、AIN、主 EX 檔都留著。
3. **不跑解構子是推論**：原版 VM 解構時跑不跑沒有追，依據是指令函式的那個閘門。
4. **混音器各群組的音量與靜音不回預設**（音訊的初始化只做一次）；原版把音訊引擎物件釋放再重建。腳本重啟後會不會每次重設音量沒有查。
5. SystemVariable、亂數的狀態跨重啟保留；原版怎麼處理沒有查。
6. 已讀表寫兩次：`system.Reset` 一次、函式庫收尾一次，內容相同；原版一次。

## 驗證

- 探針（各案內容見 [harness](../../harness/README.md)）：新模式 `system-reset` 12 案，每案一個子行程。SR1 用遊戲自己的三個呼叫點，從那一條 `CALLHLL` 執行，後面的 `RETURN`／`Peek` 不能跑到；SR2 GameVariable 與 `IsResetOnce` 跨重啟；SR3 連續十二次，計數每次歸零；SR4 v14 釋放舊堆、v13 不動；SR5、SR6 PartsEngine 與 HashMap；SR7 只經 ffi 呼叫時只設旗標；SR8 主 EX 檔；SR9 短的 CG 名稱；SR10 劇情回顧；SR11 循環中與淡出中的聲音；SR12 重啟會跑到各函式庫的收尾。探針不走 `vm_execute_ain`，自己站在重啟點上呼叫歸零函式；「`vm_execute_ain` 真的呼叫它」只有實機守。

## 與原版的對照

原版是 Wine 上的專用副本，暫時改用一個空的存檔資料夾，在那裡開新遊戲（真實存檔沒有被開啟，前後的雜湊相同）。兩邊走同一串操作，同一個行程重啟三次；原版每秒截一張圖，沒有錄影。並排十二對，實作者逐對確認是同一個畫面、同一個狀態；圖不放進 repo。這是審查修正之前的版本做的；修正不動畫面，同一條路線的數字逐項相同，沒有重做。

## 獨立審查

提交前，兩個面向（原版語義與腳本流程；重啟的安全性、殘留與回歸），審查者與實作者不同；一個發現另由一位驗證者試著反駁。審查與驗證都是靜態閱讀，沒有建置、執行或開 Wine。沒有 High；沒有找到會當機、重複釋放、釋放後使用或把存檔寫壞的問題。

- **劇情回顧的緩衝跨重啟保留**（Medium，已修）：腳本只有讀檔時才自己清回顧，返回標題或 Game Over 之後開新遊戲，回顧裡還有上一輪的對白，之後存檔很可能也帶著；原版重啟時釋放回顧物件。只有靜態證據。處置：v14 的收尾清空緩衝，探針 SR10，實機補一條。
- **音訊有沒有重置**（Medium，兩位審查者的說法相反）：一位指出 `KiwiSoundEngine` 沒有收尾函式、`audio_reset()` 全樹只有一處呼叫；另一位指出 `PE_Reset` 會經 `sact_ModuleFini()` 走到它。查證後是有重置（前一位的每一句單獨看都對，漏了那個收尾會被別的函式庫呼叫），沒有補程式，加了追蹤與守衛探針 SR11。
- **返回標題沒有確認框**（Medium，驗證後降為 Low，留著沒做）：事實屬實，但「丟進度是這次修改造成的」不成立——`system.MsgBoxOkCancel` 在基底就固定回「確定」，修改前按同一顆按鈕同樣不問，然後卡死、只能強制關閉。
- Low，都在提交前處理：`MainEXFile` 保留的理由原本寫成「沒有東西會寫它的表」，但 `AddEX`／`AddEXReader` 會追加（加了旗標；零售流程不呼叫這兩個函式是審查的盤點，沒有重查）；三處註解把沒有證實的原版行為寫成事實（改成照查到的寫）；探針有幾案驗的範圍比案名窄（SR5 補兩個斷言、SR8 改成查存在的表、新增 SR12）；實作筆記漏了上面那兩條會走到 `system.Reset` 的路。
- 審查者以反組譯獨立確認了 `system.Reset` 的處理函式、指令函式的閘門、宿主迴圈的重啟段，並把「GameVariable 的儲存在宿主物件裡」從推論補成有依據。也更正了一個說法：`system` 函式庫不是上游的，所以共用的重啟點對舊程式是新行為，不是「不受影響」。

## 與原版的差異與限制

與原版還不同的：

- 上面「刻意不同」的六點。
- **存檔縮圖沒有**：讀取清單每列左邊是一塊灰（`PartsEngine.SaveThumbnail` 是空殼，不寫縮圖檔）。
- **設定頁的「返回標題畫面」不問確認**：`system.MsgBoxOkCancel` 固定回「確定」，按一下就重啟，沒有存檔的進度丟掉；原版預設會跳確定／取消的系統對話框。修改前按這顆按鈕是卡死。之後要把它做成真的對話框（自動路線不能被它卡住；同一個空殼也影響「結束遊戲」等呼叫點）。
- 重啟時原版另外寫出四個設定檔（`CommonSystemData.sav`、`MouseCursorSetting.sav`、`ShowDPSetting.sav`、`Volume.sav`），這裡沒有。是重啟本身寫的還是腳本在那前後呼叫的，沒有查。
- 讀檔的黑畫面原版約 5 秒、這裡約 3 秒；返回標題原版在設定頁多停約 2 秒。原版跑在 Wine 上，差在哪裡沒有分析。
- 讀取確認框出現時被點那一列的底色（原版保持粉紅）。屬輸入作用域切換時底下元件的懸停外觀，這一步沒有處理。

沒有驗證的：

- **只在 Day 1 據點、設定頁、讀取畫面重啟過。** 第 2 天以後或有戰鬥進度的存檔，戰鬥、地城、春銷、對話中途的重啟，都沒有實機。
- **Game Over 沒有實機**，兩邊都沒有走到。只有靜態：它是同一個 `CALLHLL system.Reset`，探針 SR1 用那個函式裡的那一條指令跑過；Reset 之前的畫面沒有看過。
- 剛啟動程式、帶著既有存檔直接從標題讀檔沒有跑；實機的「從標題讀檔」是同一個行程返回標題之後的標題。
- 另外兩條會走到 `system.Reset` 的路（`PrepareReload`、那個劇情控制函式）沒有分析也沒有實機。修改前它們卡在 `Peek` 迴圈，現在會真的重啟；`PrepareReload` 重啟後怎麼把那個檔讀回來（若靠 `ResumeLoad`，是沒做的那條路）、是什麼操作觸發的、另一條是哪一段劇情，都沒有查。
- 循環音效正在播的那一瞬間重啟，實機沒有碰到（那條路上腳本在進設定頁時就自己把它淡出停掉了），只有探針 SR11。
- **v13 以前的程式一款都沒有實跑。** `system` 函式庫是這個分支自己加的，上游沒有；舊程式走 `SYS_RESET` 與 `vmSystem.Reset`，那兩個入口沒有動，但之後的重啟點是共用的：計數的歸零、函式旗標表不重配、主 EX 檔的保留、HashMap 的收尾，對它們都是新行為。依據只有讀程式（判斷是回到初值）與探針 SR4 的一個 v13 守衛；回顧緩衝那個「v14 才清」的條件也沒有用 v13 的程式跑過。
- **SealEngine 的狀態沒有處理**：它沒有收尾函式，而所有實機路線都沒有初始化過它，釋放的路徑沒有辦法驗證。有畫面用到 3D 的話，在那裡重啟可能留下舊的實例。
- 在建構子、解構子或元件更新裡重啟才用得到的三處歸零沒有守衛；巢狀的腳本呼叫裡重啟沒有探針。探針也不跑重啟後函式庫重新啟動的那一側。
- 確認框的「取消」與「以後不再顯示」、刪除存檔的按鈕沒有點。重啟後新遊戲的存檔裡有沒有上一輪的回顧沒有量（緩衝是空的，推論不會）。
- 不重啟的十條路線只比了對白、點擊目標與錯誤行，畫面只抽看了一張八格拼貼。
- 原版沒有讀的部分見「原版依據」各列；另外 SystemVariable、亂數的狀態在重啟時怎麼處理，那四個設定檔是誰寫的。
