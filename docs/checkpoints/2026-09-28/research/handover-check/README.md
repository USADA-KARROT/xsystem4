# 前五組的獨立查證與後續修正

2026-10-11。查證的對象是前一手推送的五組：G15 struct 陣列（`3ab99a1`）、G16 背景構築（`8787a31`）、音訊初始化（`70c7ed6`）、浮點左上角座標（`298d6ce`）、純量陣列（`f6b6c0f`）。查證之後的修正是 `c40182c`（一起推送的四個 commit 的第一個）。

## 做法

接手時對這五組各做一輪獨立的唯讀查證，對照每一組修正應該有的六項證據；判為中等級以上的發現，再由另一個查證者試著反駁（對抗驗證）。查證者沒有建置或執行任何東西：原版依據是自己重新反組譯核對的，探針、verify 與實機的結果取自既有的紀錄並重算（例如對白的雜湊），並排圖自己打開看。

六項證據：(1) 原版依據（靜態反組譯的位址與內容相符）；(2) 新探針在修正前失敗；(3) 預設與 GBK 兩組 verify 全過；(4) 實機路線沒有錯誤，對白的行數與雜湊和基準相同；(5) 與 Wine 上的原版同一畫面並排；(6) 獨立審查，High／Medium 都處理了。

## `c40182c` 修了什麼

### 左上角座標 getter 的元件查找

| 項目 | 位址 | 內容 |
| --- | --- | --- |
| 三個 getter | `0x58bf80`／`0x58c020`／`0x58c0e0`，在 `0x58bfb4`、`0x58c054`、`0x58c114` 呼叫 `0x540250` | 查找之後才判斷有沒有元件；沒有時組合版不寫輸出，X／Y 回 0.0 |
| 查找 | `0x540250` → `0x56d450` → `0x53d920` → `0x53a0b0` → `0x539c80`、`0x578ee0` | **取得或建立**：只有號碼小於等於 0 回空（`0x539cb0`）；否則格子是空的（`0x578f07`）就由 `0x578cb0` 建立預設元件。`0x540250` 有 142 個呼叫來源，寫入類的函式也用它 |
| 只找不建立的另一條 | `0x540280` | 全檔只有兩個呼叫來源，getter 不在其中 |
| 狀態 | `0x534bb0`（`0x534be8`）；低等級部件 `0x564d30` → `0x5b7cb0`／`0x5b7d20`；狀態格建於 `0x5b730c` | 狀態不加檢查地交給內容物；低等級部件以它直接索引 4 個狀態格（0..3），沒有邊界檢查 |

`298d6ce` 用的是不建立的查找，並把那當成原版行為。現在：號碼小於等於 0 不建立、不寫；其餘照原版取得或建立，新元件回報 (0,0)；查找先於狀態的檢查，所以狀態不合時元件仍會被建立。「原版的新元件也回報 (0,0)」是推論：讀到它的變換是單位矩陣、沒有內容時尺寸是 0，但沒有讀投影那一段。只在 v14 而且宣告形狀相符時生效，舊的整數函式沒有動。

狀態 4（腳本列舉的 Disable）：查證意見是「合法的值卻被當成非法」。往下讀的結果是它在原版的這條路徑上會讀到狀態格之後的成員，不是有定義的行為；所以沒有改成會寫輸出，只把程式註解、探針與文件的說法改正確：狀態不在 1..3 時不寫輸出是這個移植三個狀態的界線，不是原版規則。

探針 `parts-upper-left` 的 UL4 原本把相反的行為鎖死，改寫成：大於 0 的缺件由三個 getter 各自建立並回報 (0,0)；0 與負數不建立、不改輸出；狀態 0 與 4 不寫輸出但元件仍被建立。

### struct 陣列縮短時，解構子在尾端新增元素

原版縮短的 `Realloc` 只讀一次長度（`0x67f504`），以舊索引由後往前釋放原本的元素（`0x67f554`–`0x67f570`），然後只改大小（`0x67f572`–`0x67f57f` → `0x41a430`，它沒有任何釋放元素的呼叫）；`Alloc` 的清空同樣只讀一次長度（`0x67ec60`），結束時把長度歸零（`0x67ec7d`）再重建。所以解構子在尾端新增的元素會被截掉，既不解構也不釋放，物件就此遺失；陣列結束在要求的長度。

`3ab99a1` 在這種情況留下夾著 −1 的過長陣列。現在照原版：陣列換成要求長度的新頁，多出來的格子丟掉，不釋放、不解構（原版也有的洩漏）。另一種情形——解構子在舊的索引範圍內放了新元素（內層重建、替換）——維持既有的契約「內層的變更優先、外層停止」，但停止前把外層已經清空的格子移除，不留 −1；這一條是這個移植自己的界線，沒有原版可對。

探針 `array-construct` 新增 AC15（五輪：`EmplaceBack`、`Alloc`、另外 `Erase` 的移植界線、`PushBack`、兩個解構子各新增兩個），用遊戲裡一個真的結構與它的解構子執行，新增的動作由探針插在解構子的開頭。遊戲沒有這種呼叫點（腳本 153 個解構子裡直接呼叫的陣列函式只有 4 次 `Free`）。

### enum 陣列

沒有程式修改。`GameContext` 的建構子先跑初始化器，`X_A_INIT` 把 enum 元素與 int、bool 一樣建成具體的 int 頁，隨後的 `Alloc` 走的就是 `f6b6c0f` 的新路徑；原版 enum 的初值與釋放和 int 相同（`0x6569a9`、`0x656c50`）。探針 `array-primitive` 新增 AP8：以真的建構子建出陣列，確認頁的型別與個數，再確認重新 `Alloc` 時不把值當成物件釋放（後面這幾輪是合成的呼叫，遊戲不會對這個陣列再 `Alloc`）。

### 驗證

- 正式 before-check（[before／after](before-after.txt)）：`51e6bd8` 的 src／include 上，`parts-upper-left` 6 案中 1 案失敗（UL4）、`array-construct` 15 案中 1 案失敗（AC15，五輪都失敗）、`array-primitive` 8 案中 0 案失敗；兩種字元規則結果相同，sanitizer 0。AP8 在 `51e6bd8` 通過是預期的：它守的是 `f6b6c0f` 已經修好的行為。實作時把 `Array.c` 換回 `f6b6c0f` 的前一個提交重跑，8 案中 6 案失敗（含 AP8），這一筆不是正式的 before-check。
- 反向檢查：六處刻意改壞（查找改回不建立、拿掉號碼的守衛、狀態檢查移到查找之前、把被截掉的元素釋放掉、不移除空格、不截到要求的長度），每一處都有案例失敗。
- 這個 commit 提交前預設與 GBK 各 91 模式 PASS；四個 commit 之後各 92 模式 PASS、sanitizer 0（摘要在[已讀表](../msgskip-msk/verify-default.txt)那一組）。
- 實機：實作時 `haruuri`、`fightr`、`normal150`、`sysmenu` 與一條自訂的春銷準備路線，修正前後對白的行數與雜湊相同、沒有錯誤；顧客離場到三家店的位置修正前後相同，第一家店與原版同一階段一致。四個 commit 之後的十條路線見[已讀表](../msgskip-msk/gui-summary.json)那一組的摘要。
- **「取得或建立」只有探針驗到**：實作時以暫時加了紀錄的建置跑春銷路線，getter 只讀到已經存在的元件，建立缺件 0 次。陣列的重入分支遊戲走不到，同樣只有探針。

### 這一組自己的審查

一輪兩個面向（左上角座標、陣列），中等級以上另有對抗驗證。沒有 High。

- 成立的 Medium 一件：第一版讓陣列把被截掉的元素釋放掉。那與原版相反，不是安全措施，還多出一個原版沒有的腳本回呼；被釋放的元素的解構子若再新增，陣列又不會結束在要求的長度。已改成照原版只丟格子，探針的斷言與反向檢查一起改。
- 降為 Low 的一件：給音訊文件的更正文字把上游的呼叫點寫成「只在一處」，實際有四處；寫進文件之前已改。
- 其餘 Low：AC15 補 `PushBack` 與多個新增的兩輪，並標明哪些斷言是原版語義、哪些是移植的界線；AP8 補個數的斷言；文件更正文字的三處出入；裁切區域與量表那兩組有同一類「未知元件不建立」的敘述（另案，見下）。

## 沒有修而記下的

- **音訊沒有人聽過。** 「有非零的 PCM」是在引擎的回呼裡、混音之後量的，只能證明裝置開成功、回呼以實時速率被拉取、BGM 解出有能量的訊號；不能證明揚聲器有聲、選曲／音量／淡化／循環與原版相同，也沒有看到音效與語音（觀測的 90 秒裡只有四首 BGM）。
- 音訊的疑點（從既有紀錄看到的，原版怎麼做沒有對照）：切曲四次都在同一個頻道上準備，對另一個頻道的停止每次失敗；據點那一次下達 2000 毫秒的淡出，約 100 毫秒後就在同一個頻道換曲，等同硬切；88 個觀測區間裡 37 個的峰值正好頂到混音器的上限（有沒有削波沒有查，原版的預設音量也沒有比對）；BGM 與音效沒有資料時都落在同一個混音群組，設定畫面各音量是否各自生效沒有驗。
- 音訊修好之後才第一次會變的狀態：播放結束、淡出完成（修正前回呼從不執行，「播放中」恆為真）。腳本有 11 處依「是否播放中」分支，包含自動模式的逾時、語音時壓低 BGM、音效佇列；驗收的路線都是快進，沒有碰到。背景執行緒的存取錯誤會被既有的訊號處理函式靜默放過，混音現在在背景執行緒，那種錯誤會變成凍結而不是當機紀錄。
- 無人值守的實機測試現在會真的從機器的揚聲器出聲。
- **左上角座標影響到、沒有驗證的畫面**：顧客效果提示的位置、人材一覽與隊伍成員的立繪拖曳、鑑賞模式的音樂列表與縮圖頁的換頁、立繪細節的載入與卸掉、縮圖的點擊位置。只有讀腳本的推論（方向是變對），沒有實機或原版畫面；清單在 [upper-left](../upper-left/README.md)。第二、三家店的顧客離場沒有原版對照。
- G16：擄人環節的橫幅在修正後沒有重拍；設定第 2–7 頁、附錄、GameOver、派遣結果、商店的背景只有探針驗過；第 10 版（現在是第 11 版）的存讀檔沒有實機。
- G15：每幀的成本沒有量測（紀錄裡春銷路線的腳本指令數增加，含原版也有的路人更新）；反覆進出春銷後事件與計時器是否回到基準沒有驗；`Free`、`Erase` 等其他陣列函式在元素解構子重入同一個陣列時是否安全，不在範圍內。
- 結構成員是 enum 陣列時，`src/page.c` 的 `init_struct_slot` 不把它建成 int 頁（`X_A_INIT` 與存讀檔都會）。沒跑過初始化器的物件因此留著 generic 頁，那種頁存了 enum 值之後，銷毀、複製與舊路徑的縮短會把值當成物件參照。另有四個結構有 enum 陣列成員，有沒有不經初始化器建立的路徑沒有查。
- **「元件不存在時是取得或建立」要一次盤點**：這個錯誤在好幾組出現（左上角座標與面板已修）。裁切區域與量表那兩組的研究文件、探針與實作仍寫著未知元件不建立；裁切區域的三個原版函式已看到是呼叫取得或建立的那個查找，量表沒有查。原版以 `0x540250`（與面板的 `0x53e290`）→ `0x53d920` 取元件的是取得或建立，`0x540280`、`0x53d950` 才是只取得。
