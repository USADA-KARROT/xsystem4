## 缺陷（修前）

- **三個命令不加操作**【讀】。v14 的 `PartsEngine.AddPartsConstructionProcess` 對 103、107、121 走 default 分支：印 unknown type 的警告，不加任何操作，後面的命令照做。
- **根據地的位置列畫不完整**【量】。實機（使用者存檔的複本，第 8 天）：成員的狀態畫面與人材的操作畫面一打開，下方中央出現「第幾個人」的位置列約 2 秒（換人時再出現）。修前只有一塊半透明的黑長方形，**缺兩端的半圓（121）、每個位置的圓點（107）與目前位置上的黃色游標（103）**。那塊長方形是命令 6 填的中間部分；游標的元件是 12×12 的透明面，什麼都看不到。
- **警告**【量】。每建一次位置列印 8 次 unknown type（103 一次、121 兩次、107 五次）。使用者紀錄的 10 次就是第一次建的 8 次加第二次的前 2 次；命令的參數（矩形、顏色、角度）和下面〈腳本端〉從 AIN 讀到的完全相同。

## 原版依據

### 反組譯看到的【反】

- **派送**：構築的執行器（`0x4fa1d0`）在 `0x4fa36c` 以命令號索引跳表 `0x4fb7d8`（上限 0x84）。每一項呼叫 handler，回 0 時這一步失敗，`0x4fb675` 設旗標，之後的步驟都跳過。103 → `0x507790`、107 → `0x507f80`、121 → `0x5092a0`。handler 自己的錯誤訊息把它們叫做 `円塗りつぶし：矩形指定（アルファのみ）`、`円塗りつぶし：矩形指定（アルファブレンド）`、`扇形塗りつぶし：矩形指定（ピクセル＆アルファ）`。
- **參數的位置**：`AddPartsConstructionProcess`（case 840 → `0x59a730`）把 ArrayInt 複製成一個步驟：[6] [7] → 先矩形 X、Y（+0x1c、+0x20），[10] [11] → W、H（+0x2c、+0x30），[12..15] → 色１ RGBA（+0x34..+0x40），[37] → 回轉角度（+0xd8），[38] → 開始角度（+0xdc），[39] → 移動角度（+0xe0）（`0x59aaa4`..`0x59ab53`）。
- **103**（`0x507790`）：表面沒有 alpha（`0x5abb80`）就失敗；W 或 H 不是正的就成功、什麼都不畫（`0x5077db`）。直徑 D 取 W、H 的較大者（`0x5077ec` 比較、`0x50780b` cmovge），圓心 (X + 0.5 + D/2, Y + 0.5 + D/2)、半徑 D/2，都是 double。然後是命令 102 的圓掃描（`0x4cfb40`）與 102 的寫入器（vtable `0x80eabc`，呼叫槽 `0x4cbbd0`，和 102 的 `0x80eb2c` 是同一個函式）：有覆蓋的像素 alpha 變成 A·cov/255（向零截斷），在 `0x5b0a10` 夾到 0..255 後寫入，只寫 alpha；A 取 ArrayInt 15。所以 103 是 102 的掃描與寫入器，只差圓心與半徑；W ≠ H 時圓會超出矩形較短的那一邊。
- **107**（`0x507f80`）：沒有表面就失敗；W 或 H 不是正的就成功、不畫。和 103 同一段幾何（`0x508090` 比較、`0x50809e` cmovge）。先畫在一張同尺寸的透明暫存面（`0x5a94d0`），寫入器（vtable `0x80ead8` → `0x4cbb20` → `0x5b0b80`）寫 (R, G, B, A·cov/255)，各自夾值；`0x5b25c0` 取回寫過的範圍，寬或高小於 1（一格都沒寫到）就失敗；再以 `0x5acc00` → `0x494420` 合成：c += ((s − c)·sa) >> 8、a = max(a, sa)。所以 107 是 106 的暫存面合成加 103 的幾何。
- **121**（`0x5092a0` → `0x5b0760`）：沒有表面就失敗；W 或 H 不是正的就成功、不畫；handler 不要求 alpha。`0x5b0760` 建 122 用的同一個扇形物件（`0x4d0150`），rx = W/2、ry = H/2，圓心 (X + 0.5 + W/2, Y + 0.5 + H/2)，都是 double：**不取較大者，是矩形的內切橢圓**。寫入器 vtable `0x80ec98` 的呼叫槽是 `0x4d0510`（120 的 `0x80ec7c` 也是）：有覆蓋的像素換成 (R, G, B, A·cov/255)，RGB 各自夾值後寫，表面有 alpha 才寫夾過的 alpha（`0x5b0b80`；命令 100 用的也是這個寫入點，經 `0x4cbb20`）。掃描是 122 的 `0x4d0280`。
- **扇形掃描**（`0x4d0280`，122 共用）：`0x4d0450` 設角度範圍：`0x4eae00`（開始或移動是負的就直接返回，什麼都不取）、`0x4eafc0`（旋轉；0.0 時跳過）。r 取 rx、ry 的較大者，size = trunc(2r)，兩軸的位置是 c − r + k（k = 0..size−1）。位置的角度（`0x4eb0c0`）是 atan2(位置 y − cy, 位置 x − cx) 乘 65536/2π，負的加 65536，截斷成整數；兩端由 `0x4e5e50` 換算：度數取 360 的餘數乘 182.044…，截斷，終點是開始加移動，開始大於結束時取兩段的聯集。覆蓋（`0x4e6680`，旋轉 0 時）：8×8 的子樣本，兩軸各乘自己半徑的倒數，平方相加不大於 1 才算，cov = n·255/64。
- **atan2 的引數順序**：`0x7869ec` 在 `0x786a4e` 對第二個引數取近似倒數（rcpss），在 `0x786a69` 乘上第一個引數；`0x4eb0c0` 傳的第一個引數是 y 的差。所以「y 在前」是讀到的，不是只照 libm 的慣例（[construction-shapes](../construction-shapes/README.md) 當時寫成由幾何推得）。
- **截斷**：圓掃描的位置從 cx − r 到 cx + r、每次加 1.0，像素是位置向零截斷（欄在 `0x4cfc47`、列在 `0x4cfc39`）；覆蓋（`0x4e6530`）是位置右下 k/8 的 8×8 子樣本落在半徑內的個數，n·255/64。扇形的欄在 `0x4d03c2`、列在 `0x4d03ba` 向零截斷。所以表面左與上緣外半格的位置（−0.5）落在第一欄或第一列。
- **旋轉**：`0x4e5e00` 先把回轉角度取 360 的餘數再換成弧度，`0x4eafc0` 在 0.0 時跳過；所以 360 的倍數等同 0，其他角度照轉。

成功與失敗（【反】；失敗時這一步之後的步驟都不做）：

| 情形 | 103 | 107 | 121 |
|---|---|---|---|
| 沒有表面 | 失敗 | 失敗 | 失敗 |
| 表面沒有 alpha | 失敗 | 照做 | 照做（只寫 RGB） |
| W 或 H 不是正的 | 成功、不畫 | 成功、不畫 | 成功、不畫 |
| 圖形整個在表面外 | 成功、不畫 | 失敗（一格都沒寫到） | 成功、不畫 |
| 開始或移動是負的（沒有旋轉） | — | — | 成功、不畫 |

### 推論【推】

- 遊戲用的扇形是 90 起 180 度與 270 起 180 度，不論角度往哪個方向轉都得到左右兩半，所以實機看不出方向；方向由上面的反組譯與探針 IR11（模型的扇形掃描對已審過的 122）互相印證。
- 原版的位置列長什麼樣：只由反組譯與 AIN 推得，原版畫面沒有拍到（〈沒有原版畫面的項目〉）。

### 腳本端【AIN】

- 把 103、107、121 寫進 ArrayInt[0] 的只有三個 setter，每一個只被一個 `CASConstructionProcess` 的包裝函式呼叫：`FillCircle#5`（103，rect 與 alpha）、`FillCircleAlphaBlend#1`（107，rect 與顏色）、`FillPie#3`（121，rect、開始、移動、顏色與旋轉）。包裝函式的呼叫者都在 `PositionView`：`@BuildCursor` 呼叫 `FillCircle#5` 一次，`@BuildParts` 呼叫 `FillPie#3` 兩次、`FillCircleAlphaBlend#1` 每個位置一次。
- `PositionView@BuildParts`：n 個位置的列是 (24 + 18n)×30：整張填底色 alpha 0（命令 6），兩端各一個 30×30 方塊上的 121 半圓（90 起 180 度、270 起 180 度，顏色是底色），中間 (15, 0, 寬 − 30, 30) 再以命令 6 填底色，每個位置 i 一個 107 圓點在 (15 + 18i, 9, 12, 12)，顏色是位置色。`@BuildCursor`：12×12、整張填黃色 alpha 0，再加一個 A 200 的 103。旋轉都是 0。
- `PositionView` 是使用者元件，pactex 裡只放在兩處：成員的狀態畫面與人材的操作畫面（下方中央，縮 0.75 倍；底色與位置色兩處不同）；AIN 裡用名字取得它的也只有這兩個畫面。
- 顯示時間是腳本的：`PositionView@Show(true)` 重設計時器、以 100 毫秒淡入，更新事件在計時器超過 2000 毫秒時 `Show(false)`。
- pactex 的 168 個有手順的構築狀態，用到的命令沒有 103、107、118–121【量】，所以 pactex 載入器不改。
- v14 之前：移植版的 `AddPartsConstructionProcess` 只在 v14 的宣告組登記；舊的通用派送只認命令 0–18，這一組不碰它。103、107、121 對 v14 之前的引擎是什麼意思沒有讀。

## 做法

### 主線的決定

1. **照原版的結構**：103、107 和 102、106 共用圓掃描，121 和 122 共用扇形掃描，只換幾何與寫入器（下面〈實作〉）。
2. **只限 v14**：三個命令在 AIN 版本 14 之前照舊走 default 分支（IR10 守）。
3. **不分字集**【移】：三個命令不讀字串（原版 handler 只讀步驟的整數欄位，移植版只讀 ArrayInt 6、7、10–15、37–39），所以所有 v14 遊戲都畫，不分編碼，和 `0bf82e6`（[construction-shapes](../construction-shapes/README.md)）、`48d921e`（[construction-preview](../construction-preview/README.md)）的前例相同。探針在預設字集（SJIS 字串規則）與 GBK 下要求相同的結果。
4. **存檔版本 13 → 14**：121 帶顏色、寫 alpha 的方式和 122 不同，一定要新的操作型別；新操作要存，所以 XPE 存檔升第 14 版。
5. **奇數尺寸照原版畫**：遊戲只用 12 與 30，但新型別存的是矩形，奇數 D 的圓心在像素角、半徑是半整數，照原版畫不用另外的規則。期望值只依反組譯。
6. **尺寸上限、旋轉、角度照 xsystem4 自己的規則**【移】：D、W、H 超過 2048、121 的旋轉不是 0、開始或移動超過 360 都不畫並警告，和 102、106、122 的現行做法相同（下面〈和原版仍不同的地方〉）。
7. **原版失敗的那一步只跳過**【移】：103 畫在沒有 alpha 的表面、107 一格都沒寫到，原版讓這一步失敗、後面的步驟不做；移植版只跳過這一個操作、後面照做，和 102、106 相同。
8. 提交說明逐句查證後提出的選用註解提案（`src/parts/construction.c` 與探針檔頭的註解）不套用（〈提交說明的讀法〉第 5 條、HANDOFF 的待辦）。

### 實作【讀】【移】

- **新的操作型別** 32、33、34（`PARTS_CP_FILL_CIRCLE_AMAP_IN_RECT`、`PARTS_CP_FILL_CIRCLE_BLEND_IN_RECT`、`PARTS_CP_FILL_PIE_IN_RECT`），都用像素操作的結構，存先矩形 X、Y、W、H 與顏色，幾何在建構時才算；121 的開始、移動與旋轉放在像素操作既有的三個欄位（前例：面板的漸層把邊界放在 `line_width`）。三個值會寫進存檔，以 `_Static_assert` 釘住。
- **HLL**：103、107 → `PE_AddFillCircleInRectToPartsConstructionProcess`（先矩形、色１ 的 RGB、ArrayInt 15 的 alpha；107 是混合）；121 → `PE_AddFillPieInRectToPartsConstructionProcess`（先矩形、[38]、[39]、色１、[37]）。三個 case 都先看 `ain->version < 14`，是的話走原本的 default 分支。
- **圓**：`build_fill_circle` 的掃描抽成 `cp_fill_disc(x, y, d)`，以「左上位置 x + 0.5、直徑 d」參數化：102、106 以 (x − r, y − r, 2r) 呼叫，103、107 以 (X, Y, max(W, H)) 呼叫。覆蓋率改用 `cp_disc_coverage`，以八分之一格的整數算：u = 8i − 4d + s、v = 8j − 4d + t，u² + v² ≤ 16d²。值都是 1/8 的倍數，所以和原版的 double 版逐位元相同，奇數 D 的半整數半徑也是；d = 2r 時和原本的式子是同一個，102、106 的像素不變。pactex 的 `parts_cp_circle_cells` 仍用原本的式子，沒有改。
- **扇形**：`build_fill_pie_amap` 的掃描抽成 `cp_fill_pie(cx, cy, rx, ry, …)`，圓心與半徑是 double，另可給顏色：122 傳 (x + 0.5, y + 0.5) 與原本的半徑、不給顏色；121 傳矩形的內切橢圓與夾過的 RGB，表面有 alpha 才寫 alpha。122 的運算順序不變；位置與圓心都是 1/2 的倍數，(cy + dy) − cy 是精確的，所以 atan2 的引數和原版相同。
- **派送**：三個型別都在像素上做；103 只在有 alpha 的表面建（照 102），107 照建（照 106），121 把有沒有 alpha 傳進去。
- **存檔**：`CURRENT_SAVE_VERSION` 13 → 14；三個型別走像素操作的同一個佈局；第 13 版以前的讀取不變；AIN 版本 14 之前照舊寫第 3 版。
- **除錯輸出**：三個型別的名稱、JSON 與樹狀列印（只影響除錯傾印）。

### 適用範圍

新程式以 `ain->version >= 14` 為閘，v13 以前照父版本（IR10 守）。不讀文字規則：預設（SJIS 規則）與 GBK 在修前修後失敗與通過的案、失敗訊息都相同，下面每個突變在兩種字集失敗的案也相同。

## 和原版仍不同的地方

1. **原版失敗的那一步**【移】：103 畫在沒有 alpha 的表面、107 一格都沒寫到時，原版這一步失敗、後面的步驟都不做；移植版只跳過這個操作，後面照做（和 102、106 相同）。探針不檢查（Not covered）。
2. **尺寸上限**【移】：D、W、H 超過 2048 時原版照畫，移植版不畫、印警告（和 102、106、122 的半徑上限 1024 相同）。IR9 釘住 2049 不畫，IR13 釘住 2048 照畫。
3. **旋轉與超過一圈的角度**【移】：原版把旋轉取 360 的餘數，360 的倍數畫成 0、其他角度照轉；開始與移動也取 360 的餘數。移植版旋轉不是 0、開始或移動超過 360 就不畫（和 122 相同）。遊戲的旋轉都是 0、角度都在一圈內。
4. **atan2 的最後一位**：角度剛好落在扇形的邊界、由 atan2 結果的最後一位決定時，移植版用主機的 atan2。
5. **107 畫在沒有 alpha 的表面**：原版 `0x5acc00` 那條路沒有讀；移植版照 106 的做法。
6. v14 之前的行為是移植版自己的（不綁定），原版沒有讀。

## 沒有原版畫面的項目

- **位置列**（成員的狀態畫面與人材的操作畫面）：英文版原版沒有拍到。照交接規則備份了英文副本的存檔資料夾，Wine 的工具第一個檢查就偵測到螢幕鎖定而停下，遊戲沒有啟動、沒有送出輸入；跑完存檔逐檔比對沒有變。之後幾次查，螢幕都還是鎖定的。英文副本的存檔只到第 2 天，那一天有沒有可以點的成員與人材也沒看到。原版的期望只依反組譯與 AIN；修後的畫面和 AIN 的預期一致（第 3 人在第 3 點、換人移到第 4 點），但這不是原版截圖並排。

## Not covered（探針檔頭，`construction_in_rect_fixture.inc`）

探針檔頭列的是：

1. 原版會讓後面的步驟不做的失敗（103 畫在沒有 alpha 的表面、107 一格都沒寫到）：xsystem4 只跳過這個操作、後面照做，和 102、106 相同。
