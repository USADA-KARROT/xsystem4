## 問題與修正範圍

11/09 回報的三個戰鬥問題之一：同型敵人第二次以後被擊倒時，擊倒演出被略過，立繪以待機姿勢留在原地，直到被移除才消失。

【量測】修前（父提交的程式加只輸出記錄的追蹤）在戰鬥裡量到：`FrameInfoCollection@CopySubFrames` 從動作格的快取取出子格、存進另一個 `array<FrameInfo>` 時，存入的元素就是快取裡的那幾頁；腳本接著替元素加上起始格，快取跟著被改；同型敵人下一次取同一個鍵時第一格就超出範圍，死亡子格取到 0 格（第一次是 13 格）。兩趟、兩型敵人共 4 組都一樣；待機與受擊的快取也被改寫。死亡判定本身正確，差別只在子格是空的。

【反組譯】原版把 struct 值存進 v14 的 struct 值陣列（Add、PushBack、Insert、Fill、帶值的 Realloc）時，元素是陣列自己的物件，值逐成員指派進去；移植版原本只加參照，元素和值共用同一頁，之後腳本改其中一邊，另一邊跟著變。

【策略】本組只在 AIN v14、元素型別是 struct 值的陣列上，照原版由呼叫端新開元素（Add、PushBack、Insert）、再由元素設定函式逐成員指派，Fill 與帶值 Realloc 的新尾巴對既有元素呼叫同一個設定函式、就地指派，並照原版 struct 指派做前置與收尾：先刪掉指向目的物件的 delegate 項目，複製後把綁在來源物件上的 delegate 項目帶到目的物件上。v14 之前的引擎、不是 struct 值的陣列，以及含本程式不複製的成員型別的 struct，行為不變。另有兩項範圍內的必要改動：

- v14 struct 值陣列被 Erase 刪到空時保留帶型別的空頁。原版的元素型別屬於陣列物件，Erase 不改它；不保留的話，之後的存入會失去型別、回到共用。這個條件比存入的閘門寬：不看型別運算元與維度，v14 的 struct 陣列頁都適用，因為 v14 的 PopBack、Free、Clear 本來就對陣列保留帶型別的空頁；其他陣列維持舊規則（SC28 守）。
- AddRange 或 Concat 的目的陣列沒有頁時，v14 新做的頁帶上來源的 struct 型別，免得之後的存入讀到沒有設定的型別（SC59）。

| `0x6818c8`–`0x6818d3` → 來源的 vtable +8（`0x6818f0`） | 收尾，所有成員都指派成功才做，三步：(a) 對每個指向來源物件的 delegate，經 `0x6528f0` → `0x652210` 為目的物件加一份相同處理函式的項目（已有就先移除、附加到尾端）；(b) 走訪目的物件內含的 delegate（`0x682080` 配 `0x682330`），把自我綁定從來源改指目的；(c) 走訪來源物件內含的 delegate（`0x682080` 配 `0x6822d0`），刪掉 (a) 加進去、指向目的物件的項目。 |

巢狀 struct 成員與陣列成員裡的 struct 元素，各自完整走一次 struct 指派（含前置與收尾），子層的收尾先於父層。前置與收尾由兩次互不參考的唯讀研究讀出、結論一致，之後的語義複審再逐函式重讀；`0x653530` 由證據複審另外讀過。【推論】wrap 交出後換成參照型別碼的細節、delegate 複製時對環境的保留與釋放，沿用研究與複審的結論，本組沒有每一處都重讀。沒有執行原版二進位做這些讀取。

## 移植策略與原版的界線【策略】

- **閘門**：AIN v14、型別運算元 2、陣列頁是 struct 陣列、rank ≤ 1，而且 struct（遞迴）裡沒有不支援的成員，才走新做法；其他一律保留舊處理。不支援的成員：原版本身不能指派的（long int、型別 91、100、函式型別），以及移植版不複製的（option 的酬載是參照、rank > 1 或元素是 delegate、陣列、option、兩槽元素的巢狀陣列、型別 87 與 ref enum）。option<int> 照抄（動作格的 struct 裡就有）。
- **新元素**：不跑建構子的配置加逐成員指派；陣列接手新元素唯一的參照，值保留自己的參照，交出的那一份照 HLL 呼叫的規則歸還。
- **成員的槽**：字串、陣列、delegate 成員換成新的槽、舊槽釋放；原版是複製進既有的物件。只有在別處另外握有該成員物件本身時才看得出差別。移植版 v14 新物件的字串、struct、delegate 成員在使用前是 −1，當成原版的預設物件。
- **移植版自己做的物件**：新元素裡 wrap 成員的內層物件、給 −1 成員用的暫時預設物件，原版在這裡是 −1、不產生物件；移植版釋放它們時不跑解構子（SC39、SC40）。
- **Fill**：沒有物件的元素（−1，舊的 resize 會留下）先給新物件再指派，原版每個元素都有物件（SC4）。次數只取一次，每一輪經陣列的堆積槽重新取頁；前置或收尾跑的腳本把陣列縮短或放掉時就停下，並把現在的頁交回呼叫寫回（SC69–SC72）。原版這時會越界存取；這是本分支刻意的安全差異（原版越界後的行為來自語義複審的讀取，本組沒有全部重讀）。
- **前置只對既有物件做**：新做的物件在指派前沒有任何指向它的項目（配置不跑腳本建構子），結果和原版無條件做前置相同。
- **同一物件**：目的與來源是同一物件時，前置與收尾都跳過。原版傳進來的值是 `A_REF` 的複本，複本帶著原物件的綁定，不會遇到同一物件；移植版的 `A_REF` 對有參照成員的 struct 共用同一頁才會遇到，跳過才得到原版的結果。Fill 的值是陣列自己的某個元素時，原版推演的結果是那個元素的項目移到各 delegate 的尾端，移植版留在原位：項目集合相同，只差順序（SC52）。
- **delegate 的改動**只經既有的附加與移除函式，不直接改游標與上限；附加可能換頁，每一輪重新取頁並檢查邊界。
- **延後釋放**：舊成員與暫時物件的釋放延到整次存入之後（解構子可能再呼叫陣列函式庫）。深度上限 32 是防護。

## 驗收方式與結果

照既有判準：修前對照、預設與 GBK 兩組完整套件（142 模式）、九條路線、片頭三趟（相位判準與組層級）。另有三項只屬於本組的處理，判準與門檻都不改：

1. **片頭路線的 parts 編號**：本組之後，片頭路線的兩場戰鬥會多建立並釋放 parts（數量、建立者與釋放見下表），之後的動態編號比基準大；原本的路線比對與片頭關卡比的是絕對編號，因此一定判不過。不改這兩個工具與門檻，另外加一層證明，六項全部成立才判通過：(1) 對白、按下位置與次數相同；(2) 兩支只輸出記錄的追蹤版的配號序列對齊後，父程式的配號全部對上；(3) 多出的每一筆配號都落在核可的建立者清單內，清單外就判不過（本組多出的是特效 20、影子 4）；(4) 多出的 parts 全部釋放，每場戰鬥結束時存活集合相同；(5) 追蹤版與同一份來源的未追蹤趟比對，判準會讀的行編號相同，未追蹤趟只有游標取樣的行可以不同，而且每一行都要在追蹤趟找到佐證，找不到的趟不用於判定；(6) 把未追蹤趟的編號依配號對映轉回基準的編號空間後，原本的路線比對與片頭關卡照跑、要通過。這一層的判定工具是私人工具：用於真實資料之前經過兩輪獨立審查；第一次用在真實資料上就把提交前正式判定的第一趟判成不通過（合法的游標取樣差異找不到佐證），之後修正過兩次，兩次都是為了增加一種佐證方式；第一次修正被獨立複審擋下，第二次修正經另一次獨立複審放行，提交前後用同一版；刻意竄改轉換結果的反例在提交前與提交後都被擋下。正式判定的第一趟是九條路線那一輪的片頭趟，另外兩趟從其餘未追蹤片頭趟依序取最先通過第 (5) 項的；不通過的趟照實列出、不重新解釋。
2. **戰鬥追蹤趟**：(a) 子格陣列的元素和快取共用 0 個；(b) 每次死亡子格都取到和同型第一次相同、而且大於 0 的格數，至少一型被擊倒兩次；(c) 待機、受擊、死亡三種快取在每次進出時內容不變。戰鬥路線的比對若不過，同一支執行檔再跑一趟、確認落在同一群，才判為預期的位移。
3. **追加檢查**：整輪前後各核對一次最佳化執行檔的雜湊（路線腳本開跑前會自己建置）；每條路線找連續 30 秒以上畫面完全不變、而基準同一段有變化的地方，有就判不過；片頭前 30 秒和基準並排目視。

## 仍有差異與未涵蓋項目

- **一般的 struct 指派**（`SR_ASSIGN`）沒有前置與收尾，也是移植版既有的分歧；這款遊戲走不走得到沒有逐一追。過去沒出事是因為 v14 的 `A_REF` 對有參照成員的 struct 共用同一頁，本組是第一條「做出獨立複本、再放掉被綁定的來源」的路。
- **Copy 一族、Where、Concat、AddRange、Duplicate** 的 struct 元素不當成複本（原版 `0x6470e0` 也會逐元素指派；SC34 守現行處理）。
- **`A_REF` 的 struct 複本**只對純數值的 struct 複製，其他共用；複本沒有前置與收尾。
- **不複製的 struct**：含本程式不複製的成員型別（上面〈閘門〉所列）的 struct 走舊處理；這款遊戲有約 20 個存入點因此仍和值共用。這類 struct 在 v14 做 Fill 時，元素身分也和原版不同（本 AIN 的 struct 值陣列沒有 Fill）。
- **沒有頁的陣列**（例如從續行映像載入的空陣列）第一次存入走舊處理。舊的續行映像裡已經被改寫的快取不會被修正；驗收路線從存檔進戰鬥。玩家存檔不含動作格的快取。
- **delegate 頁的複本與環境的參照**：SC67 鎖住現況的參照平衡（成員複製、收尾複製、移除時各加減一次，最後回到原值）；對應原版保留與釋放的依據是先前的反組譯結論，本組沒有逐一重讀。
- **Fill 的防護界線**：同一輪之內，前置或收尾跑的腳本把正在處理的元素本身放掉，沒有防護（原版相同）。新元素那一側（Add、PushBack、Insert）沒有頁指標防護，依「新物件、成員的釋放延後、收尾放掉的環境仍被值的項目拿著」這個不變式不會跑腳本；這是推論，造不出讓它出錯的輸入。這款遊戲沒有對 struct 值陣列做 Fill 或帶值 Realloc，就地指派、前置與這些防護只有探針驗過。
- **Fill 途中腳本改動同一個陣列**【策略】：SC69–SC72 鎖住前置、收尾或延後釋放跑的腳本把陣列搬頁、縮短或放掉時，不讀寫已經釋放或越界的頁（每一輪經堆積槽重新取頁、長度以起點加索引判斷、新做的元素寫到當輪的頁、暫存的物件釋放之後才交回現在的頁）。這是本分支的防護行為；依語義複審的部分讀取，原版在陣列變短時會越界存取【推論】。其中兩案要靠 ASan 建置的配置器一定搬頁才抓得到對應的錯法，探針一律以 ASan 建置執行。另有兩種錯法沒有案（新做元素時把舊值立即放掉而不是延後；沒有已知槽時也寫回），現有呼叫者都走不到。
- **走訪的 delegate 陣列分支**在目前的閘門下走不到（含這種成員的 struct 走舊處理），沒有原版期望的案。
- **順序上的細節**：移植版移除項目時先搬項目再放環境，原版相反，只有放環境時連鎖改到同一個 delegate 才有差；依索引走時的位移與跨 delegate 的順序造不出合法路徑，沒有案。
- **探針的環境前提**：SC69–SC72 依賴 AIN 裡有形狀合格、解構子本體只有返回的 struct（依形狀搜尋），換一份 AIN 沒有時記為環境失敗，不會靜默通過。
- **原版畫面**只有戰鬥的擊倒演出，只有一場戰鬥、在 Wine 下執行、只比畫面內容與順序。春銷畫面的卡片現在存的是複本，由 HP1 守住 activity 的釋放；實機只有營業路線（對白 629、按下 15 次）提交前後都照既有判準和基準相符，這條路線沒有另外和原版並排。
- 期望大多由靜態反組譯推演，沒有在原版上實跑；原版實跑只確認擊倒演出的種類與順序。
- **片頭編號的證明**：那一層用私人工具判定，工具在真實資料上修正過兩次（第一次修正被獨立複審擋下）；它分不出同一位置、同一按下區間的兩個元件誰是誰，看不出同建立者、時間相近的兩個 parts 互換，多出的配號也沒有筆數上限。多出的 24 個 parts 是否和原版一樣，沒有拿原版對照。
