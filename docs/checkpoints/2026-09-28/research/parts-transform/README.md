# `A_REF` 的值複製、元件的變換與加算色、構築命令（戰鬥的量表、地城地圖）

2026-10-09。程式 `016b996`（`A_REF`）、`4046d17`（變換與加算色）、`46b78f6`（構築命令）、`8a18fc6`（審查後的修正）。

## 症狀（都和 Wine 上的原版並排比過）

- 戰鬥：角色頭頂的 HP、SP 條在原版是斜的粉紅與綠色量表，這裡灰色斜框的位置對，填色條卻水平擠在畫面最上緣；敵人量表旁的斜名稱沒有；行動中的角色高亮偏橘（原版黃）；技能演出時其餘角色不是粉紅剪影。
- 地城地圖：背景全黑、節點之間沒有連線、節點沒有白色圓底；節點名稱只有羅馬字是斜的，和中文名互相穿過。
- 教學與春銷的頁點是方塊；春銷的 READY 沒有黑色橫帶；據點的 ToDo 是黑字（原版粉紅）。

## 根因

1. **`A_REF` 共享 struct 的頁**。原版 `A_REF` 一律複製（新物件、不跑建構子、逐成員複製）。這裡對 struct 是多一個參照、同一頁；函式以 `return CASColor::BLACK;` 回傳常數時，呼叫端拿到全域常數自己的頁，之後就地修改就把常數改掉了。`PlayerFrameView@GetAddColor(Waiting)` 因此回傳 (219, 136, 0)，幾十個不相干的元件拿到同一個顏色。加算色以前根本不生效，所以看不到。
2. **父元件的變換沒有傳給子元件**。元件只用自己的位置擺放；原版每個元件有一個沿著樹累積的矩陣。加算色在原版也是沿樹的有號總和，減算色模式的元件把自己的加算色取負再加進去。
3. **構築命令沒有實作或只是近似**。地圖的背景、連線、圓底，頁點、橫帶都是腳本與 pactex 以構築命令畫出來的。

## 修正

- `016b996`：`A_REF` 對「成員全是數值」的 struct 回傳副本（本 AIN 1210 個 struct 裡有 53 個）。其他 struct 仍然共享——要連同成員的參照計數一起做，另案。
- `4046d17`：v14 的元件有累積矩陣（旋轉、縮放、翻轉傳給子元件的錨點與繪製）；加算色沿樹有號累積、減算色模式；命中測試以仿射求逆；著色器先乘後加。圖層的根元件在繼承裡是單位元。
- `46b78f6`：構築命令 25、26、27、28、29、52、97、102、106、129，腳本與 pactex 兩條路徑都接上，像素規則照原版。
- `8a18fc6`（審查後）：命令 106 的暫存緩衝原點修正（原本在邊界會寫出緩衝區外一個位元組）；鋪磚先裁切；圓框線幅的溢位；矩陣、命中測試與左上角的新算法限定 v14（v14 以前回到修改前的算式）；讀檔結束時更新一次元件；釋放父元件後子孫掛回圖層的根並重算；`A_REF` 的判定不把 long int 與型別 91 當成數值。
- **存檔是第 8 版**：隱藏清單之後是「減算色模式的元件」清單，controller 的 ID 仍在最後；新的構築操作是型別 14–22。第 7 版（有或沒有 ID 那一段）照舊讀得進來。

## 驗證

- 新模式 `aref-value`、`parts-transform`、`construction-cmds`（[harness 說明](../../harness/README.md)）。
- 正式 before-check（[before／after](before-after.txt)），每個 commit 都在前一個 commit 的 src 上執行新探針：`aref-value` 2 案全失敗；`parts-transform` 7 案全失敗、`controller-id` 2 案（存檔版本）失敗；`construction-cmds` 9 案全失敗、`panel` 1 案失敗；修正的那個 commit 之前，三個模式新增的案例失敗（命令 106 的邊界案例是 sanitizer 報的越界寫入）。修正後全過；兩種字元規則結果相同，還原後乾淨。
- 反向檢查：各部分暫時改壞的每一處都有案例失敗，除了已說明的等價改法與兩個探針環境做不到的（命令 29 的尺寸需要 CG 資產；忽略線上的水平邊對矩形與台階形是等價的）。
- 預設與 GBK 各 82 模式 VERDICT PASS、sanitizer 0（[預設](verify-default.txt)、[GBK](verify-gbk.txt)）。
- 既有探針的改動：`controller-id`（CI11、CI14）、`gauge`（HG5）、`construction`（CN6）對存檔版本的斷言；`panel` PN6 的守衛表（25–28、52、102、106 由「不加操作或只填 alpha」改成各自的操作）；`construction` 的「不支援的命令」改用 90 當例子。
- GUI（[摘要](gui-summary.json)，`RUN_RANDOM_SEED=20261008`）：十條路線沒有斷言、下溢或 VM 錯誤；對白的行數與雜湊和前一組相同。

## 實機上的改變（與原版並排）

- **戰鬥**：頭頂的粉紅 HP、綠色 SP 條與數值跟著斜框，位置與原版相符；敵人的斜名稱出現；行動中的角色是黃色剪影；技能演出時其餘角色是粉紅剪影；傷害合計的黑帶、技能按鈕的圓底。
- **地城地圖**：模糊的背景、淡斜格線、三種顏色的圓角連線（走過的紅、可走的淡紅、其餘灰）、節點的白色圓底；節點名稱整組一起斜。
- 春銷的 READY 橫帶、教學與春銷的頁點、據點 ToDo 的粉紅字。
- 春銷之後的對話視窗、春銷結算畫面仍與前一組相同（兩組的修正同時成立）。

## 獨立審查

一輪三個面向（`A_REF`、變換與存檔格式、構築命令），中等級的發現另有對抗驗證。

- 沒有 High。原版 `A_REF` 的做法、純數值的判定、各種用法下的參照計數、合併後的存檔格式、並排圖兩邊是同一個畫面，都核對無誤。
- 成立的 Medium 兩件，都在 `8a18fc6` 修掉：命令 106 的暫存緩衝在邊界越界寫入一個位元組（遊戲現有的兩個呼叫點不會觸發）；矩陣繼承等沒有版本條件，v14 以前的引擎也跟著變。
- 審查認為「戰鬥的傷害數字被這一組弄成斜 30°」。查證後：原版的傷害數字本來就斜 30°（腳本 `DamageNumber@0` 設的旋轉），而這裡目前根本沒有把傷害數字畫出來（見下）。

## 與原版的差異與限制

- **戰鬥的傷害數字沒有畫出來**：`PartsEngine.SetNumeralFont` 沒有實作（數字元件的函式多半是空殼）。被攻擊的敵人的量表在原版不透明，這裡半透明；停用的技能按鈕底色不同。
- **`DG_CALL` 與 Array 函式庫對 struct 值的所有權**沒有照原版：以值傳純數值 struct 給沒有訂閱者的 delegate 會留下一個副本，兩個以上訂閱者時第二個拿到已釋放的值（本體腳本這類 delegate 靜態上最多一個訂閱者）；`Array.PushBack` 等存入時每次留下一個副本。另案。
- 修改前存的 resume 映像可能帶著被改寫過的顏色常數，讀回後不會被修復。
- 地圖區左緣的淡出（面板的 alpha 漸層）、以構築命令 2 開頭的模糊背景（據點、春銷等 15 個狀態）、教學裡縮小畫面的模糊，都還沒有。
- 命令 29 以 GPU 混合，與原版每通道差 2 以內；多邊形的圓角與旋轉沒有做（遊戲傳 0）。
- 矩形的命中範圍仍是軸對齊的方框，旋轉的父元件底下與原版不同。
- v14 以前的原版引擎沒有讀過，只保證行為與這一組之前相同。
- 存讀檔沒有實機驗證。
