# 對話文字的已讀顏色

2026-10-11。程式 `dcf0b18`（基底 `cebc334`）。

這一步讓訊息視窗的本文照原版分「讀過」與「第一次讀」兩種顏色。已讀表本身與它的存檔是先前的 [msgskip-msk](../msgskip-msk/README.md)；文字的逐字淡入是 [dialogue-fade](../dialogue-fade/README.md)，這一步接在它上面。**文字裡的 ruby 與字型標記的樣式沒有做**，元件存檔的格式也沒有動。

## 症狀

- 原版：對白的本文，讀過的句子是淡黃色（規格值 (255,203,57)），第一次讀到的是白色；名字牌永遠是白的。設定「信息」頁的「已讀信息顏色更改」關掉後一律是白色。
- 移植版：本文永遠是白的。

## 根因

`SetMessageWindowText` 收到的訊息編號、函式名稱、版本與步數都沒有用到：視窗不知道這一句讀過沒有，建立文字時也不問腳本要顏色。

## 原版依據（靜態反組譯）

只來自多娜多娜這一支執行檔與它的 AIN；沒有執行。

| 項目 | 位址 | 內容 |
| --- | --- | --- |
| 設定文字 | `0x595610` → `0x4f2a60` | 文字與訊息編號都和現有的相同（`0x4f2ac6`–`0x4f2ae4`）就什麼都不做，**已讀旗標也不重查**；否則決定已讀旗標（下一列），並無條件清空畫面上的文字（`0x4f2b44`–`0x4f2b82`），新文字等下一次建立 |
| 已讀判定 | `0x4eea50` | 訊息編號大於 0：查已讀表（`0x4eeacf` 呼叫 MsgSkip 的 `GetFlag` `0x4c7700`；表未啟用、編號超出範圍都是未讀）。函式名稱非空（`0x4eeaee` 起）：改用 ADV 旗標，紀錄的版本相同而且步數大於等於這一次的才算已讀，結果蓋掉前一項。編號小於等於 0 又沒有名稱：旗標保持原值 |
| 新視窗 | `0x4ee701`–`0x4ee71e` | 已讀旗標 0、訊息編號 −1、一建立就算有變更 |
| 建立文字 | `0x4f2110`；更新 `0x4f25e0`、Fix `0x4f1f80` | 先向腳本取訊息速度的倍率，再看已讀旗標（`0x4f2236`，元件 +0x201）：為真就把本文字型與 ruby 字型各複製一份、各取一次色（`0x4f22e5`、`0x4f22ee`），用複製的那一份排字；視窗自己的字型不變。更新只在有變更時建立，Fix 每次都建立 |
| 取色 | `0x4f24e0`；登記 `0x6835d0` | 以字型的紅、綠、藍當初值，用參考傳給腳本的 `message::detail::GetReadMessageTextColor`（引擎以名稱登記：沒有回傳值、三個 int 的參考）。回來的值超出 0–255 時，負的當 0、其餘當 255（`0x4f255b`–`0x4f25a6`）；alpha 255；邊色不動 |
| 什麼會讓視窗重新建立 | 例：`SetKeyWaitShow` `0x5955d9` | 任何屬性的值改變都標成有變更，下一次更新重新建立並重新取色 |

腳本（兩邊跑同一份）：

- 取色函式在設定關掉時直接返回，三個值不動，所以引擎照樣回呼、顏色卻沒變。
- 設訊息視窗文字的只有四處：對白逐字加字的那一處帶訊息編號，其餘三處（清空、清空並回到起點、一個屬性的設定）都給 0。
- 設定畫面關閉之後、讀檔之後，腳本都會把目前頁的文字清空再逐則設回並 Fix。
- 一句被清掉時才把它標成已讀，所以第一次讀到的句子是白的；已讀表在回標題與結束時存檔。

## 做法

`src/parts/message_window.c`：

- 視窗多一個已讀旗標，在 `SetMessageWindowText` 照上表決定（同文同編號時不動）。新視窗的訊息編號是 −1。
- 建立文字時（元件更新或 Fix），已讀而且有文字的視窗回呼腳本的取色函式：以一個暫時的三格整數頁當三個參考的目標，照原版夾值，alpha 255。顏色只用在這一次排出來的字形上，視窗的字型與邊色不變（所以「同值再設字型不重排」比較的仍是腳本設的顏色）。回呼可能釋放或重建視窗，前後都以號碼加識別值重找。
- 腳本沒有這個名稱、或形狀不同的函式時不回呼、不變色；v13 以前不查表也不回呼。
- v14 的新文字一律等到建立之後才顯示。先前只有字速度不是 0 的文字要等（等的是倍率）；現在已讀的句子還要等顏色，而原版設文字時本來就先清空。

刻意和原版不同的地方：

1. **只有文字、字型、字速度、字距改變時才重新建立並取色**；原版在任何屬性改變後的更新、每一次 Fix、讀檔之後都重新建立。顏色仍然跟著設定走，是因為腳本在設定關閉後與讀檔後會把文字清空再設。
2. 沒有文字的視窗不回呼；ruby 字型那一次也不回呼（這裡不畫 ruby）。
3. 字型、字速度、字距改變之後到下一次建立之前，這裡把文字藏起來；原版繼續顯示已經建立的。v14 每一幀先更新再繪製，實機上沒有看到差別。
4. 元件的存檔不含已讀旗標（原版有）。讀檔後腳本會重設文字並重新查表；訊息編號小於等於 0 又沒有函式名稱的句子，原版用存檔裡的值，這裡是未讀。

## 驗證

- 探針（各案內容見 [harness](../../harness/README.md)）：新模式 `read-color` 13 案。判定的各種情形、同文同編號不重查、設定關、ADV 規則、先繪製不回呼、與淡入的時間表並存、v13 不查、回呼期間視窗被釋放／同號碼重建／被改成未讀的文字、已讀表存檔後重新載入、腳本沒有取色函式。案例真的執行腳本的取色函式，比的是字形貼圖的像素、回呼次數與堆上的頁數。
- 修前失敗（[before／after](before-after.txt)）：`cebc334` 上 13 案中 12 案失敗；修正後全過；兩種字元規則結果相同。
- 既有探針只改一處：`text-size` 的 TS11 在繪製前加一次 Fix（新文字要建立之後才顯示），位置與尺寸的斷言沒有動。`dialogue-fade` 的 16 案沒有改，仍全過。
- 反向檢查：16 處刻意改壞，14 處有案例失敗（其中一處是補強 v13 的那一案之後才抓到）；沒有抓到的兩處，一處與原來等價，一處是「空文字也回呼」，方向上更接近原版，探針沒有釘住。這是提交前、加上審查後三處小修之前的版本做的。
- 預設與 GBK 各 95 模式 VERDICT PASS、sanitizer 0（[預設](verify-default.txt)、[GBK](verify-gbk.txt)；提交後在 `dcf0b18` 上跑的）。
- GUI（[摘要](gui-summary.json)，`RUN_RANDOM_SEED=20261008`，提交後各跑一次，不帶已讀表）：十條路線沒有斷言、VM 錯誤或堆疊溢位；九條的對白行數與雜湊和前一組相同，`noskip` 與前一組互為前段。不帶已讀表時畫面上沒有任何已讀色的像素（戰鬥美術裡零星的同色像素除外）。

## 與原版的對照

移植版的例行路線每次用新的存檔資料夾，所以全部未讀。「已讀」是把第一次執行寫出的已讀表當種子再跑一次得到的。原版的「未讀」是讓 Wine 上的專用副本暫時改用一個空的存檔資料夾（真實存檔沒有被開啟），先前沒有這個畫面。

| 情形 | 原版 | 移植版 |
| --- | --- | --- |
| 第一次讀到的句子 | 本文白 | 本文白（同一句 1404 個純白像素） |
| 讀過的句子 | 本文淡黃 | 同一句 1370 個像素正好是 (255,203,57)，其餘 34 個是視窗上固定的白；名字牌 262 個純白不變 |
| 淡入途中 | 字一出現就是淡黃（半透明） | 淡入中的那一行從第一幀就是已讀色，沒有先白後黃 |
| 跨次執行 | 回標題時寫出已讀表，再開新遊戲同一句變黃 | 第一次結束時寫出已讀表，第二次同一句變黃 |
| 設定關掉 | 已讀的句子是白的；等鍵中關掉，返回後當頁立刻變白 | 已讀的句子是白的（用關掉設定後的存檔重新啟動，同一句 3002 個純白，與未讀時相同） |

- 原版的截圖是 JPEG，字心量到約 (236,204,97)；所以只比到色相與「本文黃、名字白」，沒有比數值。
- 「等鍵中關掉設定、返回後當頁立刻變色」在移植版沒有實機看到：從設定頁按「返回遊戲」時對白被推進了一頁（見最後一節），當頁已經不在。引擎端只有探針。
  > 2026-10-12 更新：「返回遊戲」推進一頁已修（`aa541a7`），返回後停在原來那一頁，見 [input-model](../input-model/README.md)。返回後當頁的顏色有沒有立刻變，那一組沒有另外確認。
- 回頭看過劇情回顧、設定「信息」頁的樣本文字、戰鬥訊息、名字牌，沒有被改到顏色。這一項用的是提交前的建置。

## 獨立審查

提交前，兩個面向（原版語義、狀態與記憶體），審查者與實作者不同；沒有 High、沒有 Medium，Low 三條，都在提交前處理：建立文字那一段的註解補上「顏色跟著設定走靠的是腳本的清空再設」；取色用的暫時頁在讀回之前擋住垃圾回收（當時是安全的，專案其他持有這種頁的地方都有擋）；探針的 40 輪多比一次堆疊深度。審查者以反組譯獨立確認了已讀判定、同文同編號不重查、取色的條件與夾值，以及回呼的參考計數是平衡的。審查全程唯讀，沒有重跑探針或實機。

## 與原版的差異與限制

- 上面「刻意不同」的四點。
- **從設定頁按「返回遊戲」，對白會被推進一頁；原版停在原來那一頁。** 這是輸入那一層的問題，不是顏色：是不是先前把全畫面點擊改到放開時才有的，還沒有在舊的建置上對照。
  > 2026-10-12 更新：已修（`aa541a7`），和原版的錄影對過。原因是按鈕在按下時就動作：設定頁關閉、回到對白的等待時左鍵還按著，放開被腳本自己的按鍵判斷算成一次點擊。這條路不經過全畫面點擊，先前把全畫面點擊改到放開的那一次沒有動到它（由那一次的 diff 靜態推定，仍沒有在更舊的建置上實測）。見 [input-model](../input-model/README.md)。
- 選項畫面沒有實機看過（沒有路線走到）；依據只有「腳本裡設訊息視窗文字的只有對白系統」。
- 存檔再讀檔之後的顏色沒有實機（讀檔流程還沒有走通）。
  > 2026-10-12 更新：讀檔流程已經走通（`6267ed3`），見 [system-reset](../system-reset/README.md)。讀檔之後的顏色那一組沒有另外看。
- 一頁裡有兩個訊息編號而只有一個已讀、以及 ADV 規則，只有探針，沒有原版畫面。
- 文字裡的字型標記與已讀色誰優先，沒有查。
- 只有 v14 變色。
- 和原版還不同、不屬這一組的：字型（原版是較細的明體類）、字距、刪節號與行的位置差幾個像素。
