# 函式呼叫的引數所有權（戰鬥中第二次點技能點不到）

2026-10-08。程式 `dfa141b`。

## 症狀

第一場戰鬥，第一個技能的演出播完後，技能按鈕上蓋著一層看不見的畫面和它上面的射程線，之後的點擊都被它擋下。

## 根因

v14 的 `function_call` 把引數從堆疊搬進被呼叫函式的頁時，對 struct、delegate、array 引數多加一個參照。位元組碼產生這些引數的指令已經交出一個參照，函式的頁釋放時只還一次，所以每次呼叫留下一個。

lambda 的 delegate 擁有建立它的函式的區域頁。把 lambda 當引數傳出去的函式，區域變數因此永遠不解構：`FrameImageCache@Join` 在區域變數裡建一個 `SceneContext`（一個元件圖層），把 lambda 交給 `Observer::Create` 後等待；它返回後 `SceneContext` 沒有解構，圖層留在戰鬥畫面上而且是作用中的 controller，之後建立的元件就蓋在技能按鈕上。

## 原版依據（靜態反組譯）

| 項目 | 位址 | 內容 |
| --- | --- | --- |
| 呼叫時存引數 | `0x657430`（表 `0x657508` → `0x6574fc`） | string 12、struct 13、delegate 63、array 79 原樣存入；ref 類 18–21／51／67／80／93、wrap 82、型別 87、介面 89 以 `0x679f10` retain；option 86 有值時依 payload |
| 函式頁釋放 | `0x6570f0` → `0x656cf0` → `0x656c10`（表 `0x656c88`） | 上述型別一律 release 一次；option 依 payload，none 不動 |
| C 端呼叫腳本函式 | `0x66a1a0` | 也經 `0x657430`，引數同樣是交出 |
| `A_REF` | `0x66b790` → `0x6794d0` | 複製一頁（字串、陣列、struct、delegate 都是；struct 的新物件不跑建構子） |
| `DG_CALL` | `0x66dce0`、`0x6722e0`、`0x672490` | 每個 entry 之前把交出型別的引數複製一份留在堆疊，原來那份交給 entry；沒有下一個 entry 時釋放剩下那份 |

所以 string、struct、delegate、array 引數是「交出」，其餘是「借用」。

## 修正

- `src/vm.c` 的 `function_call`：v14 而且不是經 `vm_call` 進來時，struct、delegate、array 引數不再加參照。
- C 端經 `vm_call` 推入的引數維持借用（這個 VM 的約定；呼叫者自己留著，頁另加一個參照）。
- string 照舊以 temporary 旗標區分。`DG_CALL` 與 HLL 回呼各自搬引數，沒有動。v13 以前不變。

## 驗證

- 新模式 `arg-ownership` 5 案（[harness 說明](../../harness/README.md)）：真的 `FrameImageCache@Join` 兩次（每次建構並解構一個 `SceneContext`、圖層移除、作用中的 controller 回到呼叫前）；交出的引數經真的被呼叫者；借用的種類照舊；兩百輪 `Observer::Create`＋`Release` 只留下已知的殘留；v13 的守衛。
- 正式 before-check：修前 `72f3174` 的 `arg-ownership` 5 案中 3 案失敗、`working-cards` 的 WC3 失敗；修後 `dfa141b` 全過；兩種字元規則結果相同，還原後 src／include 乾淨（[before／after](before-after.txt)）。
- 反向檢查 7 處（delegate／struct／array 又 retain、`vm_call` 的引數當成交出、v13 也交出、temporary 字串也 retain、wrap 當成交出），每一處都有案例失敗。
- 靜態掃描：本 AIN 最後一個引數是這三種型別的 `CALLFUNC`／`NEW` 呼叫點 1895 個，產生指令都交出一個參照；審查者另以所有引數位置（2593 個）重做，沒有例外。
- 預設與 GBK 各 73 模式 VERDICT PASS、sanitizer 0（[預設](verify-default.txt)、[GBK](verify-gbk.txt)）。
- 既有探針的改動：`working-cards` WC3 的最後一條斷言原本釘著這個洩漏留下的空 delegate 頁（殘留 +2），現在是 +1；`base-ui-review` 手建的兩槽陣列補上佈局，因為收下它的建構子現在會釋放它；`deleted-event` teardown 後的殘留由 19 個變 7 個。
- GUI（[摘要](gui-summary.json)）：八條路線都以提交後建置的執行檔執行，沒有斷言、下溢或 VM 錯誤；七條既有路線的對白與前一組相同；戰鬥路線在技能演出之後，點擊命中技能按鈕（修正前被那層畫面擋下）。另以 `MallocScribble` 跑過一次戰鬥路線（提交前的建置，與提交只差註解），沒有當機。長路線的峰值記憶體下降（走地圖的路線 1056MB → 946MB）。

## 獨立審查

一輪四個面向（原版語義、所有呼叫路徑、在真位元組碼裡找反例、探針與文件），高與中等級的發現另有對抗驗證。

- 沒有 High。在真位元組碼裡沒有找到會多釋放的呼叫點。
- 成立的 Medium 一件：探針的說明與設計筆記把 sanitizer 當成多釋放的偵測手段，實際上不會——`heap_unref` 對已釋放的 slot 靜默返回，sanitizer 與日誌都看不到。已更正；多釋放的偵測只靠探針裡精確的計數斷言。
- 其餘降為 Low 並已處理：文件的數字（3210 應為 1895）；「原版沒有 `vm_call` 這個進入點」的說法不對；`deleted-event` 的殘留數；探針檔頭與斷言不一致的兩句；`base-ui-review` 的手建陣列；`vm.c` 註解補上漏列的產生指令與 `DG_CALL` 的原版語義。

## 與原版的差異與限制

- **多釋放沒有執行期的診斷**。ASan 版引擎只走完正常路線；戰鬥路徑的依據是探針的 AO1、靜態掃描與最佳化版的實機紀錄。
- **`DG_CALL` 沒有照原版複製與釋放引數**：一個 entry 時平衡，沒有 entry 時留下一個，兩個以上時多釋放。修正前，entry 把 struct 引數再往下傳時多留的那個參照剛好會蓋住多播的少留，現在不會。本 AIN 靜態上沒有找到「多播而且引數是 struct 值」的事件，但 1288 個訂閱點裡有 669 個解析不出目標。
- **`A_REF` 對 struct 是共享同一頁**，原版是複製。被呼叫函式就地修改值引數時會改到呼叫者的物件（本 AIN 有 2 個函式這樣做，都是向量正規化）。
- **string 引數**：`S_MOD` 的結果與 HLL 回傳的字串沒有 temporary 旗標，當引數時多留一個（修正前後相同）。
- **Array 函式庫對 `A_REF` 交出的 struct 值再 retain**（`PushBack 2`、`Insert 2`）：每次登錄更新事件洩漏一筆紀錄，每個 CG 圖層物件多一個參照。探針把這些殘留數釘住了，修好時要往下改。
- 探針沒有涵蓋：struct 與 array 引數經真位元組碼的產生端（目前由 C 端建物件後直接呼叫）；多播的 delegate。
- 開場類的短路線峰值記憶體比前一組高約 20MB，原因沒有查。

## 這一組之後，戰鬥還差什麼

修正後與 Wine 上的原版並排比過（原版截圖只存本機）：

- **行動順序不同**。原版是第 2 位（珀爾諾）→ 第 4 位（藍衣，「零距射擊」可用）→ 第 1 位（電鋸）；這裡第二個行動的是第 1 位。
- 第 1 位角色在最後排時兩個技能都停用，**原版也一樣**：要按 ▶ 往前移兩格才有一個可用。所以「按鈕停用」不是錯；自動路線要先按 ▶ 才能把戰鬥打下去。
- **場景的位置與顏色不對**：原版背景在上半、黃綠色在下半，角色站在同一條地板線上，頭頂是粉紅與綠的斜量表；這裡黃綠色在最上面、敵人切在畫面最底、我方在畫面外、量表是黑的。根因在全域 struct 的啟動順序（常數被清成 0，包含顏色），是下一組。
- 原版戰鬥中沒有 DUNGEON 標題列，這裡還在。
