# 構築命令 1、12、13、89：設定第 3 頁的預覽與按鈕

2026-10-25（G7）。程式 `48d921e`，parent `97fee1d`（G2 的文件提交），libsys4 固定 `247f544`。提交前的預設與 GBK 各 117 個模式 PASS、sanitizer 0；提交後的預設與 GBK 各 118 個模式 PASS、sanitizer 0（多的一個是 G2 的 `sound-gain`）。程式推送後，本機、ls-remote 與 GitHub branches API 三方一致。

這一組在 G1 的程式 `e69dfa3` 上開發、審查與做提交前驗收，本機先提交成 `94016a3`（和提交前驗收用的原始碼逐檔相同）。這段期間 G2 的程式 `ebda614` 先推送，所以推送前把這一組接到 G2 的文件提交 `97fee1d` 之上重新提交，成為 `48d921e`，再重跑提交後驗收。兩組的引擎檔沒有交集。G2 和這一組都改了 harness 的 README、`env.sh` 與 `runtime_probe.c`：重定基底時兩邊加的模式都留下，harness README 寫的模式數改成 118，提交說明寫的也是 118。存檔版本在 parent 仍是第 12 版、這一組升為第 13 版，沒有撞號。

## 症狀

- 設定第 3 頁（信息窗口）右下的三個按鈕（返回遊戲、返回標題畫面、結束遊戲）按中間都沒有反應，只有「結束遊戲」的左端按得到。
- 同一頁右下的預覽背景，畫成整張背景照原尺寸蓋到右下角、壓在按鈕上；原版是 640×180 的一條。
- 另外 7 個構築狀態什麼都沒畫，或用原尺寸的 CG 代替（見〈原因〉的表）。

## 原因（實機紀錄加讀程式）

- **預覽背景是一個構築元件**，手順是 0、13：
  - 命令 0 建一張 640×180 的表面。
  - 命令 13 把 1280×720 背景 CG 的下半張（1280×360）縮成 640×180，混合上去。
- **為什麼點不到**：移植版的 pactex 載入器不認命令 13，整個狀態不建構，舊的 CG 備援把背景照原尺寸 1280×720 畫在預覽的位置 (512, 414)。這個元件的 `オン指針透過` 是 0，蓋到的地方游標判定都落在它身上。
- **修前實測**（基底 `e69dfa3` 的建置）：
  - 三個按鈕的中心點，按下的目標都是預覽，沒有送出點擊事件，畫面不變。
  - 對照：「結束遊戲」在預覽左邊露出的部分按得到（遊戲結束）；第 1 頁同一位置的「返回遊戲」也按得到（回到據點）。
- **這一組處理的 8 個狀態**：前兩組之後，遊戲 168 個有手順的構築狀態還有 8 個不建構，用到的就是命令 1、12、13、89。

| 命令 | 狀態 | 修前 |
|---|---|---|
| 13 | 設定第 3 頁的預覽背景（0、13） | 背景照原尺寸，擋住三個按鈕 |
| 12 | 事件提示（`EventHintView`）的條紋（0、12） | 2048×2048 的圖樣照原尺寸；推論可能擋掉提示右下一大片的點擊，沒有實測 |
| 12 | 高 290 的捲軸底（`ScrollBarUnit290` 的 `Bg`，0、12、12） | 14×460 的 CG 照原尺寸。AIN 裡只有 `ScrollBarUnit@CreateActivity` 在型別 2 時載入它，三個建立捲軸的地方傳的是 0、1、1，推論遊戲裡不出現 |
| 1 | 設定第 8、9 頁的背景（四個，1、3） | 什麼都不畫；這兩頁一般玩家進不去 |
| 89 | 人材行動頁（`SceneWorkerOperation`）的一張全畫面部件（0、89） | 什麼都不畫；這個部件執行時隱藏，見〈驗證〉 |

## 原版依據

只做靜態分析，讀多娜多娜這一支執行檔。跳表是 `0x4fb7d8`：1 → `0x4fbe40`、12 → `0x4fe050`、13 → `0x4fe330`、89 → `0x506960`。四個都是 handler 失敗就跳過其餘步驟（`0x4fb675`），和前兩組相同。

| 命令 | 位址 | 內容 |
|---|---|---|
| 13 | `0x4fe330` → `0x50b350` | 沒有表面就失敗。`補間タイプ` 只取低位元組（`0x4fe379` 的 movzx）。`0x50b350` 先取 CG 的 `元矩形`（`0x5a9ea0`；`0x5ab3b0` 在寬或高不是正的時取整張），`補間タイプ` 2 時縮放到 `先矩形` 的 W×H（`0x5aa9c0` → `0x4929e0`，和命令 14 同一個縮放）；1 走 `0x5aa7b0`（沒讀）；其他值在 CG 的解析度比例是 100 時不縮放 |
| 13 的混合 | `0x5aca90` → `0x491a50` | 只把目的矩形裁到表面（`0x5abed0`），來源從 (0, 0) 讀、不裁。表面有 alpha 時走 `0x494320`：R、G、B 各自 `c += ((s − c) × sa) sar 8`，不寫 alpha；表面沒有 alpha 而且有 SIMD 時走 `0x491c10`：`((s − d) × (sa >> 1)) >> 7` |
| 沒有 alpha 的 CG | `0x4761a0`、`0x4764b4` | QNT 解碼器把沒有 alpha 的 CG 建成只有像素的影像，每個像素的第 4 個位元組寫 0xff；取一部分（`0x5a98d0` → `0x4918e0`）與縮放（`0x4929e0`）都保留四個位元組，所以混合時 sa 是 255 |
| 12 | `0x4fe050` | 不讀 `補間タイプ`（遊戲資料寫的 1 沒有作用）。複製的寬、高是 `元矩形` 與 `先矩形` 較大的那個（`0x4fe0ce`、`0x4fe0e5` 兩個 cmovge），`0x50b160` 取 CG 的那一塊。表面有 alpha 時 `0x5acd70` → `0x4918e0`，四個位元組都複製；沒有時走 `0x5ad010`，只寫 RGB |
| 1 | `0x4fbe40` → `0x5a9680` | 先清掉原來的表面（`0x5a8df0`），再建 W×H、沒有 alpha 的表面（`0x7009e0` 只標「有像素」）；寬或高不是正的就失敗。命令 0 的表面兩者都標（`0x700960`），並塗成不透明黑（`0x5a94d0`） |
| 89 | `0x506960` | 寬或高不是正的就成功、不畫（`0x5069a0`–`0x5069aa`）。否則用命令 90 的四角（`0x4e97b0`）、依 `旋轉角度` 轉（`0x4e9940`），以命令 94 的寫入器（`0x5afa40`）把有覆蓋的像素寫成 (R, G, B, A·cov/255)，各自夾到 0..255。和 90 不同，不要求表面有 alpha |

遊戲形狀上的結果：

- **13**：1280×360 縮成 640×180 剛好是 2:1，定點的權重都是 0，每個像素就是背景的 (2x, 360 + 2y)，沒有內插（反組譯加算術）。在不透明黑的表面上以 sa = 255 混合，得 `s·255 sar 8`，也就是比背景暗一級（s ≥ 1 時是 s − 1），alpha 仍是 255。
  - 量測佐證（原版是 Wine 上的 JPEG 截圖兩張，畫面只留在私人工作區）：預覽四條邊帶（避開疊在上面的樣本信息窗口）的殘差，「以 255 混合」的中位數除了一張左條的 B 通道是 +1，其餘都是 0；「直接複製」除了兩張左條的 B 通道是 0，其餘都是 −1。同一張截圖裡這一組不碰的四塊區域，對修前建置的畫面，中位數除了標題列的 B 通道是 +1，其餘都是 0，所以 JPEG 與 Wine 本身沒有 −1 的偏差。截圖是 JPEG，只能看統計。
- **12**：捲軸底是 CG 的第 0–269 列加第 440–459 列，alpha 一起換成 CG 的；條紋是 2048×2048 圖樣左上角的 400×320，alpha 一起換，元件的 `アルファ` 是 16。兩個形狀的 `元矩形` 寬高都是 0，max 取的都是 `先矩形`。
- **89**：1480×920 的不透明黑上，從 (100, 100) 起 1280×720、`色１` (0, 0, 0, 0)：覆蓋到的像素都變成 (0, 0, 0, 0)，外圈是黑框。
- **1**：四個狀態都是 1 之後接 3 填滿整張，表面的初始內容看不到（初始是 0 是推論，只讀了反編譯輸出）。

## 做法

- **新增兩種構築操作**：`PARTS_CP_CUT_CG_COPY`（型別 30，給 12）、`PARTS_CP_CUT_CG_SCALE_BLEND`（型別 31，給 13），欄位和 7、8、29 相同。
  - 照原版的後端分塊寫成共用函式：縮放（`0x4929e0`）、複製（`0x5acd70`／`0x5ad010`）、混合（`0x494320`）、取一部分（`0x5ab3b0`）。
  - 命令 14 改用同一組函式，結果和原本逐位元組相同（`cg-scale-copy` 7/7 照過）。
- **命令 1**：用腳本路徑已經在用的「只有像素的表面」操作（`PARTS_CP_CREATE_PIXEL_ONLY`，GL 貼圖沒有 alpha）。載入器讓 1 也能當第一步，之後只收 3（遊戲的形狀）。貼圖沒有 alpha 位元是移植版的表示法；這種表面畫出來是不透明，是推論（渲染端沒有讀第 4 個位元組）。
- **命令 89**：展開成命令 94 的操作（寫顏色與 alpha），四角與條件比照 90；90 照舊用 95 的操作（只寫 alpha）。
- **沒有 alpha 的 CG**：12、13 照收，第 4 個位元組當 255（依 `0x4764b4`；libsys4 的 QNT 與 PNG 解碼也補 0xFF）。
- **存檔升為 XPE 第 13 版**：新操作要存。第 12 版以前的存檔照舊可讀；v14 的新存檔一律寫第 13 版，就算裡面沒有新操作，舊建置也會拒絕，和以前升版一樣。新操作在存檔裡是型別接著 7、8、29 的十個欄位。
- **建構條件比原版保守**，下列情形整個不建構，維持舊樣子（遊戲資料裡沒有這些組合）。這些是移植策略，不是原版的語義；原版多半會裁切後照做，或走另一條寫入路徑：
  - 13：`補間タイプ` 的低位元組不是 2（1 走 `0x5aa7b0`，沒讀；0、3 不縮放）；表面沒有 alpha（原版走 `0x491c10`，捨入不同）；定點乘積超出 32 位元（同命令 14）。
  - 12、13：`元矩形` 超出 CG，含 X 為 −1（原版 `0x5ab3b0` 裁成交集）；`先矩形` 超出表面（原版只裁目的矩形，照樣畫一部分）；接在 CG 起始或命令 1 起始之後（原版照表面能收的寫；沒有 alpha 時 12 走 `0x5ad010` 只寫 RGB）。
  - 1：寬或高超過 8192（移植版的上限）；之後接 3 以外的命令，例如 5（原版在沒有 alpha 的表面上跳過，`0x4fc378`）；已有表面時再出現第二個建表面的命令（原版清掉重建）。
  - 89：`旋轉角度` 不是 360 的倍數（原版照轉）；整個在表面外；接在命令 1 起始之後。
  - 接近 int 兩端的座標與寬高（原版以 32 位元相加會繞回）。檢查本身先確認座標不是負的，再用「上限減座標」比，不做相加。
  - 原版也失敗的一步（CG 不存在、1 的寬或高不是正的、12／13／89 在第一步而沒有表面）：原版保留前面已畫好的步驟，移植版整個狀態不建構。
- **適用範圍**：
  - 對所有 v14 遊戲都適用，不分編碼，SJIS 與 GBK 拼法的鍵都認。存檔版本號對所有 v14 遊戲都變成 13。
  - v14 之前的遊戲四個命令一律不建構，存檔仍是第 3 版。
- **既有探針跟著升版**：`button-text`、`cg-scale-copy`、`config-widgets`、`construction-cg`、`construction-cmds`、`construction`、`construction-shapes`、`controller-id`、`gradation-text` 九個，把目前存檔版本的期望值改成 13，或把改寫成舊版存檔時認得的版本上限延到 13。期望值仍是嚴格的等式。
- **沒有改的**：腳本路徑（`AddPartsConstructionProcess`）的 1、12、13、89；命令 14 對沒有 alpha 的 CG 仍不建構（見〈沒做與沒驗證〉）。

## 沒做與沒驗證

- **命令 12 的實機畫面**：見上。要跑完往春銷顧客清單的路線，或另找有人材帶事件提示的存檔，基底與這一組各一趟。
- **config 例行路線沒有加第 3 頁**：改例行路線就沒辦法對 G1 的基準比，第 3 頁另用單獨的路線實測。要加的話，在提交後另立新基準。
- **命令 89 的部件有沒有真的建出來**：可以在提交後用 debug 輸出（新型別的名稱已加）確認那個狀態的操作。
- **缺鍵沒有探針守住**：探針每一步都帶 `補間タイプ` 與 `色１`，缺鍵的路徑沒走到。審查者的兩個突變（13 缺 `補間タイプ` 時當成 2 建構、89 缺 `色１` 時不建構）都存活。原版缺鍵讀到 0：13 缺 `補間タイプ` 就是 0（比例 100 時不縮放），89 缺 `色１` 就是 (0, 0, 0, 0)、照樣建構。遊戲的每一步都帶齊全部的鍵，不影響遊戲。
- **12 和 14 對沒有 alpha 的 CG 不一致**：14 的載入器遇到沒有 alpha 的 CG 就不建構（當時的理由是第 4 個位元組沒讀），12、13 依 `0x4764b4` 照收。遊戲用到的兩張 12 的 CG 與 14 的兩個形狀都有 alpha，不影響遊戲；之後可依 `0x4764b4` 放寬 14（要補探針案例），或至少更新 14 的註解。
- **CG 的解析度比例沒有重現**：原版 `0x50b350` 讀 CG 資訊的兩個比例，不是 100 時先把 `元矩形` 乘 100 再除以比例（`0x50b486`–`0x50b4cd`）。移植版的載入器讀不到比例，這種 CG 照原本的 `元矩形` 建構，取的範圍會和原版不同；12 同樣沒有重現，探針也沒有這種案例。遊戲唯一的 13 形狀，由修後與原版截圖的殘差推論比例是 100。
