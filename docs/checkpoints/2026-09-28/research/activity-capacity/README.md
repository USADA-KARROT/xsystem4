# 活動登記表容量修正

程式提交 `3e103f6`；提交前九路線、片頭三趟與組層級通過。提交後兩組各123模式、九路線、片頭三趟及組層級均通過，片頭組平均-4.01毫秒；以下資料對應此程式提交。此文記錄 2026-10-28 至 2026-10-31 的靜態分析及有界量測，未完成項不視為通過。

【量測】連續操作時，移植版活動登記表達 128 筆後拒絕建立新活動，隨後讀取及元件查找失敗。修前受控操作在 558.563 秒因錯誤門檻停止，記錄 4 次容量拒絕、4 次讀取缺活動與 3 次斷言；程序退出碼 0 不代表驗收通過。

【反組譯】原版 CreateActivity（0x5633c0）及 ReadActivityFile（0x5634a0）經 0x563ec0／0x564200 插入動態容器，0x564450 依負載擴桶，沒有移植版 128 筆的小上限。0x56421c–0x564226 有 24,970,739 筆容量檢查，因此不能說原版完全沒有上限。

【靜態資料／AIN】pactex 鍵 Forecast 是直接 CG 子元件，普通狀態型別為 19；本身沒有巢狀子元件或構築命令。WorkerView@0 會取得該元件，CActivityWrap@GetCG 在查不到名稱或狀態型別不符時可回空值。靜態呼叫鏈與觸頂量測支持此條缺件路徑，沒有證明它只會在特定天數開放。

【移植策略】恰好 v14 使用可成長陣列，其餘版本保留 128 筆上限。配置空間不足時倍增，以元素大小、可配置位元組範圍與 int 計數上限保護容量計算；Reset 釋放表並清空指標、容量、筆數。倍增是移植選擇，並非重建原版容器。名稱查找、元件釋放與圖層生命週期不改；重複 Create 回真也是保留移植版既有行為，原版回假。

【量測】收窄為 僅 v14 後，預設與 GBK 各 123 模式 PASS、sanitizer 0。新合成探針涵蓋 257 個名稱；在 parent 的兩種字集均有 7/8 案於第 129 筆失敗，防守案通過。23 個引擎錯誤候選在兩字集均被拒收，前後控制組通過；把版本條件退回原先範圍的候選，確實只由新 v15 容量／存在性守衛抓到。部分其他候選由 sanitizer 或異常退出拒收，不能全部說成正常回傳值斷言。

【量測／限制】容量與 Reset 記錄器前後控制各 15 案通過，另 13 候選中 12 個以明確比較檢出、1 個在本機 ARM64 的整數上限下等價。它不配置巨大陣列，不代表實際 OOM、配置搬移或洩漏檢查。早期四個容量策略候選在有限功能案例中存活，配置成本及跨平台行為未全面驗證；16 項合成資料／模型自檢與 18 項判讀器案例另計，未納入引擎候選數。

【量測／限制】初版修後受控操作執行 930.392 秒，未記錄原斷言鏈或堆疊溢位，畫面推進至第 9 天及後續結果介面。這份紀錄早於 僅 v14 收窄，兩版在本遊戲的 v14 容量路徑相同是讀碼結論；不得將舊執行檔雜湊改稱最終提交。兩次操作的狀態與時序不同，不是使用者原路徑逐步重播，亦不是原版並排。

【未驗證】原版同場景畫面未取得；短暫畫面重疊、活動跨日回收是否完全符合原版、長時間穩定、真實記憶體不足、所有 SJIS 遊戲仍未驗證。此修正不代表全部顯示或生命週期問題都已解決。（2026-11-09 補記（G14 修正，程式 `d142176`）：春銷派出與場景結束時，人物卡的三個 activity 現在會釋放，顧客總覽關閉時它的顧客卡也會釋放（量測建置的釋放紀錄量到；顧客卡的參照沒有追蹤）；登記表在多天之後的筆數沒有量。見 [hll-param-handover](../hll-param-handover/README.md)。）
