# 構築命令 7、90、100、101、106：圓、矩形的 alpha 與文字

2026-10-19。程式 `0bf82e6`，基準 `8d794c6`（前一組程式 `ceeb9db`），libsys4 固定 `247f544`。提交前、後的預設與 GBK 各 110 個模式 PASS（提交前那兩組跑在加最後一道守衛之前的原始碼上）。

這一組先在 `ceeb9db` 上提交成 `aa31423`，做了推送前的覆核與第一次提交後驗收。推送前接到 `8d794c6` 之上重新提交，同時加了一道守衛（見〈做法〉），再在 `0bf82e6` 上重跑全部驗收。

## 症狀

遊戲有 11 個構築狀態什麼都沒畫，例如：

- 戰鬥結算與換人面板的頭像：沒有洋紅圓底，臉也沒有裁成圓。
- 城市地圖：地點名旁的新地點記號沒有出現。
- 成員畫面：技能槽的字母底、前列的括號都沒有。
- 地城的地圖：迷你地圖節點的圓沒有出現。
- 人材的狀態圖示說明、性格說明：畫面沒有變暗。

## 原因（實機紀錄加讀程式）

pactex 載入器不認這 11 個狀態手順裡的某一個命令（7、90、100、101、106），整個狀態不建構。遊戲 168 個有手順的構築狀態裡，前一組之後還有 19 個不建構，這次處理其中 11 個。其餘 8 個用到命令 1、12、13、89，另開一組。

## 原版依據

只做靜態分析，讀多娜多娜這一支執行檔。跳表是 `0x4fb7d8`，某一步失敗，後面的步驟跳過。

| 命令 | 位址 | 內容 |
|---|---|---|
| 100 | `0x507350` | 命令 102 的同一個圓掃描（`0x4cfb40`），但寫入器是 `0x4cbb20` → `0x5b0b80`：有覆蓋的像素換成 (R, G, B, A·cov/255)，各自夾到 0..255，表面有 alpha 才寫 a；handler 不要求表面有 alpha（102 要求） |
| 101 | `0x5074b0` | 同一個圓，直徑 D 取 `先矩形` W、H 的較大者（`0x50753a`），圓心 (X + 0.5 + D/2, Y + 0.5 + D/2)，半徑 D/2 |
| 106 | `0x507d60` | 先畫在透明的暫存面再合成，和既有的混合圓相同；一個像素都沒寫到時失敗 |
| 90 | `0x506ae0` | 矩形的四角（`0x4e97b0`）用命令 95 的多邊形掃描，只寫 alpha |
| 90 的 `丸め` | `0x4ea2e0`、`0x4e5cf0` | 每條邊的兩端各往內移 d = min(4, trunc(邊長 / 4))，再在邊往正方向走的軸加 0.5、其他軸（含 0）減 0.5。結果整個圓角矩形往左上偏一個像素，四角的切角也不對稱 |
| 7 | `0x4fc7e0` | 和命令 24 是同一段文字迴圈，只有貼字格那一步改成混合顏色（`0x5aca90`） |

`0x4e5cf0` 用的 cos、sin 由兩個函式的小引數分支直接證實（`0x7870a2`、`0x788d40`）；`0x7869ec` 是 atan2(dy, dx)，由幾何推得。

## 做法

- **沒有新增操作型別，存檔仍是 XPE 第 12 版。**
- **100、101**：
  - 展開成兩部分：每一列有覆蓋的那一段，用命令 3 填色（只換 RGB）；再加命令 102 的 alpha 操作。
  - 兩者寫的像素和順序都相同，所以逐像素等於原版。
  - 每列有覆蓋的格子一定是連續的一段（複審時對半徑 1 到 1024 的每一列窮舉過）。萬一不是，整個狀態不建構，不會只畫一半。
  - 推送前加的守衛：半徑不是正的時直接當成不畫，避免半徑是 int 最小值時取負數溢位。原版對所有不是正的半徑都是成功、不畫（`0x507395`）。
- **90**：展開成命令 95 的操作，頂點是推出來的半整數座標。
- **106、7**：用既有的混合圓與文字操作。
- **建構條件比原版保守**，下列情形整個不建構，維持舊樣子（遊戲資料裡沒有這些組合）：
  - 100、101、106 的顏色超出 0..255 或缺 `色１`；100、106 缺 `半徑`（90 缺 `色１` 時照原版當成 0，會建構）。
  - 101 的直徑是奇數。
  - 106 的圓心在表面外。
  - 90 的旋轉角度不是 360 的倍數。
  - 90 有 `丸め` 時，邊短於 4，或左上角的座標小於 16。
  - 矩形整個在表面外。
  - 7 的條件和命令 24 相同。
- **適用範圍**：
  - 90、100、101、106 對所有 v14 遊戲都適用，不分編碼。
  - 7 只在 CN 字格上建構，所以 SJIS 版的 v14 實際上不變。
  - v14 之前的遊戲不受影響。
- **代價**：100、101 的操作數變多，例如結算的頭像底 131 個。只有 activity 編輯器會讀回操作數，遊戲看不到。

## 驗證

- **探針 `construction-shapes`**（11 案，說明見 [harness](../../harness/README.md)）：
  - 期望值由探針裡另寫的模型與手算像素得出。
  - 修改前 10/11 失敗，另 1 案是守衛，見 [before.tsv](before.tsv)。
  - 20 個故意改壞的突變都有案例抓到。推送前的複審在審查後的程式（`aa31423`）上重跑過，其中 2 個照審查後的寫法改了替換點。最後加的守衛沒有重跑突變；它只影響半徑不是正的輸入，而這 20 個突變沒有一個只靠那種案例抓到（推論）。
- **既有探針**：`construction` 原本拿 90 當「載入器不認的命令」，現在 90 會建構，改用 200。200 在原版沒有 handler，原版會略過這一步、其餘照做；這裡測的是移植版整個不建構的選擇。
- **兩組 verify**：提交前、後的預設與 GBK 各 110 模式 PASS，見 [verify.tsv](verify.tsv)。
- **用真的遊戲資料建構**（推送前的複審）：
  - 對全部 168 個構築狀態跑正式的載入器：這 11 個都建構，其他狀態的結果和修改前相同。另有 26 個含 CG 的狀態，探針沒有 CG 檔、無法評估，但它們都沒有用到這五個命令。
  - 據點日程的提示記號與一種按鈕陰影，在真的 pactex 與移植版用的字型上建構成功。
  - 提示記號 24×24 共 576 個像素的 alpha，和照原版語義另寫的模型相同；字以外的顏色都是紅色；字的形狀與水平位置，和用同一個字型另畫的結果相同。
- **和原版並排**（原版是 Wine 上的截圖，畫面只留在私人工作區）：
  - 戰鬥結算的頭像底：四人中量得到的三人，圓的左右緣與上緣和原版差 0–1 px（原版截圖是 JPEG；第 1 人的髮色和底色相近，量不準）。臉照原版裁成圓。提交後的執行檔在 fightr 與片頭重播的結算畫面上重量，位置相同。
  - 換人面板的頭像底：差 0–1 px。
  - 城市地圖的新地點記號：位置相同，像素差在 JPEG 雜訊內。
- **沒有原版畫面、只有修改前後對照的**（用審查前的建置；和提交的程式只差註解，以及審查後加的兩道守衛，遊戲資料走不到）：
  - 迷你地圖的節點、技能槽的字母底、前列的括號：修改前沒有，修改後有。
  - 兩個暗幕：修改前畫面沒有變暗；修改後除了說明對象（狀態圖示、性格欄）附近的圓角洞，整個畫面變暗一半。洞的位置和上面推出的「往左上偏一個像素」相符。
  - 回頭看同一路線的其他畫面：差異只在預期的區域，其餘是動畫、轉場與隨機提示的時間差。
- **例行路線**（`0bf82e6` 的建置）：

## 沒做與沒驗證

- **頭像本身左右相反（既有問題）**：戰鬥結算的頭像，移植版和原版左右相反。修正前的畫面也一樣；回查留有結算畫面的建置，最早到 10/10 的都已經這樣，不是這一組造成的。這一組只補了圓底與圓形裁切，另開一組在查原因。換人面板的頭像方向正確。
- **兩個狀態沒有在畫面上看到**：
  - 據點日程的提示記號（106 加 7）：只在日程有要注意的項目時出現，第 3、4 天走不到。字在圓裡偏上 3–4 px，原版是不是一樣沒有證據。
  - 一種按鈕的陰影（7、27、28）：編輯時就設成隱藏，執行時看不到。
  - 兩者都已用真的遊戲資料確認會建構，但真字型下命令 7 的像素沒有和原版比過。
- **圓角暗幕的「往左上偏一個像素」只有靜態證據**：所有 Wine 截圖都沒有這兩個畫面。讀錯的話，洞會差一個像素。
- **舊存檔**：在這次修改之前存的檔，如果存檔時這些元件已經在畫面上，記下的是當時沒有建構的樣子，讀檔後要等 activity 重新載入才會變（推論，沒有實測；和修改前一樣，不是退步）。
- **腳本路徑**：`AddPartsConstructionProcess` 的 90、100、101 仍不加操作，這一組只改 pactex 載入器。命令 94、95 的 `丸め` 仍不建構。
- **仍不建構的狀態**：還有 8 個，用到命令 1（設定第 8、9 頁的背景）、12（事件提示的條紋、一種捲軸的底）、13（設定第 3 頁）、89（執行時隱藏，推論是遮罩）。
