# 第二場戰鬥的技能欄：activity 只釋放自己表上的元件

2026-10-18。程式 `a244d24`，基準 `7fa779b`，libsys4 固定 `247f544`。提交前、後的預設與 GBK 各 105 個模式 PASS。

## 症狀

同一次遊玩裡的第二場戰鬥（ASP 地城的營業部事件戰），技能欄第一次出現時疊在畫面左上角：

- 畫在 HP 條與教學遮罩之上，不跟著教學框縮放；
- 按不到；
- 換入支援角色之後恢復到左下。

第一場戰鬥、新地點的第一場戰鬥都正常。原版同一時點，技能欄在左下。

## 原因（實機紀錄加讀程式）

`PartsEngine.ReleaseActivity` 會把 activity 表上每個元件底下的整棵子樹一起釋放。

戰鬥裡，行動面板的底板把技能面板的 activity 掛在自己底下。戰鬥結束時，腳本先釋放行動面板、再釋放技能面板。接下來的連鎖：

1. 釋放行動面板時，技能面板的整棵樹被連帶拆掉。
2. 技能面板自己釋放時，走訪的是一棵空樹，所以它的五個技能選擇器沒有從使用者元件的管理器裡移除。
3. 下一場戰鬥用同一個名稱載入技能面板時，管理器以「已經註冊」為由跳過，一個選擇器都沒建。實機紀錄裡有五則對應的警告。
4. 腳本於是拿到上一場留下的選擇器。它們的底板已經不在（號碼 0），按鈕就被掛到圖層根的原點，壓在最上層，也不在教學框縮放的場景裡。

換人之後，技能面板改用另一個名稱載入，所以恢復正常。

## 原版依據

只做靜態分析，讀多娜多娜這一支執行檔：

- `ReleaseActivity`（`0x540050` → `0x55e400`）照 activity 的表一個號碼一個號碼處理（`0x55e450`–`0x55e4ed`）：先寫委派索引（`0x56d620`），跳過控制器的根（`0x53d660`），其餘只釋放那一個號碼（`0x539c80`、`0x579160`）。
- 釋放一個元件時，它的子元件改掛到它所在樹頂端的根下（`0x579160` → `0x53aa80` → `0x53b270` → `0x53b180`，根由 `0x534f00` 找）。

所以別人掛在 activity 元件底下的東西（另一個 activity 的根、腳本自己建的元件），在那個 activity 釋放後還在，連同自己的子樹。

## 做法

`src/hll/pe_v14_activity.c`：只釋放表上存在的號碼，跳過控制器的根，每個號碼寫一次委派索引，不再遞迴。v14 的 `parts_release` 本來就會把子元件改掛到控制器的根下。

這個綁定只看 AIN 版本、不分編碼，所以 SJIS 版的 v14 也改用這個釋放方式（和原版相同；沒有在 SJIS 版實機確認）。v14 之前的遊戲不受影響。

- **探針 `activity-release`**（4 案）：
  - 其中一案跑遊戲自己的位元組碼：加使用者元件、兩次載入、照戰鬥的順序釋放外層與內層，再用同一名稱重新載入。
  - 修改前 2/4 失敗：子樹被連帶釋放；管理器殘留兩筆；重新載入後沒有底板。見 [before.tsv](before.tsv)。
- **兩組 verify**：提交前、後的預設與 GBK 各 105 模式 PASS，見 [verify.tsv](verify.tsv)。
- **實機**（自動重播從第 2 天自動存檔到第二場戰鬥的路線）：
  - 技能欄一出現就在左下。
  - 教學框開著時，技能欄被縮進框內、隨遮罩變暗。
  - 和原版截圖三個時點並排一致：教學框開著時位移 (0,0)、平均差約 2（JPEG 雜訊）。

## 沒做與沒驗證

- **`RemoveAllActivityParts`** 仍連子樹一起釋放；原版只移動表項、不釋放元件。唯一的呼叫者是 activity 編輯器，一般遊玩走不到。
- **其他畫面**：
  - 同一行程第三場以後的戰鬥沒有實測。
  - 據點各頁、春銷結算、鑑賞模式這類巢狀使用者元件的畫面，只跑了上面的路線，沒有逐一確認「第二次進入」的情形。
  - 腳本的警告走 `system.Output`，移植版不印，所以「已註冊、跳過」的警告沒有全域計數。
- **移植版的選擇**：表上不存在的號碼不寫 −1（原版寫）；表滿（512 個元件）之後才建立的元件，修改後會留在圖層根下直到清層（本作最多 138 個，不會發生）。
- **其他平台**：Windows、Linux 沒有建置。
