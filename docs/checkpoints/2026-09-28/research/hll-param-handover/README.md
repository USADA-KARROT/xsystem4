## 缺陷（修前）

- **交出的參照沒有歸還**【讀】。v14 的 CALLHLL 對值型的 `hll_param` 參數，型別參數的低 16 位是 2、沒有 wrap 位元時，收到的值帶著一份屬於堆疊的參照（下面〈原版依據〉）。移植版 `hll_call` 呼叫後的收尾迴圈跳過每一個 `hll_param`，這份參照從來沒有還。
- **人物卡因此不解構**【量】。`PlayerWorkerViewCollection@CreateView` 以 `A_REF` 取得每張新卡的值、用型別參數 2 呼叫 `Array.PushBack` 推入，派出時用 `Array.Erase#1` 移除。量測建置在使用者存檔（第 8 天）的複本上量到：五張卡推入後各有 2 個參照，派出那張在 `Erase#1` 之後剩 1，另外四張在場景結束的 `RemoveComponent` 之後也剩 1，沒有一張解構；178 秒裡 155 次 `PartsEngine.ReleaseActivity` 沒有一次是卡片的。多出的那一個就是 `A_REF` 交給 `PushBack` 的那一份。
- **畫面**【量】。父版本建置的引擎截圖：派出之後，最前面那張卡的名牌前面多一個字、適性標記底下疊著舊的標記；轉盤轉動時，已派出的卡在最前面露出來。
- 診斷提出的其他候選（配對分數那段的 foreach、`ArrayExtensions::Select` 的回呼、`GetAllInstances` 的淺複製）都量到了，每一個的參照進出都平衡【量】。卡片所在的集合本身有解構（它的陣列也有釋放），所以不是「集合沒有解構」。

## 原版依據

### 反組譯看到的【反】

- **取參數**：CALLHLL（`0x66d470`）在 `0x66d5e8` 呼叫 `0x66a5e0` 建參數的 vector；每個參數經 `0x66a700` → `0x659970` 從堆疊取出，再以 `0x673c70` 搬進 vector（`0x659b70` 把來源的型別寫成 −1，所以是搬移，暫存物件的解構什麼都不放）。`0x66a700` 把 `hll_param` 設成型別 0x4a，壓縮的型別參數放在 +0x18；`ref hll_param`（0x4b）改成 0x4a 並加上 wrap 位元。
- **取參數時的 retain**：`0x659970` 只在 `0x6597f0` 與 `0x659670` 都成立時（`0x659a7e`..`0x659aa4`）以 `0x679f10` retain（`0x659aa7`）。`0x6597f0` 回答型別參數的 wrap 位元（bit 16，`0x659829`）；`0x659670` 回答「是物件」（低 16 位是 2 或 3，或帶 wrap 位元的純值；`0x6596a5`）。
- **呼叫後的 release**：呼叫、推入回傳值（`0x66d741`..`0x66d77a`）之後，在 `0x66d782` 以 `0x6734b0` 解構 vector（錯誤路徑在 `0x66d68e`、`0x66d70f`）；`0x673720` 對每個元素呼叫 `0x659d20`，它只問 `0x659670`，是物件就在 `0x659d46` 以 `0x679f90` release，不看 wrap 位元。`0x679f90` 在參照數是 1 時解構，否則減 1。
- **所以**：低 16 位 2、沒有 wrap 位元的物件值（2，以及 option 的 0x20002）是**交出**，呼叫後 release 一次；帶 wrap 位元的（0x10002、0x30002、介面 0x10003）取參數時 retain、呼叫後 release，是**借用**；低 16 位 1、沒有 wrap 位元是純值，兩邊都不動。低 16 位 3、沒有 wrap 位元的介面照同一條規則也是交出。
- **`A_REF`**（`0x66b790` → `0x6794d0`）：複製一頁，新頁唯一的參照屬於堆疊。
- **陣列存元素**：`PushBack`／`Add` 是在尾端 `Insert`（`0x6476b0` → `0x647990` → `0x646d70`）；存入時 `0x67f290` retain 新值、release 舊值；struct 陣列（元素型別 0xd）把來源 struct 的內容複製進元素，字串陣列（0xc）以 `0x65a1c0` 複製字串。所以原版的陣列持有自己的一份，呼叫交出的那一份在呼叫後放掉。

### 推論【推】

- `NEW`、函式的結果與字串運算式也帶自己的一份參照：沒有在位址上讀到。這和 [arg-ownership](../arg-ownership/README.md) 記的腳本函式引數「交出」是同一組產生者。
- 原版的春銷沒有殘留卡：只由上面的反組譯推得，原版這個畫面沒有拍（〈沒有原版畫面的項目〉）。

### 腳本端【AIN】

- 宣告值型 `hll_param` 參數的只有 Array 函式庫，14 個函式（`Realloc` 帶值的那一個、`PushBack`、`Add`、`Insert`、`Fill` 兩個、`Find` 與 `FindLast` 各兩個、`LowerBound`、`UpperBound`、`BinarySearch`、`IsExist`），每一個都是函式的最後一個引數。`ref hll_param` 只出現在回傳型別（`At`、`First`、`Last`、`Min`、`Max`），沒有函式拿它當引數。
- 型別參數 2 的值型呼叫點 2325 處：`PushBack` 2144、`Add` 84、`Insert` 46、`IsExist` 36、`Find` 11、`Find#1` 3、`Fill#1` 1。另有 `Add` 的 0x20002 兩處，帶的是字串。
- 在每個函式的控制流程圖上找每個呼叫點的值是誰產生的：2325 處、2326 個產生者（一個 `Find` 呼叫點有兩條路徑）：`S_PUSH` 1875、`A_REF` 235、`DG_CALL` 的結束目標 81、`NEW` 53、`CALLFUNC` 35、`CALLMETHOD` 29、`CALLHLL` 11、`S_ADD` 7。沒有借用型的產生者，也沒有從條件跳躍進來的。呼叫型的產生者 156 個，151 個讀得出被呼叫者，回傳型別都是值（字串 115、struct 36）；另外 5 個是方法編號來自 vtable 的 `CALLMETHOD`，探針只計數；讀 AIN 傾印，這 5 處的陣列都是字串陣列。
- 移植版這 14 個函式沒有一個「接收」交出的參照【讀】：`PushBack`、`Add`、`Insert` 自己加參照；`Fill`、帶值的 `Realloc` 複製或加參照；其餘只比較。所以歸還之後，陣列持有的參照不變。

## 做法

### 主線的決定

1. **照原版在 CALLHLL 的收尾歸還**，不在個別的 Array 函式改：只改 `PushBack` 的話，`IsExist`、`Find` 每呼叫一次仍留一份；原版的歸還也在 CALLHLL。
2. **`A_REF` 對 struct 共享頁照舊**：改成照原版複製會改變所有 v14 struct 的共享語意，範圍太大；這是 [arg-ownership](../arg-ownership/README.md)〈與原版的差異與限制〉記過的既有差異。
3. **只限 v14**：v11–v13 也有 CALLHLL 的第三個運算元，但沒有可測的遊戲；照 [arg-ownership](../arg-ownership/README.md) 與 [heap-version-boundary](../heap-version-boundary/README.md) 的界線，維持父版本的行為。
4. **字串不改**【移】：照原版歸還的話，陣列手上會留著帶暫存旗標的槽，之後元素被當成引數傳出去時，被呼叫者會把它當暫存值收下、不加參照，頁釋放時連陣列的元素一起放掉（推論，沒有實測，但風險明確）。
5. **不分字集**：判準不讀文字規則。
6. 實作後語義審查的兩個 Low（歸還在逐引數的迴圈裡、低 16 位 3 沒有守衛）與 `src/ffi.c` 註解把 retain 條件寫得簡略（Info）不改程式，寫進提交說明或 HANDOFF 的待辦（〈和原版仍不同的地方〉、〈提交說明的讀法〉）。

### 實作【讀】【移】

- 新函式 `hll_param_handed_over`：v14、型別參數的低 16 位是 2、沒有 wrap 位元。不要求型別參數大於 0（原版只看位元）。
- 取參數時，把一槽的 `hll_param` 值記下來（option 的第一槽本來就記）。【移】用取參數當下的值，不從呼叫後的堆疊讀：原版也是把彈出的值搬進 vector、呼叫後由 vector 解構；這樣 HLL 重入 VM 時覆寫堆疊也不受影響。
- 呼叫後的收尾迴圈遇到 `hll_param`：判準成立、而且記下的值是有效、活著的頁（struct、陣列、delegate）時歸還一次。字串、none 的 option（值是 −1）都不碰。

### 適用範圍

歸還以 `ain->version >= 14` 為閘（記下的值只在那裡讀），v13 與 v11 照父版本的規則（HP7 守）。不讀文字規則：預設（SJIS 規則）與 GBK 在修前修後失敗與通過的案、失敗訊息都相同，下面每個突變在兩種字集失敗的案也相同。

## 和原版仍不同的地方

1. **字串**【移】：型別參數 2 的字串值照這個 VM 的暫存旗標處理，陣列和呼叫者共用同一個槽；原版的呼叫也歸還字串，陣列存自己的複本。每推入一個字串留一份參照，修前修後相同（HP6 守）。
2. **`A_REF` 共享一部分頁**：有參照成員的 struct、struct 的陣列，這個 VM 共享同一頁，原版複製（既有差異）。現在呼叫歸還的是共享多加的那一份；陣列的元素和呼叫者的物件仍是同一頁。
3. **沒有 wrap 位元的介面**（低 16 位 3：0x3、0x20003）：原版也是交出，這裡不處理；本 AIN 沒有這種呼叫點，也沒有案檢查這一點。
4. **歸還的時機**：歸還在逐引數的迴圈裡，最後一份參照的解構子會在排在它後面的引數寫回之前、也在呼叫的結果推入之前執行；原版的 vector 在推入結果之後才解構（`0x66d782`）。本 AIN 每個值型 `hll_param` 都是最後一個引數，HP8 斷言這一點。
5. **沒有綁定的函式**：引數照舊直接丟掉、不歸還；HP8 確認每個型別參數 2 的呼叫點都有綁定。
6. v14 之前的行為是移植版自己的，原版沒有讀。

## 驗證

### 探針

說明與各案內容見 [harness](../../harness/README.md) 的 `probe/hll_param_handover_fixture.inc` 一條與探針檔頭。載入真的 AIN，經真的 `hll_call`；卡片的 activity 是合成的，不用遊戲資產；每案在子行程跑。

- 修的案 HP1–HP4：HP1 用遊戲自己的 `CreateView`（真函式的兩個 frame）推入與 `Erase#1` 移除一張卡：推入後卡片只剩陣列的 1 個參照；移除後卡片解構，`CActivityWrap` 的解構子與 `AFL_Activity_Release` 各一次、`PartsEngine.ReleaseActivity` 對它的名字一次；集合放掉時不再多放。HP2 經真的 `hll_call` 以型別參數 2 交出一個這個 VM 的 `A_REF` 會共享的 struct：`PushBack`、`Add`、`Insert` 之後剩呼叫者與陣列各一，`IsExist` 之後剩呼叫者，兩者都放掉後解構一次。HP3 其他的頁：共享的（struct 的陣列、另有持有者的 delegate）與 `A_REF` 做出的複本（數字陣列、delegate、純數值 struct），複本在 `PushBack` 之後只屬於陣列、`IsExist` 之後就釋放。HP4 option 0x20002 帶的 struct 也是交出，none 不動。
- 守衛 HP5–HP8：HP5 wrap、wrap 的 option、介面是借用，型別參數 1 不碰任何槽；HP6 字串照舊；HP7 v13 與 v11 照舊；HP8 上面〈腳本端〉的靜態前提（每個型別參數 2 的值都由交出型的指令產生、被呼叫者回傳值、每個呼叫點都有綁定、每個 `hll_param` 都是 Array 函式的最後一個引數），工作清單滿了或放棄追蹤時算環境失敗。
- 期望值的出處：上面的反組譯。屬於移植版的是：陣列和呼叫者共用 struct 的頁、字串（HP6）、v11–v13（HP7）。HP1 另要遊戲啟動時才有的東西（PartsEngine 的 `_PreLink` 形式、使用者元件的清單以空陣列代替），卡片不跑建構子，由探針放進 worker、id 字串與真的 `AFL_Activity_Create` 給的 activity。

### 跟著改的既有探針【讀】【量】

- **釘著這個洩漏的數字往下改**：
  - `arg-ownership`：更新事件的紀錄不再殘留（`AddPartsUpdateEvent` 以 `A_REF` 把區域的紀錄交給 `Array.PushBack`）。AO1 一次 `FrameImageCache@Join` 留下的 box、紀錄、清空的 delegate 頁由 25、1、1 變成 25、0、0；AO4 的 199 輪由 398、199、199 變成 398、0、0；AO2 清單放掉後，delegate 頁比呼叫前少一頁（引數那一頁）。wrap 區域變數的 box 是另一個機制，不變。
  - `array-literal`：AL2 的「其他 slot」由 9 個變 3 個：CG 圖層物件（`SelectableIndexArray<T>@Insert` 以 `A_REF` 交給 `Array.Insert`）與隨它留下的 5 個 slot 不再殘留。11 個 wrap box 不變；剩下的 3 個（2 個空字串、1 個 `CASPosF`）修前就在、種類相同，來源沒有追（〈範圍外的發現〉）。
- **合成方式改成照交出語意**：這三個探針原本以型別參數 2 交出一個只有探針自己一份參照的值，位元組碼不會這樣交（HP8）；修正之後呼叫會歸還一份，探針接著用那個值就讀到已釋放的頁或少一個參照。
  - `fill-copy-extra`：交給 `Fill#0` 的值改成一份複本（照這個 VM 的 `A_REF` 對純數值 struct 的做法），呼叫者保留原物件；加一條「呼叫後交出的複本已經釋放」。原本的斷言（每個元素各自獨立、寫入不外漏、heap 回到基準）都保留。
  - `dialogue-model`：以型別參數 2 呼叫 `Find` 之前，先替交出的值加一份參照（照 `A_REF` 共享有字串成員的 struct），先斷言它不是純數值 struct；`held` 仍是 1 的斷言保留。
  - `array-construct` 的 AC15：推入前同樣先斷言、再加一份參照；期望值仍是 2，組成寫明是陣列的一份加探針的一份，交出的那一份由呼叫歸還。
- 其他相關的模式（`working-cards`、`activity-release`、`option-array`、`aref-value`、`v13-heap`、`heap-version-boundary`、`parts-leaks`）沒有改，修前修後都通過。

- **以前靠洩漏活著的物件現在會解構**：解構子比以前早跑。看得到的是人物卡與顧客總覽的顧客卡（上面）；沒有 activity 的腳本物件有沒有也提早解構，沒有逐一追，只看了路線與實機的錯誤行（0）與 ASan 那一趟（0）。
- **activity 的實例編號改變**：腳本若用編號找 parts，可能找到別的；沒有查。
- **天數**：實機只跑到第 9 天的春銷與第 10 天的據點；之後沒有跑。
- **別的 v14 遊戲**：若有值型 `hll_param` 不是最後一個引數，排在後面的引數寫回會晚於解構子（〈和原版仍不同的地方〉第 4 條）；本 AIN 沒有。

## 範圍外的發現

1. **`array-literal` 剩下的 3 個 slot**（2 個空字串、1 個 `CASPosF`）：修前就在，編號與種類修前修後相同，和這次的修正無關；從哪裡來沒有追（要在量測建置上做參照追蹤）。探針照舊把它們當已知殘留釘住。
2. **春銷第 9 天的內容每趟不同**：同一支建置跑兩趟就有兩種內容（上面〈實機〉），比較跨趟次的畫面時要先確認是同一個內容。
3. **路線判定規則把 heartbeat 印出的堆疊行當成錯誤**：這一組用的判定已改（上面〈提交後驗收〉）；共用的範本與其他組的副本還是舊規則，要跟著換，否則戰鬥路線可能又被判成 1 個錯誤。
4. **沒有綁定的 Array 函式**（`FindLast`、`UpperBound`）呼叫時引數直接丟掉；遊戲沒有以型別參數 2 呼叫它們。
