# 存檔縮圖

2026-10-12。基底 `313ecf2`。

這一步讓存檔寫出縮圖檔，讀取清單的每一列因此顯示存檔當時的畫面。同一次推送另外把舊版引擎的系統呼叫 `SYS_PEEK` 恢復成上游的行為（最後一節）。

## 症狀

修改前：存檔之後存檔資料夾裡沒有 `Thumb*.qnt`，讀取清單每一列左邊是一塊深灰。原版在同樣的操作之後有 `Thumb0000.qnt` 與 `Thumb1000.qnt`，清單顯示存檔當時的據點畫面。

原因不是縮圖寫壞，而是 v14 的 `PartsEngine.SaveThumbnail` 一直綁在一個空函式上（`src/hll/pe_v14_message.c`）。`src/parts/parts.c` 既有的 `PE_save_thumbnail` 是 `PartsFunc` 第 6 格用的另一個函式（第二個參數是縮小的倍數，上游定的），這個遊戲走不到；它沒有被動到。

## 原版依據

只來自多娜多娜這一支執行檔、它的 AIN 與它產生的縮圖檔；沒有執行。標「偽代碼」的只看了反編譯的偽代碼，標「量測」的是對原版的檔案或截圖量出來的，其餘讀過反組譯。

| 項目 | 位址 | 內容 |
| --- | --- | --- |
| `PartsEngine.SaveThumbnail(string SaveFileName, int ThumbnailWidth)` | 分派格 `0x57bccc` → `0x56d140` | 寬 0 以下當 1；高 = 寬 × 畫面高 ÷ 畫面寬（整數除法），至少 1（`0x56d27c`–`0x56d28f`）；截取整個畫面、縮小、寫檔；**寫檔的結果不看，回傳 true**（`0x56d3a8`–`0x56d426`） |
| 截取 | `0x5aba30` → `0x468890` → `0x468440`（偽代碼） | 建立畫面大小的表面，呼叫場景的繪製再把結果複製進去。`0x468440` 就是 `ChipmunkSpriteEngine.Update` 每一幀用的同一個繪製函式（`0x468a91`），所以截的是呼叫當下重畫一次的整個場景，不是上一幀留在畫面上的東西。轉場進行中（`TRANS_Begin` 與 `TRANS_End` 之間，`0x468969` 看的旗標）改畫轉場（`0x468760`，用上一次的進度） |
| 縮小 | `0x5a7a10`（圖形程式庫的第 `0x3c` 格） | 轉給第 15 格 `0x492d30`：每個目的像素取它覆蓋範圍內來源像素的面積加權平均（兩個方向的覆蓋長度相乘當權重，`0x492f10`–`0x492f86`），三個通道各以 64 位元累加後除以來源的寬×高、向零截斷（`0x493011`–`0x493056`），不寫 alpha |
| 檔案格式 | 量測（三個原版的縮圖檔一致） | QNT 版本 2、標頭 68 位元組、24 位元、沒有 alpha 平面；像素資料是 zlib 等級 9（把解開的資料用等級 9 重壓，和原檔逐位元組相同）；高是奇數時補的那一列是 0 |

腳本這一側（AIN）：

- `ThumbnailCapture::Capture`（FUNC 30449）以寬 124 把畫面存到編號 0（`Thumb0000.qnt`，當暫存）；呼叫點是據點按下「存檔」時（在確認框出現之前）、回合結束、選地城確認。所以縮圖是按下存檔那一刻的畫面，不含確認框。
- 存檔成功之後 `ThumbnailCapture::Copy` 以 `system.CopySaveFile` 把 `Thumb0000.qnt` 複製成那一筆的編號；腳本有一個連縮圖一起刪的函式（FUNC 6244），但讀取清單的垃圾桶走的是另一個只刪存檔本身的函式。
- 給引擎的檔名是 `system.GetSaveFolderName() + "\\" + 檔名`（FUNC 6242）。清單那一端用 CG 名稱 `<save>Thumb%04d.qnt` 設一般的 CG 元件。

## 做法

- 新檔 `src/parts/thumbnail.c` 的 `PE_SaveThumbnail`：照 `0x56d140` 算寬高 → 重畫場景（`scene_render()`）→ 讀主表面 → 以精確的面積平均縮小（每個來源像素依覆蓋的面積加權，結果截斷）→ 寫成和原版同樣形狀的 QNT → 一律回傳 true（寫不出來只印警告）。
- QNT 由引擎自己寫：libsys4 的寫出函式產生的是 52 位元組的標頭、一定帶 alpha 平面，和原版的檔不同，而子模組不動。
- 路徑：腳本給的名稱開頭是存檔資料夾的名字（`SaveData\`），去掉之後寫進引擎自己的存檔資料夾，和已讀表、`<save>` 的 CG 名稱同一種處理。
- 綁定（`src/hll/pe_v14_message.c`）：只有 v14 而且 AIN 把這個函式宣告成 `bool (string, int)` 才換上新函式；其他宣告形狀保留原本的空函式。
- 清單那一端不必改：`<save>` 前綴的 CG 名稱本來就會從存檔資料夾載入，檔案不存在時元件沒有圖（就是先前看到的深灰塊）。

## 驗證

- 探針 `save-thumbnail`（7 案，見 [harness](../../harness/README.md)；場景是探針自己產生的圖樣，期望的像素由探針裡另寫的模型算出）：在這一步之前的引擎上 7 案裡 5 案失敗（其餘是守衛：別的宣告形狀保留空函式、舊的 `PE_save_thumbnail` 輸出不變）。預設與 GBK 兩組 verify 各 99 個模式通過，sanitizer 沒有報告（[預設](verify-default.txt)、[GBK](verify-gbk.txt)，[修改前後的輸出](before-after.txt)）。
- 縮圖檔和原版的縮圖檔比：尺寸（124×69）與格式一致；把原版的三個檔與這裡寫出的檔各自解開再用這裡的寫出函式編回去，都和原檔逐位元組相同。這裡的縮圖和存檔前一刻的畫面做面積平均（截斷）的結果，在畫面靜止的區域逐像素相同。
- 讀取清單和原版並排（同一串操作：新遊戲 → 據點存檔 → 讀取）：縮圖在同樣的位置、同樣的大小，畫面上的像素就是檔案的像素；從據點進去與從標題進去都看過。讀檔與返回標題的重啟之後清單仍然顯示。
- 第 2 天的據點存檔再讀檔（只有這一邊）：縮圖是第 2 天的據點，讀回來的天數、金錢與角色相同，清單三列（含自動存檔）都有縮圖。
- 刪除存檔（垃圾桶）：存檔與清單上的那一列消失；縮圖檔留在資料夾裡——清單的垃圾桶走的腳本函式只刪存檔本身（原版在同一個操作之後資料夾裡的樣子沒有對照）。
- 兩個 commit 之後（[摘要](gui-summary.json)）：十條既有路線、存讀檔的四條與確認框的六條在最終的執行檔上各跑一次，沒有斷言或 VM 錯誤，對白的行數與雜湊和上一步的紀錄相同（不快進的那一條 224 行，和上一步的 226 行互為前段）；有存檔的路線，存檔資料夾裡多出縮圖檔（`mirror` 3 個、`saveload` 3 個、`backtitle` 2 個、`load-haruuri` 3 個）。

## 與原版還不同的地方

- **轉場進行中存縮圖**：原版得到轉場混合中的畫面，這裡得到沒有轉場效果的場景。腳本的三個呼叫點附近沒有看到轉場，實機也沒有遇到。
- 縮圖裡被按的那顆「存檔」按鈕：原版是滑鼠停在上面的黃色，這裡的自動路線是另一種顏色。存檔前的整個畫面就已經這樣，不是縮圖造成的；原因沒有查。
- 檔名：原版照腳本給的完整路徑寫；這裡去掉存檔資料夾的名字後寫進引擎自己的存檔資料夾（同一個資料夾裡的同一個檔名）。
- 寬或高超過 8192 不寫檔（引擎自己的上限；腳本固定給 124）。
- 檔名只處理「存檔資料夾的名字加檔名」這一種；絕對路徑或帶 `..` 的名稱沒有擋（腳本固定給前一種）。縮圖檔是直接覆寫，寫到一半失敗會留下不完整的檔。
- 兩邊的畫面本身不同（亂數、字型），所以縮圖檔不會逐位元組相同。

## 沒做與沒驗證

- 原版的對照只有第 1 天據點的材料：第 2 天、自動存檔的縮圖、刪除存檔之後資料夾裡的樣子，原版都沒有並排；沒有為這一步另外執行原版。原版在縮圖檔不存在時清單長什麼樣沒有查。
- 讀取畫面的「自動存檔」分頁沒有點進去。這條路上原版的存檔是確認框、不開清單，別處有沒有帶縮圖的存檔清單沒有找。
- 刪除之後再存（編號重用時蓋掉舊縮圖）只有探針驗過。
- 真的元件畫到主表面再被截下來這條路探針走不到（探針沒有視窗的繪圖環境畫不出一般的元件），靠實機的幾條有存檔的路線與上面的逐像素核對。
- 螢幕上真的視窗（高解析度、全螢幕）沒有看；截的是引擎自己的主表面，理論上不受視窗大小影響。
- 幾條不存檔的短路線，行程的峰值記憶體比上一步的紀錄高 30 到 60 MB（其他路線有高有低）；沒有另外量，也沒有找原因。
- Windows、Linux 沒有建置。

## 舊版引擎的 `SYS_PEEK`

和縮圖無關，是比對這個分支與上游時看到的既有回歸，隨這一步一起修：舊式系統呼叫 `SYS_PEEK`（v14 之前的 `system.Peek`）在移入 v14 的 VM 核心時（`14c2618`）被加上一次畫面繪製與換頁，後來（`44964f9`）加上「`UpdateView` 沒有負責呈現時才做」的條件——v14 之前的遊戲沒有 `UpdateView`，所以那個條件對它們恆成立，每一次 `Peek` 都多畫一次並換頁；上游只處理事件。恢復成上游的行為。多娜多娜的腳本沒有任何舊式系統呼叫，v14 的 `system.Peek` 是另一個函式（`src/hll/system.c`），不受影響。沒有用任何一款舊遊戲實跑過。

## 適用範圍

- 新的縮圖函式只在 v14、而且 `PartsEngine.SaveThumbnail` 宣告成 `bool (string, int)` 時生效；依據只有這一支執行檔。`PartsFunc` 第 6 格的 `PE_save_thumbnail` 與 v14 之前的程式沒有變（探針有一案釘住它的輸出）。
- 存檔的格式沒有變；存檔資料夾會多出 `Thumb*.qnt`。先前存的檔沒有縮圖檔，清單上照舊是深灰塊。
