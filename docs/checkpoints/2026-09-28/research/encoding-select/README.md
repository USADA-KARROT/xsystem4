## 缺陷（修前）

- **Shift-JIS 遊戲被當成 GB18030**【讀】【量】。`main` 在讀進 AIN 之後算 `gb18030_detect_strings` 的分數；寬鬆分數（前 100 個字串中，逐位元組找得到「0xA1..0xDF 後接 0x40 以上」的字串數）大於 5 就設 `ain_is_gb18030`，印偵測與 AINCHECK 兩行；嚴格判定成立才另外開字元規則（再印一行），不成立時印「GB18030 check not confirmed」。Shift-JIS 的雙位元組字，第二個位元組落在 0xA1..0xDF、後面接下一個字的首位元組，就會命中。英文版戰國蘭斯（v5）與英文版多娜多娜（v14）的字串表都被誤判：第一層開、字元規則仍是 SJIS。這個旗標沒有任何地方設回 false。
- **沒有選擇編碼的方法**【讀】。沒有 `--encoding`：`--encoding=gbk` 是 getopt 不認得的選項（印警告、忽略），`--encoding gbk` 因為多出一個位置引數而用法錯誤結束；`.xsys4rc` 的 `encoding` 鍵靜靜忽略。`XSYS4_STRING_CHARSET` 只改字元規則，不改第一層。
- **AINCHECK**【讀】。判定的區塊裡留著一行縮排錯的除錯警告，寬鬆分數成立的每一款遊戲都印（多娜多娜也印）；[2026-09-26 的蒸餾審查](../distill-review-2026-09-26.md)就列為臨時檢查。
- **6 號馬賽克**【讀】【量】。著色器的格子從畫面的一角（GL 視窗座標的原點）起排，大小是 128 × 進度的三角（沒有取整），每格取格子中心的顏色；原始碼自己留了 FIXME，說原點應該在中心。進度 0 與 1 時大小是 0，取樣座標沒有定義，這台機器上整張都取到同一個像素（探針 MZ9、MZ10：12000 個像素中 11999 個不是逐像素的交叉淡入）；0..1 以外的進度大小是負的。
- **6 號效果在哪裡用到**【AIN】。英文版戰國蘭斯的 AIN 至少有 28 處要它（靜態掃描：直接呼叫場景函式的 16 處，加上一個包裝函式的 12 處；其他包裝沒有逐一追），遊戲前段就有兩次（各 2000 毫秒）。多娜多娜用不到（〈多娜多娜不變〉）。

## 兩層開關與判定規則

### 兩層開關【讀】

| 層 | 變數 | 誰用 |
|---|---|---|
| 第一層 | `ain_is_gb18030` | GB18030 的文字路徑：沒有 `.fnl` 時字元碼的換算、繪字的字元步進、v14 parts 的文字、找不到資產時改用 GBK 名再找等 |
| 第二層 | libsys4 的字元規則（`sys4_set_string_charset`，預設 SJIS） | String 函式庫、VM 的字元讀寫、`%D` 等（[GBK 字元規則](../gbk-string-rules/README.md)） |
| 兩層都開 | `game_charset_is_gbk()` | 遊戲字串與 UTF-8 的轉換：存檔資料夾的名字、視窗標題、記錄、檔名 |

修前寬鬆分數只開第一層，所以被誤判的 Shift-JIS 遊戲是「第一層開、第二層關」；`game_charset_is_gbk()` 仍是假，存檔資料夾與視窗標題照 SJIS 解。現在兩層一起開、一起關，`XSYS4_STRING_CHARSET` 照舊最後只改第二層。

### 判定（沒有指定編碼時）【讀】

- 嚴格判定（`gb18030_detect_strings` 的回傳值，這一組沒有改）：前 100 個字串中，**在 Shift-JIS 字元邊界上**找得到那個位元組對的超過 5 個；全部字串中「Shift-JIS 不合法、GBK 合法」的至少 16 個；有非 ASCII 位元組的字串中，合法 UTF-8 的不到一半。三個都成立才開兩層。
- 寬鬆分數不再決定任何事。嚴格判定成立的表，寬鬆分數一定也大於 5（邊界上的命中也是逐位元組掃描的命中），所以嚴格判定成立的表照舊。
- 外層「字串表不是空的才判定」拿掉：判定函式對空表什麼都不讀、回不成立。

### 三份 AIN 的分數【量】

唯讀量測（引擎修前的 `--audit` 記錄，以及照判定函式另寫的量測工具；證據審查另用獨立實作重算，數字相同）：

| AIN | 版本 | 字串數 | 寬鬆分數 | 邊界分數 | SJIS 不合法、GBK 合法 | 合法 UTF-8／非 ASCII | 嚴格判定 | 修前第一層 | 修後 |
|---|---|---|---|---|---|---|---|---|---|
| 多娜多娜繁中版 | 14 | 38310 | 92 | 92 | 1419 | 22／6143 | 成立 | 開 | 開（不變） |
| 英文版戰國蘭斯 | 5 | 9655 | 27 | 0 | 0 | 0／3471 | 不成立 | 開（誤判） | 關 |
| 英文版多娜多娜 | 14 | 38457 | 22 | 0 | 0 | 0／5871 | 不成立 | 開（誤判） | 關 |

- 兩份英文版的寬鬆分數全部是 Shift-JIS 雙位元組字的第二個位元組接下一個字的首位元組，每個字串依第一個命中分類：漢字 14 與 21 個，平假名 12 與 1 個，符號 1 與 0 個。兩張表都沒有「Shift-JIS 不合法、GBK 合法」的字串。（[v13 稽核](../v13-audit/README.md)第 1 條推測主要是平假名；實際多數是漢字。）
- 多娜多娜繁中版三個條件的餘裕都很大：邊界分數 92 對門檻 5，1419 對 16，UTF-8 22 對 6143 的一半。

### 誤判在英文版戰國蘭斯上實際影響什麼【讀】【量】

- 它有自己的 `.fnl` 字型，字元表是 Shift-JIS；這種字型的字元碼不看第一層。所以「把 SJIS 位元組當 GB18030 解、畫出別的字」是沒有 `.fnl`、用一般字型的遊戲才會走到的路，這款遊戲沒有走到。
- 字元步進：訊息表 78271 句中 2038 句、字串表 9655 個中 3471 個有非 ASCII 位元組，用 Shift-JIS 與 GB18030 兩種步進切出來的邊界全部相同（半形片假名只出現在 3 處，切法也相同；由此推論都在字尾）。
- 所以修前在走過的路線上只看得出記錄多三行（〈英文版戰國蘭斯冒煙〉），畫面與對白不受影響；收緊的價值在語義：Shift-JIS 遊戲不該走 GB18030 的路，沒有 `.fnl` 的遊戲與半形片假名後面還有字的字串才會出事。英文版多娜多娜的字串表有 2 個字串兩種步進切法不同，它的 v14 parts 文字也看第一層；這一版沒有實機跑。

## 做法

### 主線的決定

1. **沒有指定編碼時只看嚴格判定**【移】：寬鬆分數只記錄；Shift-JIS 遊戲誤觸時什麼都不印（每一款日文遊戲都會誤觸，「not confirmed」那一行沒有資訊量）。
2. **兩層一起切，命令列優先**【移】：`gbk` 兩層都開、`sjis` 兩層都不開（嚴格判定成立也一樣）；`XSYS4_STRING_CHARSET` 維持「最後、只改字元規則」的語義（A/B 對照的用法不變）。
3. **照上游的想法自己重寫**【移】：選項與 rc 鍵的寫法、警告的字句、順序照上游 `71dbfda`；不搬上游 libsys4 的 GBK 語義，也不搬上游對存檔路徑計算位置的改動（下面〈不照上游的部分〉）。
4. **馬賽克照原版**【移】：實作時先照上游 `4233c7d`（另加下限 1）；語義審查第一次反組譯了原版，格子大小與取樣點和上游不同。修正時選照原版改（不保留上游的算式只寫明差異），主線提交時確認。原點在中心這一點上游和原版相同。
5. **一個提交**：編碼與馬賽克在同一個提交（探針在同一個檔）。
6. 提交後戰鬥路線落在一個沒有代表的分群，主線以「九條中八條通過，加人工判定」放行（〈提交後驗收〉）。

### `--encoding` 與 `.xsys4rc` 的 `encoding` 鍵【讀】【移】

- 值是 `sjis` 或 `gbk`，不分大小寫（同上游）。其他值（空字串也算）印一行上游同一句的警告後忽略：命令列是 `Invalid value for --encoding option: "<值>"`，rc 是 `Invalid value for encoding in config: "<值>"`。
- 順序：全域的 `.xsys4rc`（`$XSYSTEM4_HOME`）先讀，再讀遊戲資料夾的，最後是命令列，後者蓋前者。命令列可以寫成 `--encoding=<值>` 或兩個引數；給了幾個，以最後一個為準。rc 裡錯的值留下它前面的設定；命令列只檢查最後一個值，所以最後一個錯時留下的是 rc 的設定，不是更早的 `--encoding`。
- 沒有指定：上游沒有判定、一律 SJIS；移植版保留嚴格判定當預設，多娜多娜繁中版不用加任何選項。用法說明的預設因此寫「detected」（上游寫「sjis (default)」）。
- `gbk` 經 `gbk_string_rules_enable` 開兩層；`sjis` 什麼都不開（兩層本來就是關的：寫這兩層的只有這裡與 `XSYS4_STRING_CHARSET`）。

### 不照上游的部分【讀】【移】

- **上游 libsys4 的 GBK 支援（`e2bf438`）不搬**：上游用一個全域旗標把整組字元函式換成 CP936；移植版的字元規則照中文原版，和上游不同的有：字元碼是 `(lead << 8) | trail`（上游 `lead | trail << 8`）、索引越界回安全值（上游中止）、`%D` 照原版用 Shift-JIS 的位元組（上游改成全形標點）。移植版已經有自己的兩層開關，`--encoding` 只決定它們；libsys4 固定 `247f544`，這一組不動 submodule。
- **存檔路徑的計算位置不搬**：上游把它移到讀完 `.xsys4rc` 之後，讓遊戲名用設定的編碼解。移植版的存檔資料夾在判定之後由 `save_dir_for_game_charset`（沒有改）依兩層開關決定，搬了會改到多娜多娜預設的存檔資料夾算法。

### 適用範圍

不分 AIN 版本（探針用 v5 與 v14 的合成表）。對 Shift-JIS 遊戲是刻意的改變：只有寬鬆分數成立的表，現在第一層是關的，和寬鬆分數沒有成立的 Shift-JIS 遊戲一直以來一樣。嚴格判定不成立的 GB18030 表（如果有這種遊戲）會失去寬鬆分數給的第一層，要用 `--encoding=gbk`。被誤判的 Shift-JIS 表加 `XSYS4_STRING_CHARSET=gbk`，修前兩層都開，現在只開字元規則（EN29），這是收緊的結果，不是環境變數的語義改了。

## 6 號馬賽克

### 原版依據（反組譯）【反】

- **呼叫鏈**：`Sact2.dll` 的 Effect（`0x1000de50` → `0x1000ab20`）在 `0x1000ac28` 經介面呼叫效果外掛 `GLEffectCopy.dll`（介面在 `0x10009e1b` 從外掛取得）。外掛的效果方法 `0x100044b0` 以效果號碼索引跳表 `0x10005138`，6 號 → `0x100045fe` → 時間迴圈 `0x10005940`。
- **格子大小**（`0x10005940`）：t 是經過的毫秒、T 是長度，t < T 時：half = T >> 1；t < half 時 d = t，否則 d = T − t；c = ((96·d / half，無號除法) 清掉最低位) + 1。所以 c 是奇數：t = 0 時 1；長度 98 毫秒以上時一半處 97、t = T − 1 時 1。每一張畫面以整數 alpha 255·t / T 經兩張查表混合兩個場景（表的內容沒有讀），畫完一張 Sleep(1)；t ≥ T 時畫最後的新場景。
- **畫一張畫面**（`0x10002560`）：第一欄與第一列不是空的時，寬與高是 (W/2) % c 與 (H/2) % c（`0x100025d0`..`0x100025ea`，除以 2 向零取整），之後每格 c，畫面邊上剩下的是不完整的格子。所以格線過 (⌊W/2⌋, ⌊H/2⌋)、間隔 c。每一格以它**第一個像素**（x、y 最小的那一個）的 3 個位元組填滿（`0x10002730`..`0x1000278f`）。
- **view mode**：Sact2 的 Effect 只在 view mode 0 呼叫外掛。mode 由 VIEW_GetMode 回傳（`SactEngine.dll` 的 `0x1000fe40`；建構子在 `0x1000d660` 設 0，Sact2 只在 VIEW_SetMode 經 `0x10010dd2` 改它）。mode 1 時轉場交給 SactEngine（Sact2 的 `0x1000ac80`，傳 t / T 的 float），那條路沒有讀。
- 【AIN】英文版戰國蘭斯的 AIN 沒有宣告 SACT2 的 VIEW_ 與 TRANS_ 函式，所以這款遊戲一直在 mode 0、走上面這條路。

### 推論【推】

- **第一個像素是左上**：外掛表面的第 0 列是畫面上緣，是推論：`SurfaceFactory.dll` 的像素位址方法（`0x10001080`，vtable `0x10008100` 的 +0x08）查一張列表，第 i 列從基底往後 i 個 pitch（`0x100012a9`）；Sact2 的表面是不是在那裡建、引擎的第 0 列是不是上緣，沒有追。移植版這邊紋理的第 0 列是畫面上緣是讀到的（`WV_TRANSFORM`），探針的交叉淡入對照與取樣案也一致。
- **奇數尺寸**：寬或高 n 是奇數、c > 1、n/2 是 c 的倍數時，依 `0x10002560` 迴圈的模型，最後一欄或一列不畫；移植版會畫。兩款遊戲的畫面都是偶數（800×600、1280×720）。
- 短的長度：比 98 毫秒短時兩端大於 1，其中奇數長度的最大值超過 97（3 毫秒時 193），由算式推得。

### 移植版的著色器【讀】【移】

- 格子大小 c = max(2·⌊48·tri(p)⌋ + 1, 1)，tri(p) = 1 − |2p − 1|：奇數，進度 0 與 1 時 1、一半時 97。p 在 0..1 時，照精確算術、長度是偶數時等於原版的算式（d / half = tri(t/T)，⌊⌊96x⌋/2⌋ = ⌊48x⌋）。下限 1 只擋 0..1 以外的進度（DrawEffect 與 SACT2 的 TRANS_Update 傳的是腳本給的值，【讀】），那時就是逐像素的交叉淡入。
- 原點 ⌊解析度 / 2⌋，格內偏移是 (像素 − 原點) 對 c 取餘數，兩軸都一條格線過原點。
- 取樣點是每格第一個像素的中心。左與上邊不完整的格子起點在畫面外，紋理夾邊（`init_texture`，`gfx_copy_main_surface` 用的就是它）讓它取到畫面上的第一個像素，和原版相同。
- 舊的 FIXME 與註解掉的平均版刪掉（上游也刪了）。
- 著色器是執行時讀的檔；這一組的 C 程式在多娜多娜上只少印一行記錄，著色器在多娜多娜上不會載入（〈多娜多娜不變〉）。

### 和上游 `4233c7d` 的差別

上游把格子的原點移到畫面中心（這一點和原版相同，保留）。沒有保留的：格子大小 ⌊128·tri(p)⌋（0 到 128；進度 0、1 附近是 0，取樣座標沒有定義）、取樣在格子中心、另算一個和中心差 c 的整數倍的格線偏移（數學上多餘）、中心沒有取整。上游原樣在探針上，進度接近 0 與 1 的逐像素案（MZ9–MZ12）各有 12000 個像素中 11999 個不對（探針審查的錯誤版本實測）。

### 和原版仍不同的地方

1. **著色器只拿到進度，不是時間與長度**【移】：照精確算術，偶數長度和原版相同。以 SACT2 迴圈的 float 進度 t / T、假設 IEEE float32 捨入的模型【量】：2 到 4000 毫秒的偶數長度與 5000、6000、8000、10000 毫秒，共 4,031,000 個時刻中有 2291 個比原版小 2（1000、2000 毫秒 0 個，1500 毫秒 2 個，3000 毫秒 5 個）；3 到 1999 毫秒的奇數長度，999,999 個時刻中 29205 個不同；97 毫秒以下的奇數長度，原版的格子會超過 97（移植版最大 97）。遊戲前段的兩次都是 2000 毫秒。
2. **顏色**【移】：移植版是 GPU 依進度的 mix；原版是 255·t / T 的整數權重查表。2000 毫秒效果的模型，每個通道差到 2 或 3 級（看兩張表怎麼捨入）。
3. **奇數尺寸的最後一欄或一列**（上面的推論）：原版不畫，移植版畫。
4. **節奏**：移植版 SACT2 的效果迴圈（沒有改）約每 16 毫秒畫一張，原版每張之間 Sleep 1 毫秒。
5. **範圍**：這些規則來自讀過的這一個外掛、view mode 0 那條路；別的遊戲的外掛與 view mode 1 沒有讀。著色器服務所有畫 6 號效果的遊戲，也包括原版在 view mode 1 畫它的遊戲。

## Not covered（探針檔頭，`encoding_fixture.inc`）

探針檔頭列的是：

1. 編碼決定之後 `game_charset_is_gbk()` 選的存檔資料夾（`main` 在 `--audit` 返回之後才走到）。
2. `.xsys4rc` 的 `encoding` 不是字串（ini 的讀取對每個以字串讀的鍵都會讓引擎停下）。
3. 引擎真的畫面表面上、遊戲執行中的馬賽克。
4. 逐像素的案（c = 1）取樣點離像素中心最多半個 texel（那裡紅綠容許 1；取樣案要完全相等）。
5. 原版交叉淡入的顏色：以 1/255 的整數步進加權（這裡是 GPU 依進度的 mix；2000 毫秒效果的模型每個通道差到 2 或 3）。
6. 原版以整數毫秒的長度、著色器以進度算格子大小而捨入不同的時刻（奇數長度，或不能以二進位精確表示的進度落在兩個大小的交界）。

提交說明的 Not covered 另列：最後一個 `--encoding` 之前的合法值（錯的值放在合法的之後）、原版在奇數尺寸不畫的那一欄或一列、view mode 1 的畫法；多娜多娜的 `--encoding=sjis` 與戰國蘭斯的 `--encoding=gbk` 只用 `--audit` 看過；引擎的路線截圖不是檢查。另外，多娜多娜的表嚴格判定成立由 `gbk-detect` 守，EN33、EN34 守的是 `main` 怎麼用判定（判定本身被改時，EN33 只回報環境失敗）。

## 風險

- **對 Shift-JIS 遊戲是刻意的行為改變**：只有寬鬆分數成立的表，第一層現在是關的。走得到 GB18030 路的只有沒有 `.fnl` 的遊戲與半形片假名後面還有字的字串；有 `.fnl` 的英文版戰國蘭斯走過的路線上看不出差別。
- **嚴格判定不成立的 GB18030 遊戲**：如果有，會失去寬鬆分數給的第一層，要加 `--encoding=gbk`。
- **馬賽克**：依據是一個外掛、一條路（view mode 0），畫面沒有並排；顏色與少數時刻的大小和原版不同（上面）。
- **路線的焦點條件**：戰鬥路線的分群受視窗焦點影響，基準與受測的焦點條件不同時，判定會因為分群而不過；顯示器睡眠會讓點擊悄悄失效（〈範圍外的發現〉）。

## 範圍外的發現

1. **GUI 驗收的視窗焦點**：引擎的焦點初值是「有」，只有先有焦點再失去才擋輸入。遊戲在背景啟動（或螢幕鎖定時啟動）全程沒有焦點、點擊照常；有焦點的趟中途碰上顯示器睡眠，之後的點擊全部失效，而桌面游標沒有動，現在的游標檢查抓不到。戰鬥路線的分群也受焦點影響。GUI 驗收應該記下視窗的焦點、防止顯示器睡眠，基準與受測用同一種條件。
2. **只經 fork 的子行程編不出新的著色器**（這台 Mac 實測）：harness 裡在 fork 子行程畫圖的既有 GL 探針，靠的是著色器已經在系統的快取裡；改著色器的組，突變或新寫的著色器在那些探針裡會畫不出來。這一組的馬賽克探針改用 posix_spawn；其他探針沒有改。
3. **英文版戰國蘭斯有一句開頭的兩個全形空白沒有佔位**：修前修後一樣（兩種步進都走 2 個位元組、字元碼走 `.fnl`），不是這一組的問題，另案。
