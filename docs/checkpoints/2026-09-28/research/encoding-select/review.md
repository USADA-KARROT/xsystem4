# U2 審查摘要

程式 `6e4e673` 提交前的審查、提交後驗收時戰鬥路線分群的調查與覆核，以及提交之後、推送之前的文件覆核。每一份都由獨立的審查者做，只讀工作副本，自己的實驗放在隔離副本；結論與處理照錄，細節在私人紀錄。

## 探針審查（實作前）

結論：通過，沒有 High、Medium；3 個 Low、4 個 Info，都在實作前處理。審查者在 `8f9cd6d` 的隔離副本套一份照上游想法寫的草稿實作當基準，再逐一套 25 個錯誤版本（只開一層的 `gbk`、讓位給判定的 `sjis`、命令列先於 rc、先讀到的 rc 為準、錯值重設成自動、大小寫敏感、選項的引數可省略、`XSYS4_STRING_CHARSET` 提前套用、寬鬆分數仍開第一層、空表跳過判定、留著 AINCHECK；馬賽克的原點在角落、沒有下限、round 代替 floor、只有一軸置中、取樣在格子角等）：24 個被抓到，失敗的案都和事先寫下的預測相同；被引用的程式行、三份 AIN 的分數與 6 號效果的呼叫點也重讀過，和補查一致。

- Low：馬賽克取樣點的容許差等於半個 texel，偏半格的錯誤版本存活。處理：取樣案的紅綠改成要完全相等；逐像素案（格子 1）維持容許 1，寫進探針檔頭的 Not covered。
- Low：探針檔頭把「fork 的子行程編不出新的著色器」寫成一般事實，量測也沒有留輸出。處理：改成「在 macOS 上實測」，私人紀錄補上留下的症狀證據。
- Low：照上游把存檔路徑的計算移到讀完 rc 之後，可能改到多娜多娜的存檔資料夾，而探針沒有守。處理：實作不搬（研究〈不照上游的部分〉），寫進 Not covered；提交前的實機啟動另外記下存檔資料夾的名字。
- Info：暫存資料夾的名字含有選項名（警告檢查的「鍵名」可能被路徑自動滿足，改了前綴）；幾個小案例沒有涵蓋（補了空值、重複的 `--encoding`、全域 rc 的錯值三案）；期望值只依上游的馬賽克（當時不改；之後語義審查找到原版的依據，改照原版）；私人工具的註解引錯節號。

## 實作後的兩份獨立審查

**語義與原版**（先修再提交；1 個 Medium、1 個 Low、4 個 Info）：編碼的一半和上游的想法一致：`gbk` 兩層都開、`sjis` 兩層都不開、沒有指定只看嚴格判定，`XSYS4_STRING_CHARSET` 仍在最後只動字元規則，rc 的順序、大小寫、錯值都對，沒有搬上游 libsys4；多娜多娜的三個條件餘裕都很大。審查者第一次靜態反組譯了英文版戰國蘭斯的效果外掛，另寫 8 個突變。

- Medium：6 號馬賽克只有原點照原版，格子大小與取樣點和原版不同；研究寫的「原版沒有反組譯、只依上游」不成立。處理：修正時選照原版改（格子大小、原點取整、每格第一個像素），見下一節；原版依據寫進研究〈6 號馬賽克〉。
- Low：EN33 不是「多娜多娜嚴格判定成立」的獨立守衛：判定本身被改時它只回環境失敗。處理：探針不改；提交說明寫明判定本身由既有的 `gbk-detect` 守，EN33、EN34 守的是 `main` 怎麼用它（審查的那個突變就是 `gbk-detect` 抓到的）。
- Info：探針驗分數失敗時沒有清掉暫存資料夾（留下字串表的複本，只在本機）；嚴格判定不成立、只有寬鬆分數成立的 GB18030 表，修後兩層都關（寫進提交說明與研究〈適用範圍〉）；編碼語義和上游一致（逐行讀碼與突變證實）；奇數畫面尺寸時原版的中心和上游差半個像素（那時的案都是偶數尺寸；改照原版之後加了奇數畫面的案）。

**證據與量測**（通過；2 個 Low、3 個 Info）：從原始輸出重算修前、突變、verify、九條路線、片頭、三份 AIN 的分數（另寫一份判定的實作）、英文版戰國蘭斯各趟與對照建置，都和報告一致；截圖打開看過。

- Low：春賣路線「歷來可比的趟都沒有那次懸停」沒有證據檔。處理：審查者重數為 40 趟，提交說明用 40。
- Low：「懸停跟著建置的位置、不是改動造成」樣本小（兩趟對四趟），語氣偏強。處理：提交說明寫成推論，並寫明時段、負載與工作資料夾沒有排除。
- Info：「建置 0 警告」沒有證據（完整重建有既有的警告）；「記錄唯一的差別是少了 AINCHECK」說得太廣、「畫面逐位元不變」沒有直接量（提交說明寫成判定、開關與存檔資料夾不變，路線的畫面另比）；小筆誤。

## 修正（馬賽克照原版）與複審

修正者自己逐行核對了原版的兩個函式，把著色器改成照原版（格子大小 1 到 97 的奇數、原點 ⌊解析度/2⌋、每格第一個像素；拿掉上游數學上多餘的格線偏移，下限 1 只擋 0..1 以外的進度），探針改了期望、補了奇數畫面、0..1 以外的進度與最大格子四案（19 案）；修前與突變都和事先寫下的預測一致（每個突變由預測的那一案抓到），兩組 verify 通過，戰國蘭斯的兩趟長跑走過兩次 6 號效果、錯誤 0。

複審（通過；2 個 Low、3 個 Info）：自己重跑探針、修前與 44 個突變（修正者的 32 個加自己的 12 個）都和預測相同，原版位址自己核對過，紋理夾邊與方向也查過。

- Low：「長度是偶數時和原版逐位元相同」說得太滿：float32 下少數交界時刻差 2。處理：提交說明改成「照精確算術」，另寫 float32 模型的計數。
- Low：探針檔頭「交叉淡入每個通道可能差 1」沒有依據。處理：審查者的模型是差到 2 或 3；提交說明查證時把探針檔頭的這一句改成 2 或 3（只改註解，重跑兩組 verify）。
- Info：奇數尺寸時原版的最後一欄或一列在某些格子大小下不畫（寫進提交說明與研究〈和原版仍不同〉）；「第一個像素是左上」的推論有了補強（像素位址方法的列表）；改照原版超出開工時「照上游」的範圍，而且依據只有一個版本的外掛（主線提交時確認照原版，範圍寫進研究）。

## 提交說明的逐句查證

先修再提交；4 個 Medium、5 個 Low、4 個 Info，提交前全部處理。查證者把說明裡的位址全部靜態重讀一次（呼叫鏈、算式、alpha、第一個像素、Sleep），量測自己重算或抽查。

- Medium：寬鬆分數的命中寫成假名的第二位元組，量測多數是漢字；浮點模型的長度範圍寫錯；交叉淡入的誤差和同一個提交的探針檔頭矛盾；原版 Effect 還有 view mode 1 那條路（走 SactEngine 自己的轉場），說明沒有交代。處理：四處都改了（漢字、平假名、符號的計數；正確的長度範圍與時刻數；探針檔頭改成和說明一致；新的一段寫 view mode 0 與 1，並以 AIN 確認英文版戰國蘭斯沒有宣告 VIEW_ 與 TRANS_ 函式）。
- Low：「兩端是 1、一半是 97」對很短的奇數長度不成立；「最後一欄或一列不畫」少了 c > 1 的條件；說明用了審查者自己取的函式名；13 張每 150 毫秒的截圖出自另一趟 50 秒的執行；最後一個 `--encoding` 錯時「前面的設定」指哪一個有歧義。處理：五處都改了。
- Info：突變一句括號裡的數字容易讀錯；一處文法；首行把既有的嚴格判定寫成新增；遠端已前進（模式數要改）。處理：前三處改了；最後一項在主線提交時改（下一節）。

## 提交與提交後

主線提交時接到遠端最新的 `672f0d0`（G15 的文件提交）：`env.sh` 與 `runtime_probe.c` 和 G13、G14 修正、G15 的改動取聯集（模式 140），`src`、`include`、`shaders` 與新探針的差異除 index 行外不變，提交說明只改了講 rebase 的一段與模式數。主線的決定：沒有指定編碼時只看嚴格判定；照上游的想法重寫、不搬上游 libsys4；馬賽克照原版；做成一個提交。

提交後的驗收跑了三次：前兩次修前與兩組 verify 都通過，路線因桌面游標在執行中被移動而作廢；第三次修前、兩組 verify 與八條路線通過，戰鬥路線照規則不過，片頭的第三趟因游標動了 0.3 像素作廢、補跑後組層級通過（研究〈提交後驗收〉）。

## 戰鬥路線分群的調查與覆核

**調查**（判定：執行間的分群，不是這次改動造成）：同一個提交的建置與父版本程式的建置交錯各跑幾趟；這一群在改動之前的兩支舊建置也出現過，彼此只差 1 到 3 下；分群和遊戲視窗有沒有輸入焦點有關（歷來有焦點的 15 趟中 4 趟是這一群，沒有焦點的 86 趟沒有），提交後那一趟有焦點、基準沒有。調查時發現顯示器睡眠會讓有焦點的趟之後的點擊悄悄失效（游標檢查抓不到），那一趟作廢；之後的趟在執行中防止顯示器睡眠。判定規則補了這一群的代表趟，門檻與點擊規則照舊。

**覆核**（同意判定；另有三點更正與限制）：從原始記錄自己重算每一趟的分群與距離（逐趟和調查相同）。

- 調查對成因的說法要改：分歧不是放開與換人之間的毫秒競態，而是這一群有輸入範圍記錄的兩趟（都是這次的建置）在第 29 下按下後 64 與 93 毫秒就開了下一個輸入範圍（前 28 下相同的 C 群要約 5 秒後、點過別的目標才開；10/19 的兩趟舊記錄沒有這類行）；是什麼讓遊戲提早往下走沒有查明。處理：研究寫的是更正後的說法。
- 父版本的建置在有焦點的條件下沒有跑出這一群，「改動之前就有」只靠兩支舊建置（環境設定和現在不完全相同）；在有焦點、前 28 下和既有的 C 群相同的趟裡，落在這一群的：這次的建置 2/2、舊建置 2/2、父版本 0/2（其中一趟因桌面游標移動作廢，點擊序列仍可比），樣本太小，不能排除改動讓這一群更常出現；依據是改動碰不到這條路徑（判定結果與兩層開關相同、馬賽克著色器不載入、事件時間沒有系統性偏移，覆核自己查過）。處理：研究、HANDOFF 寫明這個限制；父版本有焦點的加跑沒有做（列在〈沒做與沒驗證〉）。
- 這一群的代表趟原本取受測的建置自己跑的一趟，等於自己當自己的參照。處理：改用改動之前的舊建置那一趟（和原本的差 1 下，判定結果相同）。
- 另：把「171 行」與「點擊位置」改成對最近的代表會真的放寬檢查（離代表太遠只會寫說明、不會失敗），要採用就得另加距離的門檻。處理：不採用，維持「八條通過加人工判定」。

## 文件推送前的覆核

程式 `6e4e673` 提交與提交後驗收之後、程式與文件推送之前，兩份獨立的覆核：證據（重算提交的內容與接到 `672f0d0` 時的聯集、提交說明 14 句的抽查（含 6 句原版位址的靜態重讀）、提交後驗收的每一步與戰鬥路線的放行，以及文件裡的數字）與公開（程式提交與這一組文件的公開內容、推論與移植策略的標示、守衛、既有文件的更正、自己跑一次套用的排演並逐檔比對）。證據判通過（4 個 Low、3 個 Info）；公開判程式可以推送、文件先修再套用（1 個 Medium、4 個 Low、4 個 Info）；沒有 High。處理只改文件，程式不 amend：

- Medium（公開；證據的一個 Low 是同一件）：研究〈提交後驗收〉把「第 29 下按下後 64 到 93 毫秒就開了下一個輸入範圍」寫成這一群的四趟都有，實際只有這次建置的兩趟有這類記錄，10/19 的兩趟舊記錄只看得到放開落空；「其他群要幾秒後」實際只比了前 28 下相同的 C 群。處理：研究改成只說量到的兩趟、舊的兩趟標成推論；本檔〈戰鬥路線分群的調查與覆核〉的同一句也改了。
- Low（證據）：「父版本 0/2」的兩趟中一趟因桌面游標移動作廢，公開檔沒有註明；「既有某群」指的是 C 群。處理：研究與本檔兩處都補註、改寫。
- Low（證據）：程式提交說明講 rebase 的一段在提交時就把提交後的重跑寫成已做；提交後逐項核實都成立，但沒寫戰鬥路線照規則不過。處理：程式不 amend；研究〈提交說明的讀法〉第 1 條補一句。
- Low（證據）：私人的判定工具與調查報告沒有照覆核更正成因與代表趟的說明（判定實際載入的已是改動之前的那一趟，公開檔寫的是更正後的說法）。處理：不在這次文件修正的範圍（只改公開文件與套用工具），交給主線另改。
- Low（公開）：研究裡春賣懸停的推論，主句是肯定的語氣。處理：改成「很可能」，括號照舊。
- Low（公開）：HANDOFF〈驗證〉與 harness README 的補記把「只經 fork 的子行程編不出新的著色器」寫成 macOS 的一般性質。處理：兩處加「這台 Mac 實測」，HANDOFF 待辦的同一條也加。
- Low（公開）：最上面的狀態與 HANDOFF〈提交後驗收〉只寫「改動之前就出現過」「樣本小」，沒寫不能排除改動讓這一群更常出現。處理：README、STATUS、HANDOFF 最上面的一段與 HANDOFF〈提交後驗收〉都補上，研究的路線表同一格也補。
- Low（公開）：既有文件的更正漏了 STATUS 與 HANDOFF 的 GBK 字元規則一節「舊偵測與嚴格判定都成立時才開」，以及 GBK 字元規則研究把英文版多娜多娜的誤判寫成由回編推定的兩處。處理：四處都補記（後兩處補上引擎修前的實測：寬鬆分數 22，邊界分數與 SJIS 不合法而 GBK 合法都是 0）。
- Info：公開的四個是提交說明沒寫不搬上游 libsys4 的理由（研究有寫）、第一段的「ran」對英文版多娜多娜指的是修前的 `--audit`（這兩個是可選的〈提交說明的讀法〉補充）、上游 libsys4 的三點差異沿用先前的私人研究而這次沒能重讀，以及排演通過並提醒補這一節的計數；證據的三個是作廢的片頭第三趟補算也會通過（補跑沒有選擇性偏差）、0.3 像素的游標變動沒有查原因、沒有獨立重算的項目與磁碟空間。依這些 Info 沒有改文件（計數照補，重新排演照做）。

都沒有 High。
