# 自動輸入與游標：真實滑鼠接手、排程的滑過、拖曳與滾輪

2026-10-20。程式 `ecc7aff`，基準 `052941f`（前一組程式 `ac2356e`），libsys4 固定 `247f544`。提交前、後的預設與 GBK 各 112 個模式 PASS。

這是 UI 盤點後的第一組，屬於測試工具的前置工作：之後要修的滑過事件、滾輪、右鍵與中鍵，都要靠自動路線做得出這些動作才能驗收。

## 症狀

- 程式只要設定過一次游標位置（自動點擊，或腳本移動游標），之後就一直讀那個位置，真實的滑鼠移動被忽略。使用者在自動測試的視窗裡拖橫桿拖不動，就是這個原因。
- 自動點擊每一下都經 `SDL_WarpMouseInWindow`，會移動使用者真實的桌面游標。
- 自動排程只能按左鍵，做不出滑過、拖曳、滾輪、右鍵與中鍵。

## 原版依據

只做靜態分析，讀多娜多娜這一支執行檔。

- `Mouse_MovePosImmediately` 經滑鼠物件（`0x498856` 的虛擬呼叫）移動游標。視窗的移動是 `SetCursorPos`（`0x4c0e00` → `0x4c1200`，視窗沒有最小化、點在客戶區內才移），讀取是 `GetCursorPos`（`0x4c0ce0`）。虛擬呼叫接到 `0x4c0e00` 是推論。之後真實的滑鼠照樣移動游標。
- 遊戲腳本裡會移動游標的只有一個函式，經由一個包裝函式呼叫，而那個包裝函式只被沒有人呼叫的函式與除錯選單呼叫；系統服務的移動游標函式從未被呼叫。所以一般遊玩不會移動游標。

## 做法

- **設定的位置有來源**（warp、auto），遇到下一個真實的移動、按鍵或滾輪事件就結束，改回讀真實滑鼠。
  - 排程按著鍵的期間，以及放開之後到下一次輸入更新讀到這次放開為止，真實移動不會搶走游標，所以排程的點擊與拖曳會在指定的位置放開。
- **排程的游標算在視窗內**：回報「游標在不在視窗」的幾個函式（SACT2、IbisInputEngine、InputDevice、vmCursor）看到排程的游標時，滑鼠這一半算在視窗內（鍵盤焦點照舊，見限制）。多娜多娜的腳本會用到這個回傳值。
- **不移動桌面游標**：
  - 排程的每一步都不 warp。
  - 有排程，或設了 `XSYS4_NO_DESKTOP_WARP` 時，腳本的移動也只動程式自己的游標。
  - 有界 GUI 執行器（`run-gui-bounded.py`）每次都設這個開關。
  - 兩者都沒有時（一般遊玩），腳本的移動照原版移動真的游標。
  - 定時點擊（`XSYS4_AUTO_CLICK`）同樣不移動桌面游標，最後一次點擊現在會放開（以前一直按著）。
- **排程格式**（`XSYS4_AUTO_CLICK_SEQ`）：
  - 舊的 `T,X,Y`（左鍵點擊）意思不變。
  - 新增 `click`、`rclick`、`mclick`、`move`（可在指定時間內直線移過去）、`down`、`up`、`drag`、`wheel`。
  - 滾輪一次輸入更新送一格，最多 1000 格。座標有上限，內插用 64 位元。
  - 完整的格式與規則見 [harness](../../harness/README.md) 的「排程輸入」一條（探針是 `probe/auto_input_fixture.inc` 一條）。
- **追蹤紀錄**：記下排程的輸入、每一格滾輪、滑過目標的變化，以及每張截圖時的游標位置與來源。
- **適用範圍**：輸入層不分遊戲版本。沒有排程、也沒設 `XSYS4_NO_DESKTOP_WARP` 時（一般遊玩），腳本的移動照舊 warp，唯一的改變是設定的位置在下一個真實的滑鼠事件就結束（以前永遠保留）。

## 驗證

- **探針 `auto-input`**（13 案，說明見 [harness](../../harness/README.md)）：
  - 修改前 13/13 失敗（多數是新功能本來沒有，覆寫不結束、排程點擊會 warp 等是真的行為差異），見 [before.tsv](before.tsv)。
  - 51 個故意改壞的突變都有案例抓到。
- **兩組 verify**：提交前、後的預設與 GBK 各 112 模式 PASS，見 [verify.tsv](verify.tsv)。
- **例行路線**：
  - normal150、haruuri、fightr、config、backlog、savedialog、garage、sysmenu 與片頭重播都跑完：exit 0、錯誤 0，對白和前一組逐字相同。
  - 點擊目標：片頭重播與其他路線都相同。fightr 對基準差 141 處：基準那一趟序號 64 的自動點擊（第 65 下）碰上切換到結算畫面，只按下、沒有形成點擊（170 下）；這一趟 171 下沒有少，所以之後整串錯開一格（對齊之後差 72 處）。另外從序號 21（第 22 下）起，有位置相同、點到不同元件的戰鬥時序差別（同一個執行檔跑兩趟也會這樣）。
  - 片頭 50 張畫面仍和參考解碼器逐像素相同。
  - 見 [routes.tsv](routes.tsv)。
- **桌面游標沒有動**：每條路線前後記錄真實游標的位置，都相同；修正時另在每趟期間定時取樣（每 1–10 秒一次，共 619 次），也都沒動。截圖時的游標來源沒有一張是 warp。
- **示範路線**（提交前的建置）：
  - 在設定第 1 頁拖曳訊息速度的橫桿：把手跟著游標走，誤差 1.5 px 以內。
  - 只把游標移到據點與系統選單的按鈕上：按鈕換成滑過圖。
  - 在劇情回顧上滾輪：引擎收到每一格，各在不同的輸入更新。清單不捲，因為滾輪訊息本來就沒送給腳本（之後的滾輪那一組）。

## 沒做與沒驗證

- **沒有用真的滑鼠試**：真實移動接手、放開後的保護，只在探針裡用模擬的事件驗過。
- **腳本實際看到幾格滾輪**沒有驗：有一次兩格只隔 1 ms（兩次輸入更新緊接著），一幀只讀一次滾輪的腳本可能只看到一格。
- **鍵盤焦點**照舊：視窗沒有鍵盤焦點時，回報游標位置的幾個函式回假。無人值守時若有人切到別的程式就會遇到。
- **右鍵、中鍵**只在探針驗過；它們送給腳本的訊息是之後那一組的範圍。
- **一般遊玩時腳本移動游標**的分支沒有在實機走到（一般遊玩不會呼叫）。
- **排程本身的限制**：兩步至少隔一幀；兩步之間真實游標可以接手滑過狀態，有人移動滑鼠經過視窗時截圖不可重現；排程一直按著鍵時真實移動搶不到。見 harness README「排程輸入的限制」。
- **其他遊戲**：v14 之前的遊戲（戰國蘭斯）與英文版沒有用這一組的建置跑。v14 之前每次 `system.Peek` 都算一次輸入更新，放開後的保護與滾輪的分格在那些遊戲上的時間比較短（見 harness README）。
- **其他平台**：Windows、Linux 沒有建置。
