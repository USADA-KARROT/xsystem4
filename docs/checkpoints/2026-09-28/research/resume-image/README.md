# R1a：v14 引擎快照的讀回

2026-11-16。程式提交 `372c83e`（2026-11-16）、父提交 `1667e11`（W1 的文件提交；W1 程式 `2227b07`）；libsys4 固定 `247f544`。審查經過見 [review.md](review.md)；逐案的修前修後見 [before-after.tsv](before-after.tsv)，提交前後的套件、路線、片頭與專項見 [verify.tsv](verify.tsv)。程式推送的三方核對記在 [HANDOFF](../../HANDOFF.md)。

這一組是引擎快照讀回的第一段（讀回正確性）：只讓移植版自己寫的快照讀得回來、讀回之後堆積是 VM 預期的狀態。快照旁邊腳本要一起存的東西（部件、地圖的引擎端狀態）還沒有還原，讀不回時仍然結束程式，那是之後的段落（部件與呼叫框的還原是下一組 R1b，見[讀回後的場景狀態](../resume-scene-state/README.md)）。**所以兩個重試鈕在下一組之前仍然不算能用**（給玩家的說法見文末）。提交之後才查清楚：讀回之後操作不正常的原因之一在 VM 讀回本身——呼叫框的幾個內部欄位沒有還原，這一組的「讀回正確性」沒有涵蓋到（見〈仍有差異與未涵蓋項目〉）。

用語：**引擎快照**（VM 映像）是腳本以 `system.ResumeSave` 把整個 VM（堆積、呼叫堆疊、區域頁）寫成的檔，`system.ResumeLoad` 讀回。預設格式是 rsm（以名字存函式與結構；移植版寫的是 libsys4 的 rsm 第 9 版），另一種是 json（以編號存）。**盒子**是移植版給 v14 的 wrap 值所用的一格 struct 頁，沒有結構編號（編號 -1）。**保護頁**是開機時放在第 0 號槽的一個 64 格陣列頁，用來吸收寫進第 0 號槽的值。

## 問題與量測（修前）

腳本在地圖上走一格、進戰鬥等時候寫引擎快照（開始回想的重播之前也寫一份）；遊戲結束畫面的兩個重試鈕（回到戰鬥之前、回到一格之前）與重播結束時讀回。v14 的遊戲用預設格式時讀不回：

- **實機【量測】**：上一組已推送的最佳化執行檔 `5858e23f`（程式 `2227b07`），從標題讀第 15 天的存檔複本、在敵方數值調高的遊戲資料複本上全滅。回到戰鬥之前：按確定約 2 秒後程式結束（退出碼 1，`load_rsave_frame` 的變數型別檢查）；回到一格之前：同樣約 2 秒後結束（退出碼 134，`free` 偵測到二次釋放）。沒有任何提示，上次存檔之後的進度會不見。回想的重播：重播一放完程式就結束（退出碼 134，訊號 6；提交後關卡另跑一趟量到）。B2 那一輪另量到回到戰鬥之前印出結構的錯誤後結束（退出碼 1），以及新開局路線的教學戰選回到戰鬥之前時當掉（退出碼 139）。
- **原因【讀程式】【量測】**：前期研究對 30 個 rsm 快照樣本離線逐槽模擬讀入（另一位研究者獨立重查，沒有一條被推翻），找到三個互相獨立的缺口，修前兩個重試鈕的失敗形式各對到一個：
  1. **盒子**：寫出端對結構編號無效的 struct 頁寫空的結構名；讀入端把空名解成 -1 之後直接讀結構表的第 -1 項（越界讀）。結果看那塊記憶體剛好是什麼：印出和真正原因無關的結構錯誤後結束、在印字時當掉（退出碼 139），或剛好通過。每個樣本裡有 5.7 萬到 63 萬個這種頁，每個樣本第一個讀不過的都是這種頁。W1 之後區域變數不再配盒子，但 struct 成員與陣列元素的 wrap 初值、複製 wrap 值時做的盒子仍是這種頁，數量少了很多，快照裡一定還有。
  2. **同名的多載函式**：v14 裡函式可以同名（本作 37,742 個函式裡 5,524 組同名、共 11,191 個）。區域頁與返回紀錄只寫名字，讀入時取同名的第一個。進戰鬥的快照裡有兩個函式因此被解成別的多載：變數數或型別對不上，呼叫框的雜湊也不符。前一個缺口剛好通過時，就在這裡以退出碼 1 結束——修前實機的回到戰鬥之前就是這一種。舊檔沒辦法靠形狀挑對：5,524 組裡有 4,901 組含變數數、型別與雜湊都和另一個相同的成員。
  3. **空閒清單與懸空指標**：rsm 讀入後沒有重建空閒清單（json 那條路有）；清空堆積時釋放了字串與頁，但沒有清掉槽的型別與指標。映像裡是空的那些槽留著已釋放的指標，下一次回收把其中的字串再釋放一次（頁那一類的型別值是 0，回收器會跳過）。進地圖的快照讀入時沒有報錯、之後才中止，就是這一種——修前實機的回到一格之前（退出碼 134）。json 一樣留著懸空指標，只是比較晚才踩到；json 讀回後也沒有重建 delegate 目標表（物件被釋放時，要刪掉指向它的 delegate 項目，靠的就是這張表）。
- 另有兩個修好上面三個之後才會遇到的缺口：第 0 號槽的保護頁在 rsm 讀回後變成空頁（寫出時存的「維度減一」是 -1，讀入端把它當成空陣列）；陣列頁的 struct_type 超出結構表範圍的值存不下來（這一組不處理，見〈仍有差異與未涵蓋項目〉）。
- 檔案格式本身裝得下這些東西（名字欄是任意字串、libsys4 的函式查找已支援「名字#序號」），是讀寫兩端沒有對齊。

## 和原版寫的快照的對照

這一組改的是移植版在 rsm 第 9 版裡的寫法與讀入端的對齊，以及讀回後堆積的內部狀態。**有對照過原版寫的快照【量測】**：真實存檔資料夾裡有兩份原版引擎在 Wine 下寫的引擎快照（只讀複製、離線解析；樣本含遊戲狀態，只在私人報告），兩份都完整解析到最後一個位元組。原版寫的是 **rsm 第 14 版，是另一套配置**：wrap 沒有自己的頁（變數直接存被包的 struct 的槽號，空的是 -1；陣列元素空的是 0）；函式名帶參數型別，多載各有自己的名字；第 0 號槽是全域頁；沒有函式名表、沒有每個物件的序號。移植版寫的是 libsys4 的第 9 版，libsys4 也只讀得了 4／6／7／9 版。**兩邊互不相容**：修後的讀入程式讀這兩份，在 libsys4 的版本檢查就被拒（不支援的格式）；原版讀不讀得了第 9 版沒有驗證。所以「空結構名」與「名字#n」是移植版在第 9 版裡自己的記法，兩者都沒有出現在原版的映像裡。

**這一組不追求和原版的快照相容**：要讀或寫第 14 版，得在 libsys4 加一版解析，並轉換整個堆積模型（wrap、槽號、指令位址、函式名、delegate），是另一個量級的工作。引擎快照（重試與回想用的那兩三份）是同一次執行裡寫後讀。依據是移植版的程式、libsys4、前期研究對樣本的量測與上面的對照；期望值是「寫出端寫了什麼，讀入端就讀回什麼，讀完的堆積是 VM 其他部分預期的狀態」。照規定沒有執行原版。

## 修改【讀程式】

只改引擎三個檔：`src/resume.c`、`src/vm.c`、`include/vm.h`（另加 harness 的新探針與模式清單）。對應六項：

1. **沒有結構編號的 struct 頁**：`load_rsave_struct` 遇到空的結構名，建編號 -1 的頁、照抄值，不查結構表、不做成員型別檢查（沒有結構可以對）。名字不是空的但 AIN 裡沒有，或以編號存的結構編號超出範圍：明確報錯，不再越界讀。同一條規則也用在區域頁的函式名：`load_rsave_frame` 查不到函式名（含空名）時明確報錯，修前那裡讀的是函式表的第 -1 項。寫出端不變（檔案格式不變）。
2. **多載函式的符號**：寫出端新增 `function_symbol()`：同名裡不是第一個的函式寫「名字#n」，n 由 libsys4 現成的 `ain_get_function_index` 算（同名清單裡依函式編號的位置，從 0 起算）；第一個照舊只寫名字，所以沒有多載的映像位元組不變。區域頁的函式符號（`frame_page_to_rsave`）與返回紀錄的呼叫者（`save_call_stack_to_rsave`）兩處都改。讀入端新增 `resolve_function_name()`，照 libsys4 的 `ain_get_function` 解析；因為它會在「#」處就地截斷傳進去的字串，傳給它的是複本。沒有「#」的舊檔照舊取同名第一個，不猜。struct 頁的建構子與解構子名、檔頭的函式名表不改（讀入端不用它們）。不改 libsys4。
3. **空閒清單與懸空指標**：清空堆積的 `delete_heap`（兩種格式共用）把每一槽的型別與指標一併清掉；rsm 讀入後重建空閒清單，用的是 json 那條路原本就用的同一個函式。
4. **delegate 目標表**：兩種格式讀入後都先重設、再從堆積裡的頁型別重建（rsm 原本從檔案的標記重建，結果等價；json 原本沒有重建）。
5. **第 0 號槽的保護頁**：兩種格式讀入後，放掉第 0 號槽原本的東西，換上一個和開機時一樣的新保護頁（參照數 1、陣列頁、元素 void、64 格、維度 0、struct_type 0、全 0；序號沿用映像的）。做在讀入端，所以修前寫的 rsm 檔讀回也對；寫出端不改。建這個頁的程式抽成 `vm.c` 的 `vm_alloc_guard_page()`，開機（`vm_execute_ain`）與讀回共用，並明確把 struct_type 與維度設成 0（從頁快取拿到的頁會留著舊的陣列欄位）。
6. **呼叫堆疊的框數**：兩種格式讀入時，在填呼叫堆疊之前先數框數，超過固定陣列的大小（4096）就明確報錯。修前兩種格式都直接寫過陣列尾。

除了 delegate 目標表（只有 v14 才有），其餘修改都不分 AIN 版本；沒有跑過 v14 之前的遊戲。

新加的錯誤訊息用名字的複本（`message_name()`）：`display_sjis0` 每次呼叫都會釋放上一次的緩衝區，錯誤處理先印出訊息、再印呼叫堆疊（印的時候會呼叫它）、最後再格式化一次訊息，直接把共用緩衝區當參數，第二次格式化會讀到已釋放的記憶體（第一次修正時 sanitizer 版實測到）。**既有的錯誤訊息沒有改**：其中四則（讀呼叫堆疊的函式裡兩則、映像檔讀不了的兩則）仍把共用緩衝區傳給錯誤常式，只有損壞或讀不了的檔才走得到，那時程式本來就要結束；留到失敗時的處理那一段。

**這一段不做**：先驗證再拆、讀不回時回到腳本（仍以退出碼 1 結束）、錯誤訊息照原版做成要玩家確認的對話框、寫快照失敗時的回傳、返回位址落點等額外驗證（都屬失敗時的處理）；部件與其他引擎端狀態的存出與讀回、畫面（屬下一組）；預設格式不改（改成 json 只是讓崩潰晚一點出現，檔案大約 12 倍）；檔案格式不改（新檔和舊檔只差後面那些多載的「#n」）；libsys4 不改；和原版第 14 版的快照互通。

## 連帶的行為改變【讀程式】

1. 新寫的 rsm 檔：只有同名裡不是第一個的函式，區域頁與返回紀錄的符號多了「#n」，其他位元組不變。
2. **預設格式讀入之後的配置**：新物件從最小的空閒槽拿（和 json 讀入、開機時相同）；以前是從堆積尾端拿新槽，或第一次配置就開始回收。所以讀入之後的槽號、堆積擴大與回收的時機都不同。
3. **修後的引擎讀修前寫的檔**：盒子、空閒清單、第 0 號槽、delegate 目標表都對；多載照舊取同名第一個——變數不同時（或呼叫框的雜湊不同時）讀入被拒（明確報錯、程式結束）；變數數、型別與雜湊都和同名第一個相同時**不會報錯，靜靜讀成第一個**，返回位址落在別的函式的程式碼裡，之後的行為不確定。真實樣本裡沒有出現這種框（出現的兩個非第一個多載形狀都不同，會報錯）；引擎快照（重試與回想用的那兩三份）是同一次執行裡寫後讀，所以要有舊版本留下的快照才會碰到。（實作後的語義審查補的。）
4. 修前的引擎讀新檔：libsys4 本來就認得「#n」，多載這部分反而讀得對；但盒子、空閒清單、第 0 號槽的問題仍在，修前的引擎本來就讀不回 v14 的 rsm。
5. 讀入失敗時：原本越界讀的三處（結構名、函式名、框數）改成明確的錯誤訊息，並和其他讀入錯誤走同一條路以退出碼 1 結束。
6. json 讀入：多了 delegate 目標表的重建與保護頁的換回；以前 json 會把第 0 號槽吸收的雜值讀回來，現在是全 0。delegate 目標表改成看頁型別之後，參照數 0 的 delegate 頁不再登記（寫出端本來就不會寫出這種頁）。
7. 結構編號不小於結構數的 struct 頁：寫出端本來就寫空名，讀回現在一律是編號 -1（修前會越界讀）；樣本裡只有 -1 這一種。
8. **VM 重啟時的保護頁**：回標題、讀存檔、`system.Reset` 都會重建堆積；以前重建時的保護頁可能沿用頁快取裡舊頁的陣列欄位，現在一律是 0，和第一次開機相同。`system-reset` 模式的輸出逐行相同；沒有找到讀第 0 號槽這兩個欄位的程式。（實作後的語義審查補的。）

## 探針與修前對照【量測】

新模式 `resume-image` 共 33 案，每案在子行程執行，和格式有關的案兩種格式各一次。「預期讀入被拒」的案在孫行程裡讀，判法是：退出碼必須是 1（不是訊號；sanitizer 版報錯時會變成訊號），輸出含指定的訊息，而且沒有 sanitizer 報告。要做壞的或舊式的檔，用 libsys4 的讀寫函式（rsm）與 cJSON（json）改暫存資料夾裡的檔。探針原始碼沒有寫死任何腳本名稱：主程式取 AIN 記載的那一個，物件取第一個成員全是 int 的結構，多載依函式編號取第一個符合條件的。探針只用移植版寫的檔（rsm 第 9 版）；原版寫的第 14 版 libsys4 讀不了。

涵蓋：

- 盒子的往返：空的盒子、裝著物件的盒子；型別、編號 -1、格數、值、參照數、序號都回來，物件的參照數不變。
- 名字在 AIN 裡查不到（只有 rsm，json 存的是編號）：結構名、區域頁的函式名、序號超出同名個數的「名字#99」；讀入被拒，訊息帶完整的符號，沒有 sanitizer 報告。
- 多載：變數比同名第一個多、比它少、數目相同而型別不同、變數與雜湊都和第一個相同而位址不同，各推兩框（第二框返回到第一框裡）存讀；讀回後兩框、兩個區域頁、指令位址都還是那個函式。
- 檔裡的符號（只有 rsm）：同名第一個只寫名字（護欄），後面的多載在區域頁與返回紀錄都寫「名字#n」；把檔裡所有「#n」截掉（等於修前寫的檔）時，形狀相同的多載讀成同名第一個（護欄，舊檔照舊取第一個）。
- 大堆積：長到 16,384 槽、只剩約 200 個空槽（期間抑制回收），寫映像後配置 120 個字串佔住映像裡是空的槽，再讀回：參照數 0 的槽沒有型別與指標、空閒數等於參照數 0 的槽數（並逐一走過清單）、映像的字串回來；之後再配置 2,000 個（會觸發回收）字串仍正確。另一案在同一個行程裡先後讀回同一狀態的 rsm 與 json，兩次的空閒數相同。
- 第 0 號槽：讀回後是開機時的保護頁；另兩種情形是存檔前保護頁已經吸收過寫入、讀入時放掉的另一個 64 格頁可能被頁快取交出來。
- delegate 目標表：映像裡有物件與指向它的 delegate、讀回前先釋放物件，讀回後再釋放物件時 delegate 指向它的項目要被刪掉；寫映像之後才登記的 delegate，讀回後釋放那個物件不會動到映像裡的 delegate（護欄）。
- 框數：比呼叫堆疊多一框（4097）時讀入被拒、不寫出界；剛好 4096 框讀得回（護欄）。

**沒有驗的**：讀回後每個呼叫框除了函式、返回位址、區域頁與 struct 頁以外的內部欄位（移植版自己加的，見〈仍有差異與未涵蓋項目〉），以及 delegate 頁的游標。

**沒有被擋下的那一個**：不先重設，只是讓讀入前的舊表和新登記並存。舊表只在找某個物件的 delegate 時用到（釋放那個物件，或對它做 struct 指派），每次只動指向那個物件的項目；映像裡真的指向它的 delegate，重建時也會登記上去，結果相同；沒有就沒有項目可動。所以行為上看不出來，只多佔記憶體，沒有補案。語義審查判這個理由在正常情況下成立，只有一個極邊緣的例外（映像本身帶著一個陳舊的項目、讀入前的舊表又剛好有對應的登記）；重設才是和 rsm 原本一致的做法，保留。

**預測的紀錄照實寫**：突變表在第一個突變結果出來之前建立，預測欄寫在表裡；表之後被整份改寫填入實際結果，預測欄當時的內容沒有另存副本或雜湊，所以「預測沒有事後改過」只能說沒有看到改過的跡象。整個換回的那一個其實是重現先前已經量過的修前結果，真正事前預測的是其餘十四個，它們的結果和事前寫的逐案相同（十三個擋下的案、一個沒被擋下）。

## 仍有差異與未涵蓋項目

- **讀回之後畫面與操作不正常的兩個成因**（提交之後，下一組的前期研究由紀錄與程式對上，經獨立查核成立；修正在下一組 R1b，作為同一組、一次提交，見[讀回後的場景狀態](../resume-scene-state/README.md)）：

  2. **呼叫框的內部欄位沒有還原（這一組「讀回正確性」沒有涵蓋到的）**：VM 讀回時每個呼叫框只還原了檔案裡的四個欄位；移植版自己加的欄位（返回時校正堆疊用的基準、是不是方法或委派呼叫、閉包的環境頁等）與委派的游標沒有還原，之後第一次函式返回就把運算堆疊截掉——堆疊下溢的警告就是這樣來的，委派迴圈剩下的處理也會被跳過。新探針驗了框的函式、返回位址與頁，沒有驗這幾個欄位。程式提交與它的訊息不改（訊息寫的是「原因沒有追」，提交當時成立）。
  - 另外，查核指出玩家的選單存檔可能也經過同一個存檔函式（還沒定案）；下一組的驗收會加選單存讀與讀修正前的舊存檔。
- **失敗時的處理那一段要做的**：先完整驗證、成功才拆掉現有堆積，讀不回時回到腳本並讓玩家看得到出口；錯誤訊息照原版做成要玩家確認的對話框；既有錯誤訊息直接用共用緩衝區的那四則一起改；寫出端改成同名的函式一律帶序號，讀入端把「沒有序號、而名字有多個同名函式」視為讀不回，舊檔才能判定（上面連帶的行為改變第 3 項）；寫快照失敗時的回傳照原版的約定；讀回函式的每個呼叫入口都要涵蓋。實作者另記的範圍外觀察：指令位址無效時報錯會越界讀；json 讀入沒有範圍檢查（這一段只加了框數）、把最底框的返回位址讀成別的值；rsm 寫出端在呼叫堆疊是空的時候會讀空指標（遊戲碰不到）；讀入後沒有更新回收器的掃描上限（量到的情形都正常）；延後釋放的佇列與回收的抑制狀態在讀回時沒有重設。
