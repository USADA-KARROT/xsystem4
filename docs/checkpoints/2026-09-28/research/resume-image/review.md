## 已採用與保留的宣稱邊界

- 【量測】有對照過兩份原版引擎寫的快照：原版是 rsm 第 14 版、另一套配置，移植版寫 libsys4 的第 9 版，互不相容；「空結構名」與「名字#n」是移植版在第 9 版裡自己的記法。不能寫成「與原版的快照相容」，也不能寫成「沒有和原版的檔對照過」。
- 【量測】兩個重試鈕修後都不會讓程式結束，但回到戰鬥之前打贏後回到地圖全黑、回到一格之前讀回後全黑、重播後要按兩次才回標題；下一組之前不能寫成「重試修好了」或「重試可以用」。
- 【量測】黑畫面的出口（Esc → 設定頁 → 回標題 → 確認框 → 讀存檔）在回到一格之前與重試打贏之後兩種黑畫面都實測過；確認框在測試環境由自動應答按確定，玩家要自己按。重試打贏的成果保不住：右鍵沒有反應，地圖上的系統鈕開出的系統選單看不見（右鍵在兩種黑畫面都試過，系統鈕只在重試打贏後的黑畫面試過）；「系統選單裡沒有存檔」是由選單項目的型別與對白畫面那個看得見的系統選單推的，給玩家只寫量得到的「看不見，沒辦法從那裡存檔」。
- 【量測】實機的全滅與打贏都是人工條件（重試趟用敵方 HP 與攻擊 ×100 的遊戲資料複本；打贏那一趟另用敵方速度 1、攻擊 ×100、HP 不變的複本，第一次只丟道具）；原版數值下沒有輸過，也沒有「輸了、重試、打贏」；第二次重試沒有走到。
- 【量測】所有實機趟都在螢幕鎖定下跑；沒有和原版同情境的畫面對照。
- 【推論→查核】全黑的直接原因在提交當時是推論、沒有追；之後下一組的前期研究由紀錄與程式對上、經獨立查核成立（部件存出是空的、讀回時部件引擎放棄、遊戲結束畫面那一層留著）。修正在下一組。
- 【讀程式，提交後查清】讀回之後操作不正常的另一個原因在 VM 讀回本身：每個呼叫框只還原了檔案裡的四個欄位，移植版自己加的欄位與委派的游標沒有還原。**這是這一組「讀回正確性」沒有涵蓋到的**：新探針驗了框的函式、返回位址與頁，沒有驗這幾個欄位。不能寫成「讀回後 VM 狀態完全正確」。程式提交與它的訊息不改（訊息寫的是「原因沒有追」，提交當時成立）。
- 【量測】修前寫的真實快照：進地圖的 20 個讀得回、寫出再讀在比對的欄位上相同；比對的範圍與限制（同一份程式自己寫自己讀、帶序號的真實映像只有 4 份由 json 轉寫）照實寫，不能寫成「每一槽每一框都相同」——json 轉 rsm 的往返在最底框的返回位址不同（json 讀入端修前就有的行為）。
- 【量測】突變表在第一個結果之前建立，預測欄沒有另存副本；真正事前預測的是 14 個。不能寫成「預測都有事前紀錄」。
- 【量測】片頭三趟提交後的逐像素比對沒有獨立重算，只有關卡自己的判準結果；獨立重算的是時序、錨點與落點餘裕。
- 【讀程式】修後的引擎讀修前寫的檔時，形狀與雜湊都和同名第一個相同的多載會讀成第一個而不報錯；真實樣本裡沒有出現；引擎快照（重試與回想用的那兩三份）是同一次執行裡寫後讀。玩家的選單存檔可能也經過同一個存檔函式（還沒定案），所以不寫「快照只在同一次執行裡寫後讀」這種斷言。
- 【讀程式】讀不回時仍然結束程式（退出碼 1）；既有的錯誤訊息沒有改，其中四則仍把共用緩衝區傳給錯誤常式。
- 提交說明的讀法（不 amend，以研究頁為準）：「This fixes reading the image itself」要讀成移植版寫的快照讀得回來、讀回後的堆積是 VM 預期的狀態；呼叫框的內部欄位與委派游標沒有還原（提交後才查清，見上）。「The game writes each image in the same run that reads it」要讀成引擎快照（重試與回想用的那兩三份）是同一次執行裡寫後讀；玩家的選單存檔可能也經過同一個存檔函式，還沒定案。「most likely from what is not restored yet; their cause was not traced」在提交當時成立；之後查清楚的兩個成因，一個是快照旁邊的部件資料存出是空的，另一個在 VM 讀回本身（呼叫框的內部欄位與委派游標），不屬於訊息開頭所說「快照旁邊還沒有還原的東西」（見上兩點）。原版那一段的「written by the original game」是高把握的推論（第 14 版、沒有加密、帶型別名、日期和紀錄吻合）；「-1 when empty」「an array element, 0」裡的值是量到的，把它們當成「空」是解讀。
